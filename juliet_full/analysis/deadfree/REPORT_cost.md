# DeadFree cost comparison (layer3 eval, 2,656 units) — cost lane

Generated by `make_cost.py` → `cost_deadfree.json` (all numbers + file paths), `cost_deadfree.csv`, `cost_deadfree.md`.
`make_cost.py` is offline and rerunnable: the public prices were fetched once on 2026-11-25 and are constants in the
script.

## Slide message (suggestion)

1. Per 1,000 DeadFree units our FT L4-D (opt.) costs **$0.070** on a rented RTX 3090. That is about the same as
   DeepSeek L1 ($0.065) and more than Jev L1/L3 ($0.036/$0.039). It is cheaper than DeepSeek L4 ($0.110) and Jev L4-D ($0.182).
   On an owned GPU, electricity alone is $0.006 per 1k.
2. One-off cost: 2.3 GPU-h of training ($1.16 rented) plus 0.14 CPU-h of dynamic labelling. At the rental price this pays
   off after ≈11k units against Jev L4-D and ≈31k units against DeepSeek L4. It never pays off against DeepSeek L1 or Jev L3.
3. Cost is not where we win. Every cloud model is already well under $0.20 per 1k units. Our case is the latency (0.47 s vs 0.8–1.0 s c1) and
   keeping code on-premise, at a quality cost (macro-F1 0.826 vs 0.86–0.95).

## Method

### Cloud (actual billed usage)
- Source: `juliet_full/llm/ledger.jsonl`, rows with `kind == "call"`, `layer == "layer3"`. Cost is the sum of `cost` per run set
  divided by 2,656, × 1,000.
- Run sets:
  - DeepSeek L1–L3: `l3_n25_L*_r1` + `l3_apirest_L*_r1` + `l3_rest_L*_r1` (664 + 664 + 1,328 calls).
  - DeepSeek L4: `l3_n25_L4_r1` + `l3_rest75_L4_r1` (664 + 1,992).
  - Jev L1–L3: `l3_eval_L*_r1` (2,656 each).
  - Jev L4-D: `eval_r1`, strategy L4D (15,619 question calls).
- Coverage, all checks passed:
  - For each per-unit set, the set of `unit_id` equals the 2,656 layer3 eval units (`data/build/layer3.jsonl`, set == eval),
    each exactly once.
  - Jev L4-D: every `qid` appears once, and per unit the call count equals `n_questions_kept` in
    `l4d_ft/results/jev_l4d/layer3/eval_r1_units.jsonl` (0 units without a kept question).
  - All calls have status ok.
- Recompute check: the token usage recomputed with `llm/llmlane/pricing.py` (at the logged `peak_price` flag) matches the
  billed `cost` exactly (relative difference 0.0) for every method.
- DeepSeek tokens per unit:

  | | input | cached | output | cache-hit share |
  |---|---|---|---|---|
  | L1 | 565 | 199 | 16 | 35 % |
  | L2 | 1,234 | 891 | 16 | 72 % |
  | L3 | 616 | 411 | 16 | 67 % |
  | L4 | 1,230 | 839 | 81 | 68 % |

- No eval call was billed at the peak price (0 %), so billed = all-off-peak. The all-peak cost is 2× (peak multiplier in
  `pricing.py`, Beijing Mon–Fri 09–12, 14–18).
- Jev bills input tokens only ($0.042 per 1M; output free). There is no cache field.
- Excluded from per-1k, reported in `cost_deadfree.json` `side_runs_not_in_per_1k`:
  - latency300 c1 runs: DeepSeek ¥0.26–0.53 per 1k, cheaper because of a warmer prefix cache; Jev $0.036–0.184 per 1k.
  - The Jev L4-D `lat_smoke` run.

### Local GPU time per unit
- c1: mean `extra.server_forward_s` of the primary (fallback causal_conv1d = prediction config) latency300 c1 run named in
  `latency_deadfree.csv`:

  | method | file | mean |
  |---|---|---|
  | L4-D (opt.) | `l4d_ft/results/lora_l4d_opt/layer3/lat300_c1_fallback.jsonl` | 0.5077 s |
  | L1 | `l4d_ft/results/kernel/decision_ft/fallback/layer3/latency300_L1_v1.jsonl` | 0.1032 s |
  | L3 | `.../latency300_L3_v1.jsonl` | 0.1146 s |

- batch, L4-D: `unit_forward_s` (one forward batch of all the unit's questions), deduplicated per unit, from the three fold files.
  - Files: `l4d_ft/build/remote_results/lora_l4d/layer3/eval_r1_fold{0,1,2}.jsonl`. The task named
    `l4d_ft/results/lora_l4d/layer3/eval_r1_fold*.jsonl`. Those files do not exist there; the merged
    `results/lora_l4d/layer3/eval_r1.jsonl` is byte-identical after sorting to their concatenation (37,376 rows).
  - These are the full question sets: 1.204 GPU-s per unit.
  - Opt equivalent: each unit's time × its own `n_questions_kept` (from `lora_l4d_opt/layer3/eval_r1_units.jsonl`) /
    `unit_n_questions`, giving 15,619 / 37,376 questions kept and **0.506 GPU-s per unit**.
  - Cross-check on the same 300 latency300 units: the measured forward ratio opt/full is 0.431 against a question ratio of 0.423,
    which gives 0.520 GPU-s per unit. Linear scaling is therefore about 3 % optimistic.
  - The wall-clock time of the three eval runs including model load is 3,199 s, or 1.20 s per unit for the full set (`l4d_batch_detail`).
- batch, old LoRA L1/L3: mean `latency_s` of `decision_ft/results/decision_ft/layer3/L{1,3}_cv_v1.jsonl`. This is server-side time per
  unit at batch size 1 on one RTX 3090 (meta `latency_note`).

### Prices (all fetched 2026-11-25)
- FX: 0.15005 USD/CNY from https://api.frankfurter.app/latest?from=CNY&to=USD (ECB reference rates, ECB date 2026-11-24).
  Cross-check: https://open.er-api.com/v6/latest/CNY gives 0.149742. CNY values are kept in the JSON/CSV.
- Rental: $0.50/h for one RTX 3090, RunPod Secure Cloud on-demand, https://www.runpod.io/pricing (page HTML
  `data-secure="0.5" data-community="0.22"`). Community Cloud $0.22/h is used as a sensitivity only.
- Power: 350 W, "Graphics Card Power (W)" for the RTX 3090 on
  https://www.nvidia.com/en-us/geforce/graphics-cards/30-series/rtx-3090-3090ti/.
- Electricity:
  - CNY 0.791/kWh, China business tariff, https://www.globalpetrolprices.com/China/electricity_prices/ (data
    collected March 2026, incl. distribution, transmission and taxes). That is $0.1187/kWh, or **$0.0415 per GPU-h**.
  - Sensitivity: the US commercial average of 14.27 ¢/kWh (EIA Electric Power Monthly Table 5.6.A, Sept 2026,
    https://www.eia.gov/electricity/monthly/epm_table_grapher.php?t=epmt_5_6_a) is about 20 % higher, which gives $0.050 per GPU-h.
  - The Shanghai-specific tariff page was not tried. The China national business average was used instead.
- Amortized purchase row: **not included**. No public RTX 3090 street-price page could be read with our tools
  (bestvaluegpu.com returned HTTP 403, and the Tom's Hardware GPU price tracker no longer lists the 3090).

## Assumptions and caveats
- Cloud: these are the prices we were actually billed. DeepSeek ran with prefix caching (35–72 % of input tokens were cache hits)
  and off-peak scheduling (a peak gate kept every eval call off-peak). At peak or without the cache, DeepSeek costs up to 2× more
  (see the all-peak column). Prices are as of the run dates (2026-11-23..25).
- Local excludes engineering time, the host machine, storage, the idle GPU time between requests, and the network.
  The rental price implicitly includes the hardware, so rental rows are the comparable number.
- The electricity-only rows are a **lower bound**:
  - The GPU is assumed to draw its full board power only for the GPU-seconds used.
  - Host CPU, PSU losses and the hardware purchase are excluded.
- The local per-unit time is for one unit per forward batch (same as eval and latency300) on an under-utilised 3090.
  Batching several units per forward would cut the GPU-s per unit, but this was not measured.
- The L4-D (opt.) batch time is an estimate. The stored predictions asked the full question set, so the time was rescaled per unit (see
  the cross-check above). The c1 measurement of the pruned set (0.508 s) agrees within 0.3 %.
- One-off excludes:
  - smoke and speed tests and dev re-selection;
  - eval predictions on the other layers;
  - the old LoRA (decision_ft) training;
  - training a deployment model on all data (≈1.5× the questions of one fold; not measured).
- The break-even against DeepSeek L1 and Jev L3 is "never" at the Secure rental price because ours costs more per unit
  ($0.070 vs $0.065 / $0.039). With RunPod Community ($0.22/h) or an owned GPU, ours becomes cheaper per unit, and
  break-even is 1.7k–71k units (sensitivity table).
- Every cloud model has higher macro-F1 than ours (0.86–0.95 vs 0.826). The cost comparison is therefore not at equal quality.
- Sanity vs the expected ranges:
  - DeepSeek ¥0.280 (L3, cheapest) to ¥0.731 (L4, most expensive) per 1k, inside the expected ¥0.28–0.73.
  - Jev L1 $0.0364/1k (expected ≈ $0.036) and Jev L4-D $0.182/1k (expected ≈ $0.18).
  - No deviations.

# 创新结论与证据分级：哪些是真实发现，哪些只是工程技巧

**生成日期**：2026-11-12（Asia/Shanghai）
**范围**：只读综合 `hybrid/REPORT.md`、`pair_joint/report.md`、`evidence_prompt/analysis/report.md`、`juliet_repair/report/comparison.md`、`analysis/model_comparison.md`，以及 `traditional/` 与 `benchmark/` 中的传统工具结果。本文件不重跑 API、不改写任何原始结果、不覆盖旧 run。
**口径**：`pp` = 百分点；`strict` = 全部计划单元计入、invalid/API error 记错；`valid-only` = 只在有效输出上计算；`common valid` = 两个条件都有效的交集。所有 McNemar 均为精确双侧；bootstrap 为配对 bootstrap（10,000 次；`pair_joint`/`evidence_prompt`/`model_comparison` 按项目或配对聚类，`hybrid` 为配对单元 bootstrap；`pair_joint`/`evidence_prompt`/`model_comparison` 用 seed 42，`hybrid` 用 seed 20261112，除非另注）。

## 0. 结论摘要

### 0.1 可以写进论文/答辩的三句话

1. **联合 A/B 的任务级提升是真实的，但不能归因于“跨版本推理能力”。** 同一 180 对上，分侧独立判定的 DA 只有 11.67%（DeepSeek）/7.78%（MiMo），联合强制二选一升到 76.67%/86.67%（McNemar p≈3.6e-34/3.6e-43）。然而“选较短版本”这一条不看语义的规则就有 74.44%；DeepSeek 与它不可区分（p=0.6587），只有 MiMo 显著高于它（p=0.0003）。联合 prompt 还消除了分侧基线中 113/108 个 `both_safe`，因此这是“任务框架 + 强制选择 + 长度分布”的复合效应，不是干净的比较推理证据。

2. **证据行提示显著提高召回，但主要是把操作点推向“多报”，不是提高判别力。** DeepSeek 召回 29.13%→38.58%（+9.45 pp，Holm p=0.0055），FPR 25.00%→34.38%（+9.38 pp，Holm p=0.2500）；MiMo 召回 24.37%→35.29%（+10.92 pp，Holm p=0.0010），FPR 20.69%→34.48%（+13.79 pp，Holm p=0.2500）。两个模型的 balanced accuracy 变化为 +0.0004 / −0.0143，MCC 为 −0.0020 / −0.0276。证据行 `±3` 命中率与同函数随机抽同样多行的基线几乎相同（62.79% vs 62.50%；63.64% vs 59.66%），引用行精确率只有 21.89%/25.55%。所以可以写“操作点偏移”，不能写“检测能力提升”或“可靠定位”。

3. **工具证据在 Juliet 冻结 test 140 上没有可检测的边际收益；“100%”是天花板上的 5 个单元。** DeepSeek direct 135/140（96.43%）→combined 140/140（100.00%），+3.57 pp，5 对 0，精确 McNemar p=0.0625；5 个不一致样本时这已经是可能的最小 p，实验没有功效在 0.05 水平上宣称显著。MiMo 135/140→138/140（+2.14 pp，4 对 1，p=0.375）。shuffled 安慰剂两个模型都恰好 135/140；133/140 个单元在 5 种方法下预测完全不变。工具的独立准确率是动态 91.43%、静态任一工具 85.00%，低于 LLM direct 的 96.43%；动态证据的 12 个 bad 未观察到泄漏、静态有 4 个 test 单元编译失败，证据方法继承了这些错误。

### 0.2 不能写的五句话

- 不能写“LLM + 工具达到 100%，显著优于基线”。100% 是 140 个单元、5 个 `_22` good 假阳性被修复的结果；p=0.0625，且天花板使证据最多只能修复 5 个单元。
- 不能写“联合 A/B 证明模型会做跨版本漏洞推理”。联合 prompt 同时改变了任务（消除 `both_safe`）、呈现长度（两版本并列）和选择约束（强制 A/B）；长度与位置两个混淆都足以解释大部分表观增益。
- 不能写“证据行可以可靠定位漏洞”。`±3` 命中率近随机，引用行精确率 21.89%/25.55%，修复行 exact 召回 16.33%/14.61%；`grounded=100%` 只说明引用行非空、在范围内，不说明定位正确。
- 不能写“修复 100%”或“可推广到真实项目”。58/58 只覆盖 70 个 bad 中 58 个 LSan 可观测单元；全 70 的 strict 是 58/70（82.86%）；12 个单元在 harness 根集配置下根本不产生可观测泄漏；没有真实项目编译/PoC。
- 不能写“DeepSeek 显著优于 MiMo”或“MiMo 显著优于 DeepSeek”。12 个 run 的模型轴是 post-hoc，所有比较在 Holm 后都不显著；表观差异主要由覆盖率、字段漂移和修复 schema 口径驱动。

### 0.3 证据分级定义

| 等级 | 定义 | 本文件中的用途 |
| --- | --- | --- |
| **E1 可复现的对照效应** | 有明确对照、统计支持、混淆已被设计排除或至少量化；可在同一冻结数据上复现 | 可以写成主要实证结论 |
| **E2 方向性证据** | 统计支持，但存在单一关键混淆（长度、位置、单模型、单次运行、事后分层） | 只能写成“方向一致/假设”，不能写成确证 |
| **E3 工程/描述性证据** | 管线在指定数据上跑通，指标可审计，但不能外推能力 | 写成“在本设置下通过”，不写成“方法有效” |
| **E4 不可支持** | 功效不足、天花板、事后选择、口径依赖，或效应与噪声同量级 | 不进入结论，只作为限制或未来工作 |

本文件的核心判断是：**这个项目目前最强的创新不是“新检测器/新修复器”，而是“把看起来很大的收益拆成可检验的成分”这一测量与归因框架。** 方法学贡献（冻结 split、泄漏审计、strict/valid-only 双口径、安慰剂、配对 bootstrap）是真实的，但它属于“让结论可信”的工程与评测创新，不是 SOTA 声明。

### 1.2 为什么同一件事会有不同数字

读这份文件时最容易误读的是“同一个模型为什么有 96.43%、97.14%、76.67% 等不同数字”。它们不是矛盾，而是不同任务/口径：

| 口径 | 含义 | 典型例子 |
| --- | --- | --- |
| 独立检测 accuracy | 160 或 140 个单函数二分类，全部计划单元 | hybrid direct 135/140 = 96.43% |
| 配对 DA | 180 对中“漏洞侧判漏洞且修复侧判安全”的比例 | pair_joint 138/180 = 76.67% |
| 分侧 pair DA | 每对两次独立单函数判定，再组合成 DA | 11.67% / 7.78%（DeepSeek / MiMo direct） |
| strict | invalid/API error 记错，分母为全部计划单元 | evidence 160 strict 38.75%→43.75% |
| valid-only / common valid | 只在有效输出、或两条件都有效的交集上算 | evidence common valid `n=159/148` |
| 工具端到端 | 编译失败/超时按“未报泄漏”计入 | Clang 200 端到端 accuracy 86.50% vs 可评估 87.63% |

**关键**：`pair_joint` 的 76.67%/86.67% 不能与独立检测的 96.43% 直接比较；前者是“二选一”，后者是“单函数是否有漏洞”。`hybrid` 的 100% 也不能与 `pair_joint` 的 86.67% 比较；前者是 140 个单函数，后者是 180 对。后文所有表格都带分母或口径。

## 2. 发现 A：联合 A/B 的 +65/+79 pp 是任务框架效应，不是干净的跨版本推理

### 2.1 主结果：提升巨大且可重复

同一 180 对、同一 A/B 映射（HMAC-SHA256，90/90 平衡）、同一 prompt 版本 `pair-joint-2026-11-12.1`：

| 对比 | joint DA | 分侧基线 DA | ΔDA | 不一致 b/c | McNemar p | 项目聚类 95% CI |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| DeepSeek vs direct | 138/180 = **76.67%** | 21/180 = 11.67% | **+65.00 pp** | 118 / 1 | 3.611e-34 | [+58.65, +77.91] |
| DeepSeek vs context | 76.67% | 22/180 = 12.22% | +64.44 pp | 117 / 1 | 7.162e-34 | [+56.89, +79.61] |
| MiMo vs direct | 156/180 = **86.67%** | 14/180 = 7.78% | **+78.89 pp** | 142 / 0 | 3.587e-43 | [+74.15, +87.62] |
| MiMo vs context | 86.67% | 19/180 = 10.56% | +76.11 pp | 137 / 0 | 1.148e-41 | [+71.34, +84.88] |

Wilson 95% 区间：DeepSeek 76.67% [69.97%, 82.25%]；MiMo 86.67% [80.93%, 90.87%]。两模型均 180/180 返回 `A` 或 `B`，`both_vulnerable`/`both_safe`/`invalid` 都是 0。

这个效应很大，而且两个模型方向一致，所以“联合 A/B 任务级提升”本身是 **E1**。但它不是“模型会做跨版本推理”的证据，原因在下面三个混淆。

### 2.2 混淆一：强制二选一改变了任务

分侧基线的低 DA 主要不是“判反”，而是 **`both_safe`**：DeepSeek direct 113/180、MiMo direct 108/180 把两侧都判成非漏洞。联合 prompt 明确说“恰好一个版本有漏洞”，模型不能输出 `both_safe`，于是原本“两侧都安全”的保守输出被强制分配到一个槽位。

| 基线（同一 180 对） | correct | both_safe | both_vulnerable | swapped | invalid |
| --- | ---: | ---: | ---: | ---: | ---: |
| DeepSeek direct | 21 | 113 | 44 | 2 | 0 |
| DeepSeek context | 22 | 108 | 49 | 1 | 0 |
| MiMo direct | 14 | 108 | 27 | 5 | 26 |
| MiMo context | 19 | 106 | 38 | 3 | 14 |

因此 §2.1 的 +65/+79 pp 比较的是“分侧自由判定”与“联合强制二选一”两种任务，不只是 prompt 措辞差异。**不能把全部增益归因于“看到另一版本”。** 要分离这一点，必须做开放 `both`/`neither` 消融（§8.3）。

### 2.3 混淆二：长度启发式单独就有 74.44%

修复通常会增加检查/代码，所以漏洞版本往往更短。180 对中：

| 长度关系 | 对数 | 占比 |
| --- | ---: | ---: |
| 漏洞版本更短 | 130 | 72.22% |
| 漏洞版本更长 | 44 | 24.44% |
| 等长 | 6 | 3.33% |

一条完全不看语义的规则——“选字符数较短的版本；等长时选 A”——在 180 对上正确 134 次，**DA = 74.44%**；按行数则 133/180 = 73.89%。

| 模型 | 漏洞更短（130） | 漏洞更长（44） | 等长（6） | joint vs 字符启发式 b/c | McNemar p |
| --- | ---: | ---: | ---: | ---: | ---: |
| DeepSeek | 109/130 = 83.85% | 25/44 = 56.82% | 4/6 = 66.67% | 25 / 21 | **0.6587** |
| MiMo | 123/130 = 94.62% | 28/44 = 63.64% | 5/6 = 83.33% | 29 / 7 | **0.0003** |

解读必须分两层：

- **DeepSeek 的 76.67% 与 74.44% 在统计上不可区分（p=0.6587）。** 它的净增益来自“漏洞更长”的 44 对（56.82%，而启发式按定义在这些对上全错），但在“漏洞更短”的 130 对上反而低于启发式（83.85% vs 100%）。所以 DeepSeek 的联合结果**不能排除“主要学到了长度/格式”**。
- **MiMo 的 86.67% 显著高于长度启发式（p=0.0003）。** 它在“漏洞更长”的 44 对上仍有 63.64%，说明存在超出长度的信号；但它在“漏洞更短”的 130 对上只有 94.62%，仍受长度分布影响。因此 MiMo 的证据是“**有**超出长度的信号”，不是“**主要**是跨版本推理”。

这是本实验最重要的限制，也是最重要的正结果：**只有 MiMo 提供了超出长度伪影的统计证据；DeepSeek 没有。** 该诊断是测试后加入的，不是预注册基线，因此只能算 **E2**。

### 2.4 混淆三：DeepSeek 有 31.11 pp 的位置偏差

A/B 顺序由 HMAC 伪随机产生，90/90 平衡；位置与标签在期望上独立。但模型本身强烈偏向 A：

| 模型 | 漏洞在 A：DA | 漏洞在 B：DA | 差值 | Fisher p | 选 A / 选 B | A 占比 | 二项 p |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| DeepSeek | 83/90 = 92.22% | 55/90 = 61.11% | **31.11 pp** | 1.0e-06 | 118 / 62 | **65.56%** | 3.6e-05 |
| MiMo | 80/90 = 88.89% | 76/90 = 84.44% | 4.44 pp | 0.5114 | 94 / 86 | 52.22% | 0.6020 |

难度混杂检查：分侧 direct 基线在同样的 A/B 分组上 DA 为 13.33% vs 10.00%（DeepSeek）、10.00% vs 5.56%（MiMo），两组难度接近；因此 DeepSeek 的 31 pp 差距不太可能由分组难度解释，更像 first-position bias。由于聚合 DA 混合了“漏洞在 A”和“漏洞在 B”两种情形，31 pp 的位置效应会同时影响总体点估计和错误结构。**没有 A/B 反向重复，就不能区分“位置偏好”与“该位置代码更易判”的细微交互。**

### 2.5 证据行质量：格式合规不等于定位正确

joint 输出的证据行审计：

| 模型 | evidence 存在 | schema 完全匹配 | evidence 合规 | 行文本精确匹配 | 判对且可定位 | 定位命中（判对中） | 判对且命中（全体） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| DeepSeek | 180/180 | 180/180 | 177/180 = 98.33% | 348/356 = 97.75% | 129 | 120/129 = 93.02% | 120/180 = 66.67% |
| MiMo | 180/180 | 180/180 | 176/180 = 97.78% | 363/370 = 98.11% | 146 | 140/146 = 95.89% | 140/180 = 77.78% |

3 个 DeepSeek 证据不合规是格式问题（整行 `"79 | ..."` 放进 `line` 字段、或行号写成字符串且缺 `code`）；4 个 MiMo 不合规是附加了另一版本的一行。定位可评分 pair 少于判对 pair，是因为部分 pair 的 diff 只有插入（修复新增行），漏洞版本没有可定位的变更行（DeepSeek 9 个、MiMo 10 个）。**这些数字说明“证据格式基本合规”，不说明“证据定位正确”；后者在 §3.2 单独评估。**

### 2.6 判定

| 主张 | 证据等级 | 可以写 | 不能写 |
| --- | --- | --- | --- |
| 联合 A/B 相对分侧任务有大幅提升 | **E1（任务级）** | “在 180 对上，joint DA 从 11.67%/7.78% 升到 76.67%/86.67%，p≈1e-34/1e-43” | “模型具备跨版本推理能力” |
| 提升超出长度伪影 | **E2（仅 MiMo）** | “MiMo 86.67% 显著高于 74.44% 长度启发式（p=0.0003）” | “两个模型都超出长度”或“LLM 普遍能跨版本推理” |
| 提升来自比较而非强制选择 | **E4（未识别）** | “强制二选一消除了 113/108 个 both_safe，任务已改变” | “看到另一版本是增益的原因” |
| 证据行可审计/可定位 | **E2（格式）/ E4（定位）** | “98% 证据格式合规；定位需进一步验证” | “证据行可靠定位漏洞” |

## 3. 发现 B：证据行提示移动的是操作点，不是判别力

### 3.1 召回显著上升，FPR 同向上升，MCC/BA 不升

数据：160 个冻结函数（128 漏洞 / 32 非漏洞，40 项目）；主检验在共同 valid 样本上做精确 McNemar，四个主检验（2 模型 × recall/FPR）做 Holm 校正。

| 模型 | 共同 valid n | 召回 direct→evidence | Δ召回 | 召回 Holm p | FPR direct→evidence | ΔFPR | FPR Holm p | ΔBA | ΔMCC | strict acc（全 160） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| DeepSeek | 159 | 29.13% → 38.58% | **+9.45 pp** | **0.0055** | 25.00% → 34.38% | +9.38 pp | 0.2500 | +0.0004 | −0.0020 | 38.75% → 43.75% |
| MiMo | 148 | 24.37% → 35.29% | **+10.92 pp** | **0.0010** | 20.69% → 34.48% | +13.79 pp | 0.2500 | −0.0143 | −0.0276 | 32.50% → 41.88% |

关键细节：

- 召回的新增 TP/丢失 TP：DeepSeek +13/−1，MiMo +13/−0；FPR 的新增 FP/修复 FP：DeepSeek +3/−0，MiMo +4/−0。**两个模型都是“新增 TP 远多于丢失 TP”，但新增 FP 没有任何修复。**
- predicted positive rate 明显上升：DeepSeek 28.30%→37.74%，MiMo 23.65%→35.14%。这就是“操作点向多报移动”的直接证据。
- balanced accuracy 基本不动或下降（+0.0004 / −0.0143），MCC 下降（−0.0020 / −0.0276）。**召回/F1 的上升不能解释为判别力提升。**
- FPR 的点估计上升，但负例只有 32/29 个，McNemar p=0.25，不能宣称“显著增加 FPR”；同样也不能宣称“没有增加 FPR”。正确写法是“FPR 点估计上升，区间很宽，当前样本不足以判定”。Wilson 区间：DeepSeek evidence FPR 34.38% [20.41%, 51.69%]；MiMo 35.48% [21.12%, 53.05%]。
- 严格口径（invalid 算错）：DeepSeek 38.75%→43.75%（+5.00 pp，p=0.0963）；MiMo 32.50%→41.88%（+9.38 pp，p=0.0026）。MiMo 的严格提升有一部分来自 schema 合规（direct 10 条 invalid → evidence 2 条），不能全部解释为检测能力提升。
- 解释边界：如果下游 triage 中漏报（FN）的代价远高于误报（FP），这个更高召回的操作点可能有实用价值；但它是**操作点/先验的移动**，不是判别力提升，而且 FPR 代价在当前 32/29 个负例下没有被精确估计。

### 3.2 定位：`±3` 近随机，exact 仅略高于随机，引用行精确率低

证据行按 1-based 行号审计；`grounded` 只表示引用行非空且在范围内；`changed_lines` 映射到函数体行号只用于评估。随机基线是在同一函数里随机抽同样多的行，至少碰到一个修复行的期望概率（超几何分布，对 TP 取平均）。

| 模型 | TP 可映射 | exact hit | exact 随机 | ±3 hit | ±3 随机 | 引用行精确率 exact | 引用行精确率 ±3 | 修复行 exact 召回 | 修复行 ±3 召回 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| DeepSeek | 43 | 48.84% | 34.46% | **62.79%** | **62.50%** | 21.89% | 34.34% | 16.33% | 35.68% |
| MiMo | 44 | 45.45% | 31.59% | **63.64%** | **59.66%** | 25.55% | 39.65% | 14.61% | 31.23% |

怎么读：

- **`±3` 命中率与随机基线几乎相同**（DeepSeek 62.79% vs 62.50%；MiMo 63.64% vs 59.66%）。这说明“引用行在修复行附近”这件事，在粗粒度上基本可以用“引用足够多的行”解释。
- **`exact` 命中率高于随机**（48.84% vs 34.46%；45.45% vs 31.59%），但引用行精确率只有 21.89%/25.55%，修复行 exact 召回只有 16.33%/14.61%。模型平均引用 6.95/5.03 行，覆盖面广但精度低。
- `grounded=100%`、`counterfactual confirmed≈100%` 在 TP 和 FP 上都成立（DeepSeek TP/FP 都是 1.000；MiMo TP 0.979、FP 1.000），**反事实自检没有区分真伪正例的能力**。它不是独立验证，不能替代编译/PoC/人工评审。
- 映射质量：128 个漏洞样本中，DeepSeek/MiMo 都是 full=108、partial=9、none=11；716 个修复行条目中 683 个可映射。exact/±3 只在可映射 TP 上算，分母已列出。

### 3.3 判定

| 主张 | 证据等级 | 可以写 | 不能写 |
| --- | --- | --- | --- |
| 证据行提示提高召回 | **E1** | “召回 +9.45/+10.92 pp，Holm p=0.0055/0.0010” | “检测能力显著提升” |
| 召回提升不牺牲 FPR | **E4** | “FPR 点估计上升，负例太少无法判定” | “提高召回而不增加假阳性已经实现” |
| 证据行提升判别力 | **E4** | “BA/MCC 不变或下降，是操作点偏移” | “证据让模型更会区分漏洞” |
| 证据行可靠定位 | **E2/E4** | “exact 略高于随机，±3 近随机，引用精度低” | “证据行可作为可靠定位” |

## 4. 发现 C：工具证据在 Juliet 上没有可检测的边际收益；“100%”是天花板

### 4.1 主结果：+3.57 pp，p=0.0625

140 个冻结 test 单元（70 bad / 70 good，58 C / 82 C++），2 模型 × 5 方法 = 1400 请求，全部 `ok`，无 invalid/API error。

| 模型 | direct | static | dynamic | combined | shuffled（安慰剂） |
| --- | ---: | ---: | ---: | ---: | ---: |
| DeepSeek | 135/140 = 96.43% | 135/140 = 96.43% | 139/140 = 99.29% | **140/140 = 100.00%** | 135/140 = 96.43% |
| MiMo | 135/140 = 96.43% | 136/140 = 97.14% | 135/140 = 96.43% | **138/140 = 98.57%** | 135/140 = 96.43% |

配对比较（strict，精确 McNemar，配对 bootstrap 10,000 次）：

| 模型 | 对比 | Δ准确率 | 95% CI | 不一致（新对/旧对） | p |
| --- | --- | ---: | --- | ---: | ---: |
| DeepSeek | direct → combined | **+3.57 pp** | [+0.71, +7.14] | 5 / 0 | **0.0625** |
| DeepSeek | direct → dynamic | +2.86 pp | [+0.71, +5.71] | 4 / 0 | 0.125 |
| DeepSeek | direct → static | 0.00 pp | [0.00, 0.00] | 0 / 0 | 1.000 |
| MiMo | direct → combined | +2.14 pp | [−0.71, +5.71] | 4 / 1 | 0.375 |
| MiMo | direct → static | +0.71 pp | [−1.43, +2.87] | 2 / 1 | 1.000 |
| MiMo | direct → dynamic | 0.00 pp | [−2.14, +2.14] | 1 / 1 | 1.000 |

**DeepSeek 的 5 个改进单元全部是 direct 错、combined 对，没有反向翻转；但 5 个不一致样本时精确 McNemar 的最小可能 p 就是 0.0625。** 也就是说，这个实验在 0.05 水平上**没有功效**宣称显著；要让 p<0.05，至少需要 6 个同向不一致样本（6/0 时 p=0.03125）。MiMo 是 4 对 1，p=0.375。

### 4.2 安慰剂：聚合无收益，个体方向会动

两个模型的 shuffled 与 direct 聚合完全相同（都是 135/140），但个体预测并非完全不动：

| 模型 | 被翻动单元数 | 方向（2 个向“有漏洞”、2 个向“无漏洞”） | 供体 bad 时判 vulnerable | 供体 good 时判 vulnerable |
| --- | ---: | --- | ---: | ---: |
| DeepSeek | 4/140 | `malloc_realloc_int64_t_09__good`、`new_array_wchar_t_72__good` → 1；`new_array_int_22__good`、`twoIntsStruct_realloc_22__good` → 0 | 41/70 = 58.6% | 34/70 = 48.6% |
| MiMo | 4/140 | `int_calloc_54__good`、`int_malloc_22__good` → 1；`new_array_char_22__good`、`new_array_int_22__good` → 0 | 39/70 = 55.7% | 34/70 = 48.6% |

解读：

- 错配证据确实会按供体方向轻微推动边界样本：供体是 bad 时更倾向判 vulnerable，供体是 good 时更倾向判 not_vulnerable；幅度约 7–10 pp，方向对称，净准确率恰好不变。
- **因此 combined 相对 direct 的 +5/+3 个单元不能简单归因于“多了一段证据文本”：同样长度、同样格式的错配证据没有带来聚合收益。**
- 但受样本量限制，这只是方向性证据，不能作为显著因果结论。当前只抽了一个 derangement，无法估计 placebo 的抽样分布；需要多 placebo（§8.4）。
- 两个模型都有 **133/140 个单元在 5 种方法下预测完全一致**；方法间差异集中在其余 7 个边界单元。这说明代码本身仍是主导信号，证据只在少数边界样本上起作用。

### 4.3 天花板与 `_22` 错误结构

DeepSeek direct 的 5 个错误**全部是 FP，且全部是 `_22` good**：`int_malloc_22`、`new_array_char_22`、`new_array_int_22`、`new_int_22`、`twoIntsStruct_realloc_22`。combined 全部纠正。

MiMo direct 有 4 个 FP（同样是 `_22` good 中的 4 个）和 1 个 FN（`malloc_realloc_int_01__bad`）。combined 纠正了 3 个 `_22` FP 和该 FN，但新增 `int_malloc_22__good` 这个 FP，并保留 `twoIntsStruct_realloc_22__good`，净错误数从 5 降到 2。

`_22` 变体通过全局变量在多个 sink 之间传递控制流；good 版本在“另一条”分支释放内存，direct 容易只看到当前分支未释放而误报。动态 clean 证据和组合证据能帮助模型重新检查全局标志，但 MiMo combined 仍有 2 个 FP（都是 C 单元；其 82 个 C++ 单元全部正确）。**这是一个可检验的机制假设：动态 clean 证据主要修复“全局控制流导致的假阳性”，而不是普遍提升检测。** 但当前只有 5 个单元，不能把这个机制写成已证结论。

### 4.4 传统工具的错误结构：高精度、低召回，与 LLM 互补但不显著

| 方法 | 数据/分母 | TP | FP | TN | FN | 召回 | FPR | 准确率 | 备注 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| Clang SA 22.1.8 | Juliet 200，可评估 194 | 73 | 0 | 97 | 24 | 75.26% | 0.00% | 87.63% | 6 个编译失败；端到端 86.50% |
| Cppcheck 2.21.0 | Juliet 200 | 30 | 4 | 96 | 70 | 30.00% | 4.00% | 63.00% | 4 FP |
| ASan+LSan / Valgrind | Juliet 全量 3,316 | 1,467 | 0 | 1,658 | 190 | 88.53% | 0.00% | 94.27% | 1 个 inconclusive；accuracy 按 3,315 decisive 计；C 82.03%、C++ 95.69% |

- LLM direct 是“高召回、较低 specificity”：140 上 0 FN，但 5 个 FP；combined 恰好把这 5 个 FP 修掉。
- 这看起来是完美的互补，但 **互补只发生在 5 个同变体单元上**；在 96.43% 的 ceiling 下，证据最多只能修复 5 个单元。不能把“5 个单元被修复”外推为“工具证据普遍有效”。
- 工具证据还继承了工具错误：动态 12 个 bad 未观察到泄漏（会被渲染成 clean，虽然 prompt 明确“clean 不是证明”），静态 4 个 test 单元编译失败（渲染为“分析失败、无结论”）。这些错误在真实项目上可能更大。

## 5. 发现 D：修复 58/58 是“可观测合成子集”的上限，不是通用修复能力

### 5.1 数字

70 个冻结 bad 单元，同一清洗输入、同一 compile/LSan/behaviour harness；每模型一次初始请求 + 至多一次反馈迭代。

| 指标 | DeepSeek V4.1 Flash | MiMo V2.6 Flash |
| --- | ---: | ---: |
| compile pass（全 70） | 70 | 70 |
| leak removed（全 70；12 个 vacuous） | 70 | 70 |
| behaviour preserved（全 70） | 70 | 70 |
| **strict pass（全 70；non-evaluable 记失败）** | **58/70 = 82.86%** | **58/70 = 82.86%** |
| **strict pass（58 个可观测）** | **58/58 = 100%** | **58/58 = 100%** |
| first-attempt strict（58 可观测） | 58/58 | 57/58 |
| 使用反馈的单元 | 0 | 2（1 次真实 compile/LSan/behaviour 失败，1 次 schema/parse 拒绝） |
| 被拒绝的响应 | 0 | 1 |
| API 调用数 | 70 | 72 |
| 成本 USD | $0.026990 | $0.005841 |

### 5.2 12 个 vacuous 单元为什么不能算“修复成功”

58/70 的分母不是随便选的：70 个 bad 中有 12 个在 harness 的 LSan 根集配置（`use_stacks=0:use_registers=0`）下**根本不产生可观测泄漏**：

- 7 个 `malloc_realloc` 用例只有在 `realloc` 失败时才泄漏；
- 5 个 variant-68 用例把唯一指针放在全局变量里，LSan 把它当作 reachable。

这些单元的 compile/behaviour 结果可以报告，但**不能支持“leak removed”**。所以：

- 58/58 是“**在 58 个可观测合成 bad 单元上**全部通过”；
- 全 70 的 strict 是 58/70 = 82.86%；
- 12/70 = 17.14% 的单元是“不可评估”，不是“通过”。

### 5.3 反馈回路的边际价值很小

- DeepSeek 一次都没用反馈，first-attempt 就是 58/58。
- MiMo 用了 2 次反馈：1 次真实失败、1 次 schema/parse 拒绝；first-attempt 57/58，最终 58/58。**反馈回路净贡献 1 个单元。**
- 这更像工程上的“保底重试”，不是“迭代修复能力”的证据。要证明反馈有价值，需要构造 first-attempt 失败率更高的困难集（真实项目、复杂补丁），并报告每次迭代的边际收益与成本。

| 修复可推广到真实项目 | **E4** | “未做真实项目编译/PoC；需要外部验证” | “可修复真实 CVE”或“行为保持已被证明” |

### 6.1 12 个 run 的矩阵

| 6 | 工具证据提升 LLM 检测 | +3.57 pp（5/0，p=0.0625）；MiMo +2.14 pp（4/1，p=0.375）；placebo 135/135 | **E2/E4** | “点估计为正，但在 ceiling 下未达显著” | “显著提升”或“100% 所以有效” |
| 7 | 安慰剂证明证据内容有效 | placebo 聚合与 direct 相同；4/140 个体翻动，方向对称；供体 bad/good：DeepSeek 58.6/48.6%，MiMo 55.7/48.6% | **E2** | “模型会读证据方向，但代码仍是主导信号” | “证据内容已被证明有效” |
| 8 | 修复达到 100% | 58/58 可观测；全 70 strict 58/70；12 vacuous | **E3** | “58 个可观测合成 bad 上 58/58；全 70 为 58/70” | “修复成功率 100%”或“可推广到真实项目” |
| 9 | 反馈迭代提升修复 | MiMo first-attempt 57/58 → 58/58；DeepSeek 0 反馈 | **E3/E4** | “反馈净贡献 1 个单元” | “迭代反馈普遍有效” |
| 10 | 跨模型总体排名 | 12 run；所有模型比较 Holm 后不显著；coverage/schema 主导 | **E2/E4** | “没有稳健总体赢家；差异是端点特定的” | “DeepSeek/MiMo 整体更强” |
| 11 | 统一评测协议/泄漏审计/安慰剂/双口径 | 跨实验：1400/1400 请求（hybrid）、200/200 清洗（Juliet）、180/180 prompt（pair_joint）、140/140 direct prompt 一致（hybrid） | **E1（方法学/工程）** | “可复现、可审计的评测协议” | “新检测方法达到 SOTA” |

**结论**：真正能作为“创新证据”的是第 1、2、3、11 条，其中第 1 条是任务级效应、第 2 条是单模型方向性证据、第 3 条是操作点偏移、第 11 条是方法学/工程贡献。第 4、5、6、7、8、9、10 条都是**负结果、限制或工程技巧**，不能包装成能力提升。**如果论文只能保留一个“新意”，应保留“收益分解”：把联合 A/B、证据行、工具证据、修复四类表面收益，分别对照长度、位置、强制选择、操作点、天花板五类伪影，给出可复现的归因表。** 这比“又做了一个 LLM+工具”更有区分度，也更诚实。

### 7.1 工程技巧清单：可写进“可复现性”，不要写进“创新点”

| 工程技巧 | 作用 | 为什么不是创新证据 |
| --- | --- | --- |
| 统一 runner / prompt wrapper / JSON schema / retry / cache | 让 1400+ 请求可批量、可恢复、可审计 | 是实验基础设施，不改变方法的能力上限 |
| 源码清洗 / 标识符重命名 / 泄漏审计 | 去除 Juliet 的文件名、注释、`bad`/`good`、CWE 标签 | 是测量前提；审计通过只说明“没有明显泄漏”，不说明模型推理 |
| strict / valid-only 双口径 | 避免把 invalid/格式失败静默丢弃 | 是评分规范，不是检测算法 |
| 安慰剂 / derangement | 分离“证据内容”与“证据长度/格式” | 当前只抽了一个 draw，本身还不足以估计 placebo 分布（需 §8.4） |
| 修复 harness（compile/LSan/behaviour） | 把“生成补丁”变成可执行检查 | 只覆盖 58 个可观测合成单元；12 个 vacuous；无真实项目/PoC |
| 反馈迭代（至多一次） | 在 schema/编译失败时保底重试 | MiMo 净 +1 个单元；DeepSeek 未使用；不是“迭代修复能力” |
| 成本/延迟记账 | 区分列表价、allowance、cached token | 是运营指标；DeepSeek 的 reported cost 还多报 28.5% |

这些技巧让结果**可信**，但它们不是“新方法”。论文的 novelty 应放在“收益分解 + 对照设计”，而不是“我们又接了一个工具”。

### 7.2 真正创新证据的边界

- **可以主张**：在同一冻结集上，联合 A/B 相对分侧任务有大幅任务级提升；MiMo 的联合结果显著超过长度启发式；证据行提示显著提高召回但主要是操作点移动；工具证据在 ceiling 下没有可检测的边际收益；修复只在可观测合成子集上饱和。
- **不能主张**：跨版本推理能力、通用工具增益、可靠证据定位、通用修复、模型总体排名、SOTA。
- **最能站住的“新意”**：不是某个单点方法，而是“用长度/位置/强制选择/操作点/天花板五类对照，把表面收益拆开”的评测与归因框架。它产生的是**可复现的负结果和边界条件**，这比一个未经对照的 +3.57 pp 更有信息量。

## 8. 下一步最有价值的消融

### 8.0 优先级与预算总表

### 8.1 P0：长度匹配（最关键的消融）

**为什么最关键**：当前 180 对中 130 对（72.22%）漏洞版本更短；长度启发式 74.44%，DeepSeek 76.67% 与它不可区分（p=0.6587），MiMo 86.67% 才显著高于它（p=0.0003）。如果不控制长度，联合 A/B 的“跨版本推理”主张无法成立。

**设计**：

1. **匹配子集（最便宜）**：在现有 180 对中按 `|len_vuln − len_fixed| / max(len)` 分层，取差值最小的层；但等长只有 6 对，匹配子集会非常小，只能作为案例，不能作为主检验。
2. **新构造匹配对（推荐）**：从同一批项目/函数族中构造 **≥300 对**，要求 `|Δchars|/max ≤5%` 且 `|Δlines| ≤1`；漏洞/修复长度差接近 0，长度启发式退化为 50%（tie 规则除外）。两模型、AB+BA 两顺序；主终点为双顺序平均 DA，对照 50% 与长度 oracle 50%。
3. **统计**：精确 McNemar；项目聚类 bootstrap；预注册“长度匹配子集”为主要分析，原始 180 对为次要/敏感性。报告每层的 DA 与长度差分布，不要只报总体。
4. **功效**：若 300 对中 20% 不一致（60 个 discordant），80% 功效可检测约 70/30 的 discordant 方向（精确检验约 83.8%）；若只有 10% 不一致（30 个），80% 功效约对应 75/25（精确检验约 80.3%）。当前 180 对、20% 不一致（36 个）时，70/30 只有约 61% 功效；这就是为什么当前 76.67% vs 74.44% 的 p=0.66 不能证明“无差异”，只能证明“没有足够证据”。
5. **判定**：如果匹配子集 DA 的 95% CI 下界 >50%，且显著高于长度 oracle（按构造为 50%），才能写“存在超出长度的信号”；如果 CI 跨 50%，写“在本匹配子集上未检测到超出长度的信号”，不要写“模型不会推理”。

**能回答**：联合增益在长度信息被移除后还剩多少。
**不能回答**：真实项目中长度差是否天然存在；匹配会改变样本分布，外推需谨慎。

### 8.2 P0/P1：A/B 反向（直接估计位置偏差）

**为什么关键**：DeepSeek 漏洞在 A 时 92.22%、在 B 时 61.11%（31.11 pp，Fisher p=1.0e-06），选 A 118/180（65.56%）；MiMo 只有 4.44 pp（p=0.5114）。当前只用 90/90 平衡降低位置与标签的相关，不能消除“同一对换槽位后模型是否改变”的 within-pair 位置效应。

**设计**：

- 现有 180 对每对跑 **AB 和 BA 两次**；两模型共 720 请求；同一 prompt、同一温度，只改槽位。
- 指标：顺序一致率（同一对两次选同一“内容版本”的比例）、按槽位 DA、选 A 率、McNemar（AB vs BA 的正确性）、混合效应/条件 logistic（槽位 + 正确性 + 项目随机截距）。
- 判定：若 DeepSeek 的顺序一致率低、槽位系数显著，则 31 pp 是真实位置偏差，主结果应报告“双顺序平均 DA”并单独报告位置效应；若 MiMo 的顺序一致率高，说明其 86.67% 不是位置驱动。
- 功效：31 pp 的效应在 180 对上很容易显著；4.44 pp 的效应在当前 90/90 分组上不显著，若要排除中小位置效应，需要数百对量级——若不一致率约 20%，约 270–300 对才能在 70/30 方向上达到 80% 功效；不一致率更低时需要更多。因此 MiMo 的位置效应即使不显著，也不能写“无位置偏差”，只能写“未检测到”。

**能回答**：DeepSeek 的总体 DA 中有多少是“选 A 倾向”；双顺序平均后联合增益是否仍在。
**不能回答**：位置偏好与“该位置代码更易判”的细微交互，仍需内容级分析。

### 8.3 P1：开放 both/neither（分离强制选择）

**为什么关键**：分侧基线 113/108 个 `both_safe` 被联合 prompt 消除；这是任务改变，不是能力提升。当前 `both`/`neither` 为 0 是强制指令的直接结果，不代表模型在开放任务中不会输出。

**设计**：

- 同一 A/B 展示，允许 `vulnerable_version ∈ {A, B, both, neither}`；180 对 ×2 模型；保留 evidence/rationale 字段。
- 另构造 **60 对 both-vulnerable + 60 对 both-safe** 的对照（从同一数据池配对），测量模型的“过度报警/过度保守”；这两类在真实代码中合法，但在当前 one-sided 数据中不存在。
- 指标：四类分布、DA（只在 one-sided 对上）、both/neither 的校准、与 forced-choice 的逐对一致性。
- 判定：若开放 prompt 下 both/neither 比例 >20%，则 forced-choice 的 76.67%/86.67% 不能解释为“模型能比较”；若比例很低且 DA 接近，说明强制选择不是主要驱动。
- 额外价值：both-vuln/both-safe 对照可以估计模型在真实“可能两侧都有问题”的场景中的错误率，这是当前 one-sided 数据无法回答的。

**能回答**：强制二选一贡献了多少；模型在开放场景是否过度报警/过度保守。
**不能回答**：真实项目中 both/neither 的先验比例；需要真实数据。

### 8.4 P1：多 placebo（估计安慰剂分布）

**为什么关键**：当前只抽了一个 derangement；两个模型 shuffled 都恰好 135/140，4/140 个体翻动方向对称。单次抽样无法区分“证据内容无效”与“这次 placebo 恰好净收益为零”。

**设计**：

- **20 个独立 derangement**（非自身、不同 group），每个 140 单元 ×2 模型 = **5,600 请求**；或先做 10 个 draw（2,800 请求）看方差。
- 三种 placebo：
  1. **同格式错配证据**（当前）：供体来自不同 group；
  2. **长度匹配的随机文本**：与真实证据同样 token 长度，但不含泄漏方向；
  3. **方向翻转证据**：取真实证据但把 leak/clean 方向反转，测量模型是否按方向调整。
- 指标：每个 draw 的 accuracy、TP/FP 翻转数、predicted positive rate；placebo 均值/SD/95% 区间；真实 combined 与 placebo 分布的比较（permutation/rank）。
- 判定：真实 combined 必须超过 placebo 95% 区间，才能说“证据内容有聚合效应”；否则只能写“格式/长度/方向效应，净收益不显著”。
- 预算：20 个 draw 约 $0.41（按 hybrid combined 单价）；这是性价比最高的消融之一。

**能回答**：工具证据的 +3.57 pp 是否大于 placebo 抽样分布；当前单次 placebo 的“零净收益”是否稳定。
**不能回答**：placebo 的“表面可信度”是否与真实证据完全匹配；只能尽量匹配格式/长度/来源。

### 8.5 P2：多 seed / 重复解码

**为什么关键**：所有实验都是单次贪心解码（temperature=0），没有模型方差估计；temperature=0 不保证确定性（`juliet_llm` 的 MiMo 两次真实运行 140 上 accuracy 0.9571 vs 0.9500，差 1 个单元）。当前 2–3 pp 的差异（如 hybrid +3.57 pp、模型 macro-F1 +3.1 pp）与端点/解码噪声同量级。

**设计**：

- **5 次重复，temperature=0**：估计服务端非确定性；180 对 ×2 模型 ×5 = 1,800 请求，约 $1.13。
- **3 次重复，temperature=0.7**：估计采样方差；可加多数投票作为探索性条件，但不要与 greedy 结果混在一起。
- 指标：每次的 DA、macro-F1、accuracy；between-seed SD、ICC、95% 区间；单次结果的“是否落在重复分布内”。
- 判定：若 between-seed SD >5 pp，则任何小于 5 pp 的单次差异都不能作为结论；若 SD 很小，当前点估计更可信。
- 对检测任务同样适用：160 函数 ×2 模型 ×5 次 = 1,600 请求。

**能回答**：2–3 pp 的差异是否只是解码噪声；当前单次点估计的稳定性。
**不能回答**：模型版本更新带来的漂移；需要锁定版本/端点。

### 8.6 P2：真实项目编译/PoC（外部效度）

**为什么关键**：Juliet 是合成、单缺陷、模板生成；SecVulEval 是函数片段；修复只到文本/结构层面，没有真实项目编译/PoC。当前所有“修复”结论都不能外推到真实 CVE。

**设计**：

- 选 **20–30 对真实 C/C++ CVE**（vulnerable/fixed commit），优先有公开 PoC/ARVO/OSS-Fuzz 复现的样本；排除训练集已见过的 CVE（至少做去污染检查/时间切分）。
- 四阶段指标：
  1. patch apply（补丁能否应用到 vulnerable 版本）；
  2. compile（项目能否构建）；
  3. PoC blocked（原 PoC 是否不再触发崩溃/泄漏）；
  4. regression（现有测试是否通过）。
- 另做 **检测**：模型能否在真实项目上下文中指出 vulnerable 版本/行；与静态/动态工具对比。
- 盲评：至少两人独立判断补丁是否真正修复，而不是只“让 PoC 不触发”；报告 Cohen's κ。
- 预算：主要成本是 Docker/构建/人工，2–4 周；API 成本按当前单价约 $10–50 量级，取决于补丁长度和迭代次数。
- 判定：只有四阶段都通过才能写“在该 PoC/测试下修复”；否则报告阶段 attrition（apply/compile/PoC/regression），不要只报“生成成功”。
- 功效边界：20–30 对只适合做外部效度/可行性验证，不足以检测小效应；若要统计比较修复率，需要 100+ 对或预注册的案例系列，并报告每个阶段的失败原因。

**能回答**：合成集结论是否外推；修复是否真的能编译、阻断 PoC、保持行为。
**不能回答**：所有真实项目/所有 CWE；样本量和项目选择仍是限制。

### 8.7 补充：证据行因果干预（让“定位”从关联变成因果）

当前只测了“引用行与 changed_lines 的重叠”，没有测“模型是否因果使用引用行”。建议：

- 对 200–300 个 TP/FP 样本，构造三种干预：
  1. **gold line**：只给真实 changed line；
  2. **random line**：给同函数随机行；
  3. **counterfactual line**：删除/变异引用行对应的代码，观察预测是否翻转。
- 指标：预测翻转率、证据行必要性（删除后是否改变答案）、充分性（只给该行是否足以复现答案）。
- 判定：若 gold line 与 random line 无差异，说明证据行不是因果定位；若删除引用行后预测不翻转，说明模型没有真正使用该行。
- 这比继续增加“证据行数量”更能回答“证据是否忠实”。

## 9. 统计功效与解释边界

### 9.1 当前关键对比的功效

| 对比 | N | 不一致 b/c | 精确 p | 能得出的结论 |
| --- | ---: | ---: | ---: | --- |
| DeepSeek combined vs direct | 140 | 5 / 0 | **0.0625** | 5 个同向样本时可能的最小 p；**无法**在 0.05 显著 |
| MiMo combined vs direct | 140 | 4 / 1 | 0.375 | 无显著差异 |
| DeepSeek joint vs 长度启发式 | 180 | 25 / 21 | 0.6587 | 与长度不可区分 |
| MiMo joint vs 长度启发式 | 180 | 29 / 7 | 0.0003 | 显著高于长度 |
| DeepSeek 证据召回 | 127 正例 | 13 / 1 | 0.0018（Holm 0.0055） | 召回显著提高 |
| DeepSeek 证据 FPR | 32 负例 | 3 / 0 | 0.2500 | 负例太少，不能判定 |
| MiMo 证据 FPR | 29 负例 | 4 / 0 | 0.1250（Holm 0.2500） | 负例太少，不能判定 |
| 模型 few-shot macro-F1 | 160 | — | Δmacro-F1 CI [+1.0, +12.9] pp 排除 0；严格准确率 McNemar Holm 0.157 | 边缘/不一致，不能写“显著” |

**最小 p 的算术**：5 个不一致样本全部同向时，双侧精确 p = 2×(1/2)^5 = 0.0625；6 个同向时 p = 2×(1/2)^6 = 0.03125。因此 hybrid 的 DeepSeek 结果不是“差一点显著”，而是**在这个样本量下不可能显著**；要显著，必须增加单元或找到第 6 个同向不一致样本。

### 9.2 为下一步设计做的功效近似

精确 McNemar 在双侧 α=0.05 下，若不一致对数为 `n_d`、其中“新方法正确”的比例为 `p`，则拒绝域由二项分布决定。下表是精确计算（不是正态近似）：

| 不一致对数 n_d | p=0.65 | p=0.70 | p=0.75 | p=0.80 |
| ---: | ---: | ---: | ---: | ---: |
| 18 | 18.9% | 33.3% | 51.9% | 71.6% |
| 36 | 35.6% | 60.9% | **83.3%** | 95.8% |
| 54 | 57.3% | **83.7%** | 96.7% | 99.7% |
| 60 | 55.9% | **83.8%** | 97.0% | 99.8% |
| 90 | 81.2% | 97.3% | 99.9% | 100% |
| 100 | 82.8% | 97.9% | 99.9% | 100% |

用法：

- 若计划 300 对、预期 20% 不一致（n_d=60），80% 功效可检测约 70/30 的方向；若真实效应只有 65/35，功效只有约 56%，需要更多对。
- 若只有 180 对、20% 不一致（n_d=36），70/30 只有约 61% 功效；当前 DeepSeek 与长度比较的 46 个不一致、25/21 分裂，当然不显著。
- **不要用“p>0.05”证明无差异**；应报告 CI，并说明“在本样本量下只能排除大于 X pp 的效应”。

### 9.3 FPR 与负例数量

evidence_prompt 只有 32 个非漏洞样本（MiMo 共同 valid 29 个）。FPR 的点估计从 25.00%→34.38%（DeepSeek）、20.69%→34.48%（MiMo），但 95% Wilson 区间很宽（例如 DeepSeek evidence [20.41%, 51.69%]）。因此：

- 不能写“证据提示不增加 FPR”；
- 不能写“证据提示显著增加 FPR”；
- 只能写“FPR 点估计上升，当前负例数量不足以判定；需要扩充负例或使用更大样本”。

### 9.4 单次运行与端点噪声

- 所有 run 都是单次贪心解码；没有多 seed、多服务副本。`juliet_llm` 的 MiMo 两次真实运行在同一 140 上 accuracy 0.9571 vs 0.9500（差 1 个单元），说明端点/解码噪声与 hybrid 的 +3/+5 个单元同量级。
- 模型版本、端点路由、tokenizer/chat template 可能随供应商更新；复现时必须锁定 run 目录与配置指纹。
- 因此，**任何小于 5 pp 的单次差异都应视为不稳定**，除非有多 seed 或独立复现。

## 10. 限制清单

### 10.1 设计与数据

1. **合成/片段数据**：Juliet 是模板生成的单缺陷单元；SecVulEval 是函数片段；没有真实项目仓库级上下文、构建系统、跨函数数据流。所有结论的外部效度有限。
2. **单数据集、单时间点**：每个任务只有一个冻结测试集；不能外推到其他 CWE、语言、项目或未来模型版本。
3. **项目不平衡**：pair_joint 中 `linux` 占 53/180；项目聚类 bootstrap 受少数大项目影响。独立检测 40 项目、配对 60 项目， cluster 数有限。
4. **单次运行**：每个 (model, strategy, dataset) 只有一个 run；temperature=0 不保证确定性；没有模型方差估计。
5. **模型/端点配置不对称**：DeepSeek 非 thinking + `max_tokens`；MiMo `reasoning_effort=none` + `max_completion_tokens`；两者都走 OpenCode Go，但 tokenizer/chat template/路由可能不同。比较的是“模型+配置”，不是纯权重。

### 10.2 测量与统计

6. **多重比较**：pair_joint 的 4 个 baseline 对比未做 Holm；模型轴 12 个 run 的 Holm 只在 dataset×endpoint family 内；length/position/placebo 是 post-hoc 诊断，不是预注册。所有“显著”都应带“在该 family/该诊断下”的限定。
7. **FPR 负例太少**：evidence_prompt 只有 32/29 个负例；FPR 区间很宽，不能判定“不增加 FPR”。
8. **McNemar 独立性假设**：同一项目/同一 pair 内相关可能让 p 偏小；主分析用 cluster bootstrap 作为补充，但 cluster 数有限。
9. **天花板效应**：hybrid direct 96.43%，最多 5 个错误；证据方法没有足够空间展示效应。`100%` 不是“完美检测”，而是“在这个 140 单元、这个错误结构上刚好全对”。
10. **口径依赖**：修复 CAC 的官方排名与 code-only 反事实方向相反；MiMo 的 strict 提升部分来自 schema 合规；DeepSeek 的 strict 损失主要来自缺 `explanation`。不能把口径差异读成能力差异。

### 10.3 构念与外部效度

11. **证据行是模型自报，不是执行证明**：`grounded` 只说明行非空/在范围内；`changed_lines` 映射有 11 个 none、9 个 partial；反事实自检没有编译/测试，且在 TP/FP 上都接近 1，不能区分真伪。
12. **动态 clean 不是验证过的 TN**：动态 run 没有行/分支覆盖；clean 只表示 `NO_LEAK_OBSERVED`。12 个 test bad 未观察到泄漏；全量 190 个 FN。把 clean 当负标签会继承工具 FN。
13. **静态编译失败不是零**：Clang 200 有 6 个 compile_error（test 140 有 4 个）；端到端视图把它们按“未报泄漏”计，可评估视图排除它们。两种口径都报，但不能只报一种。
14. **修复 harness 的根集配置**：12 个 bad 在 `use_stacks=0:use_registers=0` 下不可观测；它们不是“修复成功”，也不是“修复失败”，是“不可评估”。`behaviour preserved` 只到 harness 定义的数据行，不是完整语义等价。
15. **没有真实项目编译/PoC**：修复结论只到文本/结构/合成 harness；不能声称补丁可编译、漏洞已消除、行为保持。
16. **没有人类评审**：修复/证据行没有独立人工标注；现有盲评是 LLM 辅助（81 候选/30 案例，κ=0.015），不能替代人类判断。

### 10.4 泄漏与数据伪影

17. **长度伪影**：130/180 漏洞版本更短；长度启发式 74.44%。这是最重要的混淆，且是测试后诊断。
18. **强制选择伪影**：分侧基线 113/108 个 `both_safe` 被消除；联合任务不是同一任务。
19. **位置伪影**：DeepSeek 31.11 pp 的 A/B 偏差；MiMo 4.44 pp 不显著，但也不能证明无偏差。
20. **残余标签泄漏**：pair_joint 1/180 对两侧相同注释含 `CVE-2017-17969`；不指示槽位，但不能清除。Juliet 清洗审计 200/200 通过，但清洗器不是形式化证明。
21. **证据格式问题**：3 个 DeepSeek 证据不合规（2 个把整行编号放进 `line`，1 个把行号写成字符串且缺 `code`）；4 个 MiMo 证据附了另一版本的行。严格规则判不合规，没有事后改写；这会轻微影响证据质量统计。
22. **标签/理由不一致**：DeepSeek 有 2 个 FP 的 `reason` 写“No leak”但 `label=vulnerable`；按 `label` 评分，未把 `reason` 纳入自动评分。这说明“模型说了什么”和“模型选了什么”可能不一致。

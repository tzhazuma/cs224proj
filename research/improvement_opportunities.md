# DeepSeek V4.1 Flash 三策略：失败诊断与改进机会

> **证据边界**：本文只读取并复算现有产物，不发起新的 API 请求，不修改 `runner/runs/test_v1_*`、`report/`、`analysis/`、`qualitative/` 中的任何旧结果。所有数值要么直接来自 `report/results_summary.md`、`analysis/aggregation.md`、`qualitative/cases.md`、`repair_eval/analysis/repair_blind_v1/final/summary.md`，要么来自对 `runner/runs/test_v1_*/results.jsonl` 的只读统计。文中标注为“目标”“规划估算”“建议验收线”的数字不是实验结果。

## 0. 结论摘要

1. **主矛盾是低召回，不是低精确率。** 三种策略在 128 条漏洞样本上只召回 29.7%–32.0%，漏报 87–90 条；精确率 0.81–0.84，特异度 0.72–0.75。漏报集中在短函数（FN 中位 35 行，TP 中位 76–78 行）和生命周期/访问控制类 CWE（CWE-416 召回 1/19，CWE-20 1/9，CWE-264 0/5）。
2. **配对任务在实现上并不是“配对”任务。** 每个 pair 被拆成两次独立的单函数分类（360 次检测调用 / 180 对），prompt 中不包含另一侧；180/180 对的 context 块完全相同。结果是 DA 只有 0.089–0.122，both_clean 108–113/180，both_flagged 44–49/180；三种策略都失败的 pair 有 151/180。
3. **schema 失败主要是可回收的工程问题，不是模型不会修。** 924 条修复请求中 102 条（11.0%）schema 无效；其中 93 条是“只缺 explanation”，不是截断。93 条都能解析出 `fixed_function`，91 条结构完整，71 条有实质改动。严格校验把这 71 条可用补丁丢掉了。
4. **“与输入不同”高估了真实修改。** 22.1%/44.5%/18.8% 的修复没有实质改动（完全不变或只改空白）；few-shot 的“与输入不同”62.6% 里，有 23 条只是空白变化。盲评中 no-change/空白变化候选的 VR=2 是 **0/23**，而有实质改动的候选是 **17/58（29.3%）**。
5. **文本相似度不是修复正确率。** no-change 补丁与参考修复的行相似度中位数仍有 0.899–0.923，14–43 条达到 ≥0.9；如果只看相似度，会把“返回原文”误判成“接近参考修复”。盲评的 81/81 `compile_status` 都是 `NOT_RUN`，没有任何编译或 PoC 证据。
6. **context 策略的总体指标不可解释。** 独立集里“context 非空 ⇒ 漏洞”这条平凡规则的准确率是 98.8%、MCC 0.963；而 M3 的准确率只有 38.8%。context 非空层 126/126 全是漏洞，空层 34 条中 32 条非漏洞；M3 与 M1 只在 8/160 条上预测不同。M3 的 null effect 既不能证明“context 有用”，也不能证明“context 无用”，因为操纵本身很弱（context 中位 76.5 字符，只有标识符列表）且与标签混杂。
7. **置信度目前不能用于路由或人工分流。** ECE 0.300–0.448，Brier 0.312–0.432，confidence→correctness 的 AUC 只有 0.581–0.607；平均置信度比准确率高 0.285–0.442。高置信（≥0.9）子集的准确率只有 46.2%–54.5%，其中 few-shot 49 条高置信预测里有 23 条是错的。跨策略一致性也不提供有效信号：三策略一致时覆盖率 91.3%，准确率仍只有 38.4%。
8. **成本被修复主导，且约 28.5% 的花费没有产生可用补丁。** 三策略总成本 $2.439；修复占 65.1%。无效修复 $0.221 + 无实质改动修复 $0.474 = $0.695（28.5%）。few-shot 比 direct 贵 75.2%，只换来 +3 TP、M1−M2 的 macro-F1 = −0.0167（区间跨 0）和 −5 个正确区分 pair。
9. **最高优先级的改进不是“再换一种提示”，而是把任务改成可验证的联合任务。** 优先做：pair A/B 联合输入 + 反事实差异（P1/P3）；证据行 + CWE 约束（P2）；修复后处理/自检/编译闭环（P5）；置信度校准只作为路由的前置条件（P6）；成本预算按“每正确 pair / 每验证补丁”计（P7）。静态/动态工具反馈（P4）价值高但工程成本也高，应先做 30–50 条的子集可行性验证。
10. **当前实验没有实现协议里写的 evidence_lines、CWE、pair A/B prompt、工具反馈和编译验证。** 这些是未来建议，不是已测结论。MiMo 对比应由并行任务在**同一提示/同一 schema**下运行，避免把模型差异和提示差异混在一起。

**配对集的 repair 只跑漏洞侧。** 180 条 repair 全部是 `side=vulnerable`；修复侧（fixed）没有 repair 请求。这意味着“配对修复”实际上只是“对漏洞侧做一次单函数修复”，模型没有机会看到参考修复，也没有机会比较两侧。

### 1.2 实际实现的提示 vs 评估协议草案

`research/evaluation_protocol.md` 描述的是更丰富的 schema 和 pair A/B prompt，但 `runner/secvul_runner/prompts.py` 的实际实现是一个更简版本。两者差异直接影响如何解释结果：

| 能力 | 协议草案 | runner 实际实现 | 证据 |
| --- | --- | --- | --- |
| 检测输出 | `verdict`、`confidence`、`evidence_lines`、`cwe`、`rationale`、`schema_version` | 只有 `is_vulnerable`、`confidence`、`rationale` | `prompts.py:203-209`；`results.jsonl` 的 `parsed` 只有 3 个键 |
| 行号 | 代码按 4 位行号前缀编号，`evidence_lines` 指向编号 | 函数正文原样放入 `<FUNCTION_SOURCE>`，没有行号 | `prompts.py:219-246` |
| CWE 约束 | `cwe` 字段，允许 `CWE-\d+` | 没有 CWE 输出，也没有 CWE 条件 | `prompts.py:203-209` |
| 配对检测 | 一个 prompt 同时给 VERSION A/B，输出 `verdict_A/B` | 每个 pair 拆成两次单函数调用，prompt 中没有另一侧 | `prompts.py:231-246`；pairs run 中每个 pair 2 条 detection 记录 |
| 修复输出 | `patched_function`、`explanation`、`cwe` | `fixed_function`、`explanation` | `prompts.py:211-216` |
| schema 版本 | `det-v1` / `pair-v1` / `repair-v1` | 没有 schema 版本字段 | 同上 |
| 工具反馈 | 协议明确说未使用 Clang（0/20 可编译） | 没有静态/动态工具反馈 | `research/evaluation_protocol.md` §7.1 |
| 编译/PoC | 三值 `compile_status` | 没有编译；盲评 81/81 `NOT_RUN` | `repair_eval/.../summary.md` |
| 置信度校准 | 未实现 | 直接使用模型自报 confidence | 本文 §2.7 |
| 多 seed / 多模型 | 未实现 | 单模型、单次运行 | `report/results_summary.md` §7 |

**结论**：当前实验比较的是“三种**很轻量**的提示策略”，不是协议中更丰富的“证据行 + CWE + 配对联合”设计。任何关于 evidence_lines、CWE、pair A/B 的效果，都不能从现有结果推断；它们是本文建议的未来实验。

### 1.3 口径说明

- **检测指标**：独立集 n=160；主表用 complete-case（160/160 全部有效），无效预测计错时结果相同，因为检测 schema 无效为 0。
- **配对指标**：180 对；DA（discrimination accuracy）= 漏洞侧判漏洞且修复侧判安全的 pair 比例。`both_clean` = 两侧都判安全；`both_flagged` = 两侧都判漏洞；`reversed` = 漏洞侧判安全且修复侧判漏洞。
- **修复指标**：每策略 308 条请求。`schema_valid` 是严格 JSON 校验；`changed_from_input` 是规范化文本不同（会包含空白/缩进变化）；`whitespace_changed_from_input` 是折叠空白后仍不同，本文称为**实质改动**。`changed_from_input=true` 但 `whitespace_changed_from_input=false` 的样本，本文称为**空白变化**，与完全不变合并为**无实质改动**。
- **置信度**：模型自报的 0–1 数值，不是 API logprob；因此不能做温度缩放，只能做后验校准或分箱分析。
- **成本**：按记录级 `response.cost.cost_usd` 汇总，单位 USD；不使用套餐 allowance。价格快照见 `report/results_summary.md` §1。
- **统计**：本文的置信区间和检验沿用 `analysis/aggregation.md`；本文新增的比例只做描述性统计，不额外做显著性检验。

## 2. 量化失败模式

### 2.1 低召回是主矛盾

| 策略 | TP | FP | TN | FN | Precision | Recall | F1 | Accuracy | Specificity | MCC | Macro-F1 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| M1 direct | 38 | 8 | 24 | 90 | 0.826 | 0.297 | 0.437 | 0.388 | 0.750 | 0.041 | 0.383 |
| M2 few-shot | 41 | 8 | 24 | 87 | 0.837 | 0.320 | 0.463 | 0.406 | 0.750 | 0.061 | 0.400 |
| M3 context | 39 | 9 | 23 | 89 | 0.813 | 0.305 | 0.443 | 0.388 | 0.719 | 0.021 | 0.381 |

三策略的 macro-F1 区间高度重叠（M1 0.305–0.552，M2 0.305–0.593，M3 0.286–0.560），两两差值区间全部跨 0。**当前数据不支持“某个策略更好”的强结论；但支持“三种策略都严重漏报”这一共同结论。**

#### 漏报的结构

| 观察 | 数值 | 含义 |
| --- | --- | --- |
| FN 数量 | 87–90 / 128 | 召回只有 29.7%–32.0% |
| FN 函数行数中位数 | 35 行 | 漏报集中在短函数 |
| TP 函数行数中位数 | 76–78 行 | 检出集中在长函数 |
| 漏洞 test-path 样本 | 4 条，4 条全部 FN | 模型把测试代码判安全；可能是正确行为，也可能是标签噪声 |
| FN rationale 含 “safe” | 71/90 | 模型不是“没看懂”，而是明确判断安全 |
| FN rationale 含 “no memory” | 9/90 | 模型把“没有明显内存不安全操作”等同于“没有漏洞” |

FN 中位 35 行 vs TP 中位 76–78 行，说明模型倾向于在“有足够多代码可看”时才敢报漏洞；短函数里的生命周期错误、访问控制错误、输入校验错误更容易被“这段代码很简单，看起来安全”覆盖。这与 C-02（unit test 被判安全，但标签为漏洞）一致，也提示**标签可能是 commit 级传播**，而不是函数级可利用性。

#### 按 CWE 的召回（M1 direct；M2/M3 同量级）

| CWE | n | M1 召回 | M2 召回 | M3 召回 |
| --- | ---: | ---: | ---: | ---: |
| CWE-416（use-after-free） | 19 | 1/19 = 0.053 | 0.053 | 0.053 |
| CWE-119（缓冲区错误） | 19 | 6/19 = 0.316 | 0.368 | 0.368 |
| CWE-476（空指针解引用） | 14 | 6/14 = 0.429 | 0.357 | 0.429 |
| CWE-125（越界读） | 10 | 6/10 = 0.600 | 0.600 | 0.500 |
| CWE-20（输入校验） | 9 | 1/9 = 0.111 | 0.111 | 0.111 |
| CWE-399（资源管理） | 8 | 2/8 = 0.250 | 0.250 | 0.250 |
| NVD-CWE-noinfo | 7 | 0/7 = 0.000 | 0.143 | 0.000 |
| CWE-787（越界写） | 7 | 4/7 = 0.571 | 0.714 | 0.571 |
| CWE-264（权限/访问控制） | 5 | 0/5 = 0.000 | 0.200 | 0.200 |
| CWE-200（信息暴露） | 5 | 0/5 = 0.000 | 0.000 | 0.200 |
| CWE-190（整数溢出） | 4 | 3/4 = 0.750 | 0.750 | 0.750 |

**读法**：模型对“有明确越界/整数操作”的 CWE 召回较高（CWE-190 0.75、CWE-787 0.57–0.71、CWE-125 0.50–0.60），对“生命周期/权限/输入校验”类 CWE 召回很低（CWE-416 0.05、CWE-20 0.11、CWE-264 0–0.20）。这不是简单的“模型不够强”，而是**提示没有给模型一个缺陷类型的先验或检查清单**：任务只说“是否有安全漏洞”，模型就按“有没有显眼的内存不安全调用”去匹配。

### 2.2 配对任务实际上不是配对任务

#### 联合类别

| 策略 | 正确区分（DA） | both_flagged | both_clean | reversed | DA 比例 | 漏洞侧 Recall | 修复侧 Specificity | 总体 Accuracy |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| M1 direct | 21 | 44 | 113 | 2 | 0.117 | 0.361 | 0.744 | 0.553 |
| M2 few-shot | 16 | 49 | 113 | 2 | 0.089 | 0.361 | 0.717 | 0.539 |
| M3 context | 22 | 49 | 108 | 1 | 0.122 | 0.394 | 0.722 | 0.558 |

- 测试集随机指定一侧的双方均正确率为 **56.1%**（101/180）；DA 0.089–0.122 远低于机会水平。
- 三种策略都失败的 pair：**151/180**；三种策略都 both_clean：**103/180**；都 both_flagged：**39/180**；至少一种策略正确区分：**29/180**。
- 只有 4/2/5 个 pair 是某一策略“独有”的正确区分，说明三种提示共享同一失败模式，不是互补。

#### 为什么“配对”失效

1. **实现层面：每个 pair 被拆成两次独立调用。** pairs run 每条 detection 记录只包含一个函数；`sample_id` 是 `pair:<id>:vulnerable` 或 `pair:<id>:fixed`，`side` 字段在请求里，但模型看不到 `side`，也看不到另一侧。180 对 → 360 次 detection 调用。模型没有机会做“A 和 B 哪个变了”的比较。
2. **数据层面：pair 两侧高度相似。** 180 对的函数行级相似度中位数 **0.926**；≥0.95 有 66 对，≥0.9 有 108 对，<0.8 只有 32 对。对这样接近的两个版本，独立分类很容易给出相同判断；both_clean 113 对、both_flagged 44–49 对就是这种“看不出差异”的表现。
3. **context 层面：pair 两侧的 context 块 180/180 完全相同。** 即使 M3 想利用 context，它也没有任何“哪一侧被修过”的信息；context 只是 External Function/Globals/Type 的标识符列表，中位 83 字符。

**这不是“模型不会配对推理”，而是“模型从来没有被要求配对推理”。** 现有 DA 应被解释为“两次独立单函数分类的联合正确率”，不是配对辨识能力。任何关于“模型能否利用修复差异”的结论，都必须先实现 A/B 联合输入。

### 2.3 schema 失败是可回收的工程问题

#### 修复 schema 无效的构成

| 策略 | 无效 / 308 | 无效率 | 缺 `explanation` | 非法 JSON / 截断 | 可解析出 `fixed_function` | 结构完整 | 有实质改动 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| M1 direct | 48 | 15.6% | 45 | 3 | 45 | 44 | 35 |
| M2 few-shot | 3 | 1.0% | 0 | 3 | 0 | 0 | 0 |
| M3 context | 51 | 16.6% | 48 | 3 | 48 | 47 | 36 |
| 合计 | 102 / 924 | 11.0% | 93 | 9 | 93 | 91 | 71 |

- **93/102（91.2%）是“只缺 explanation”**，不是长度截断：这些响应 `finish_reason=stop`，`fixed_function` 完整可解析。只有 9 条是非法 JSON/截断（其中 3 条 few-shot 是 `finish_reason=length`）。
- **91/102 含完整函数，71/102 含实质改动。** 严格 schema 校验把 71 条本来可用的补丁全部判为无效；这是当前最大的“零成本可回收”损失。
- 按全部 828 请求计，无效率是 5.8%/0.4%/6.2%（与 `results_summary.md` 一致）；按 308 条修复计，是 15.6%/1.0%/16.6%。两个分母都对，但讨论修复质量时应该用后者。

#### 成本

| 策略 | 无效修复成本 | 占总成本 | 说明 |
| --- | ---: | ---: | --- |
| M1 direct | $0.0861 | 13.3% | 45 条缺 explanation + 3 条截断 |
| M2 few-shot | $0.0408 | 3.6% | 只有 3 条截断 |
| M3 context | $0.0941 | 14.2% | 48 条缺 explanation + 3 条截断 |

**改进含义**：不需要重新生成整段补丁；只需对缺 `explanation` 的响应做一次短补字段请求，或直接在评分时接受“只有 `fixed_function`”的补丁并单独报告 explanation 缺失。前者保留解释，后者零额外成本但解释质量不可评。两种都应该在新实验里作为预先登记的 schema 变体，而不是事后修改旧结果。

### 2.4 无改动修复与“文本相似度陷阱”

#### 修复的实质改动率

| 策略 | 完全不变 | 仅空白变化 | 无实质改动（合计） | 有实质改动 | schema 无效 |
| --- | ---: | ---: | ---: | ---: | ---: |
| M1 direct | 51 | 17 | 68 / 308 = 22.1% | 192 / 308 = 62.3% | 48 (15.6%) |
| M2 few-shot | 114 | 23 | 137 / 308 = 44.5% | 168 / 308 = 54.5% | 3 (1.0%) |
| M3 context | 43 | 15 | 58 / 308 = 18.8% | 199 / 308 = 64.6% | 51 (16.6%) |

- `results_summary.md` 的“与输入不同”是 80.4%/62.6%/83.3%（分母为有效修复 260/305/257）；它包含空白变化。**若按“实质改动/全部请求”计，只有 62.3%/54.5%/64.6%。**
- few-shot 的独立集无实质改动率是 **50.0%**（64/128）：一半的“修复”没有改任何非空白字符。paired 侧是 40.6%（73/180）。
- 修复 system prompt 写的是“Rewrite the supplied vulnerable function”，预设输入有漏洞；模型仍然有 22.1%–44.5% 的概率返回原文或只改空白。说明 prompt 的“必须修”与模型的“这段代码已经安全”判断冲突，且没有一致性约束。

#### 盲评中的 no-change

`repair_eval/analysis/repair_blind_v1/final/summary.md` 的 81 个候选（30 个案例）按结构分组：

| 组 | n | VR=2 | 比例 |
| --- | ---: | ---: | ---: |
| 完全不变 / 无实质改动 | 18 | 0 | 0.0% |
| 仅空白变化 | 5 | 0 | 0.0% |
| 有实质改动 | 58 | 17 | 29.3% |
| 合计 | 81 | 17 | 21.0% |

**no-change 和空白变化候选没有一条被盲评判为“处理了根因”。** 这与结构指标一致：`changed_from_input=true` 不能当作“修了”。

#### 文本相似度为什么危险

对配对修复（有参考修复的 180 条），计算 no-change 补丁与参考修复的行级相似度：

| 策略 | no-change n | 参考相似度中位数 | ≥0.9 的条数 |
| --- | ---: | ---: | ---: |
| M1 direct | 35 | 0.909 | 19 |
| M2 few-shot | 73 | 0.923 | 43 |
| M3 context | 30 | 0.899 | 14 |

也就是说，**返回原文的补丁，和参考修复的文本相似度中位数仍有 0.90 左右**，因为参考修复通常只改几行。若用“行相似度 ≥0.9”当修复正确率，会把大量 no-op 判成“接近正确”。精确匹配参考修复只有 1.7%–5.0%，这个数字才是文本层面的“完全一致”，但它同样不是语义正确率。

**结论**：修复质量必须靠“是否改了缺陷相关行 + 是否保持行为 + 是否可编译/可测试”，不能靠 BLEU/行相似度/`changed_from_input`。在现有产物里，只有 LLM 辅助盲评的 VR 分数，且 81/81 未编译；这只能支持“17/81 在该 rubric 下被认为处理了根因”，不能支持“修复正确率”。

### 2.5 检测与修复不一致

修复只跑漏洞侧，所以独立集/配对漏洞侧的检测结果可以和 repair 结果逐条对齐：

| 策略 | 数据集 | 检测 FN n | FN 中仍有实质修复 | 检测 TP n | TP 中修复无实质改动 |
| --- | --- | ---: | ---: | ---: | ---: |
| M1 direct | independent | 90 | 46 (51.1%) | 38 | 1 (2.6%) |
| M2 few-shot | independent | 87 | 31 (35.6%) | 41 | 8 (19.5%) |
| M3 context | independent | 89 | 47 (52.8%) | 39 | 2 (5.1%) |
| M1 direct | pairs (vuln side) | 115 | 74 (64.3%) | 65 | 8 (12.3%) |
| M2 few-shot | pairs (vuln side) | 115 | 61 (53.0%) | 65 | 20 (30.8%) |
| M3 context | pairs (vuln side) | 109 | 68 (62.4%) | 71 | 5 (7.0%) |

**读法**：

- 检测说“安全”的样本里，35.6%–64.3% 的修复仍然实质改了代码。模型在修复 prompt 下“知道该怎么改”，但在检测 prompt 下“不敢报”。这说明检测和修复是两个独立的提示行为，不是同一个理解的两个出口。
- 检测说“漏洞”的样本里，2.6%–30.8% 的修复没有实质改动。few-shot 最严重：它一边说“漏洞”，一边返回原文。
- 这直接支持**联合任务/一致性约束**：如果 verdict=vulnerable，补丁必须改动并给出缺陷行；如果 verdict=safe，补丁应与输入一致。当前没有这个约束，所以两个任务的输出可以互相矛盾。

### 2.6 context 伪影与弱操纵

#### 数据层面的伪影

独立集 context 分层：

| 策略 | context 非空 n=126，漏洞 126 | 非空层 Recall | context 空 n=34（2 漏洞/32 非漏洞） | 空层 Specificity |
| --- | --- | ---: | --- | ---: |
| M1 direct | 126/126 漏洞 | 0.294 | 2 漏洞 / 32 非漏洞 | 0.750 |
| M2 few-shot | 126/126 漏洞 | 0.317 | 同上 | 0.750 |
| M3 context | 126/126 漏洞 | 0.302 | 同上 | 0.719 |

“context 非空 ⇒ 漏洞”的平凡规则：

| 规则 | TP | FP | FN | TN | Precision | Recall | Specificity | Accuracy | F1 | MCC |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| context 非空 → 漏洞 | 126 | 0 | 2 | 32 | 1.000 | 0.984 | 1.000 | 0.988 | 0.992 | 0.963 |

这条规则没有任何代码理解，却在独立集上接近满分。它说明**独立集的 context 可用性与标签几乎完全共线**；M3 的总体指标不能解释为“context 推理能力”。`analysis/aggregation.md` 已经给出 `high` 风险警告，本文把它量化成一个可对照的平凡基线。

#### 提示层面的弱操纵

- M3 的 context 是 allow-list 的 5 个字段（Execution Environment、External Function、Function Argument、Globals、Type Execution Declaration），实际内容只是标识符列表。独立集 context 字符数：中位 **76.5**，均值 103.7，p95 276；空 context 34/160。配对集：中位 83，最大 857；非空 176/180。
- 这些字段能告诉模型“调用了哪些外部函数/用了哪些全局变量/参数类型是什么”，但不能告诉模型“这个指针被 free 后又被解引用”“这个长度来自不可信输入”。对生命周期/访问控制类漏洞，信息量很低。
- **配对集的 context 块 180/180 完全相同**：即使 M3 拿到 context，它也无法区分漏洞侧和修复侧。
- M3 的 prompt 对空 context 写的是 `(No usable structured context was available.)`，这本身是一个“缺失标记”，与标签相关（空层 32/34 非漏洞）。模型没有明显利用它（空层特异度 71.9%，还不如 M1 的 75.0%），但作为实验设计，这个标记应该中性化，避免把“缺失”变成泄漏。
- M1 与 M3 只在 **8/160** 条上预测不同：4 条 F→T（全是漏洞）、3 条 T→F（全是漏洞）、1 条 F→T（非漏洞）；净效果是 +1 TP、+1 FP，准确率完全一样。**M3 相对 M1 几乎没有改变行为**，所以“M3 ≈ M1”不是“context 无效”的证据，而是“这个 context 操纵太弱，根本没触发差异”。

#### 改进含义

1. **不要再用独立集总体指标评价 context 策略。** 必须报告非空/空分层；如果非空层是单类别，只报正类召回，不报 macro-F1。
2. **构造标签无关的 context**：例如固定窗口的相邻函数、调用点、类型定义、数据流事实；同一 pair 两侧使用**对称但侧相关**的 context（例如各自的调用点），而不是同一份标识符列表。
3. **中性化缺失标记**：空 context 用固定长度的占位文本，或在分析中把“空”作为分层变量，而不是在 prompt 里直接说“没有可用 context”。
4. **更强的 context 需要工具**：调用图、别名/生命周期事实、sanitizer 检查、静态分析告警，而不是只有名字列表。见 P4。

### 2.7 置信度未校准

| 策略 | 平均置信度 | 准确率 | 置信度−准确率 | ECE（10 分箱） | Brier | AUC（conf→correct） | 高置信 n（≥0.9） | 高置信准确率 | 高置信错误 | 置信度众数 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| M1 direct | 0.688 | 0.388 | +0.301 | 0.301 | 0.323 | 0.581 | 13 | 0.462 | 7 | 0.60 × 82 |
| M2 few-shot | 0.848 | 0.406 | +0.442 | 0.448 | 0.432 | 0.607 | 49 | 0.531 | 23 | 0.85 × 83 |
| M3 context | 0.672 | 0.388 | +0.285 | 0.300 | 0.312 | 0.603 | 11 | 0.545 | 5 | 0.60 × 87 |

- 置信度几乎不区分对错：正确预测的平均置信度只比错误高 0.034（M1）、0.021（M2）、0.038（M3）；AUC 0.58–0.61，接近随机。
- 置信度分布是“模板化”的：M1/M3 大量集中在 0.60，M2 大量集中在 0.85/0.90。`prompts.py:249-258` 的 few-shot assistant 示例把 confidence 固定为 0.95（漏洞）/0.90（安全），模型明显模仿了这种风格；few-shot 的 ECE 0.448，是三者最差的。**这是提示造成的置信度伪影，不是模型内在不确定性。**
- 高置信错误很多：M2 的 49 条 ≥0.9 预测里 23 条错；M1 13 条里 7 条错；M3 11 条里 5 条错。高置信子集的准确率只有 46.2%–54.5%，不能用于人工分流。

#### 风险—覆盖率（按置信度从高到低取子集）

| 策略 | 覆盖 10% | 覆盖 25% | 覆盖 50% | 覆盖 100% |
| --- | ---: | ---: | ---: | ---: |
| M1 direct | 0.562 | 0.600 | 0.450 | 0.388 |
| M2 few-shot | 0.625 | 0.650 | 0.713 | 0.406 |
| M3 context | 0.688 | 0.650 | 0.562 | 0.388 |

即使只保留置信度最高的 25%，准确率也只有 0.60–0.65；覆盖 50% 时，M1/M3 降到 0.45–0.56。**当前置信度不能支撑“高置信自动通过、低置信转人工”的路由。**

#### 跨策略一致性也不提供有效信号

| 规则 | 覆盖率 | 准确率 | Precision | Recall | Specificity |
| --- | ---: | ---: | ---: | ---: | ---: |
| 三策略一致 | 146/160 = 91.3% | 0.384 | 0.805 | 0.287 | 0.742 |
| direct + context 一致 | 152/160 = 95.0% | 0.382 | 0.814 | 0.289 | 0.742 |
| direct + few-shot 一致 | 149/160 = 93.1% | 0.389 | 0.810 | 0.291 | 0.750 |
| 多数投票 | 160/160 | 0.394 | 0.830 | 0.305 | 0.750 |

三种提示共享同一盲区；一致性没有带来精度或召回提升。**“多提示投票”不是低召回的解药。**

## 3. 改进方案（按优先级）

> 以下全部是**未实现的建议**。每条都给出“对应证据 → 具体改动 → 可检验假设 → 成本 → 验收线 → 风险”。验收线是建议值，不是已测结果。

### P1（最高优先）：pair A/B 联合输入 + 反事实差异

**对应证据**

- 每个 pair 现在是 2 次独立调用，模型看不到另一侧；360 次 detection 调用 / 180 对。
- DA 0.089–0.122，both_clean 108–113/180，both_flagged 44–49/180；三策略全失败 151/180，至少一个成功仅 29/180。
- pair 行相似度中位 0.926，≥0.95 有 66 对；独立分类几乎必然给出相同判断。
- 配对两侧 context 180/180 相同，M3 也没有任何差异信号。

**改动**

1. 新增 `pair-joint` 策略：一次调用同时给 `VERSION A` 和 `VERSION B`，A/B 顺序按 pair 随机 90/90 平衡；prompt 明确说“不要假设恰好一个是漏洞版本”，以保留 both_clean/both_flagged 的测量。
2. 输出 schema 建议：

```json
{
  "schema_version": "pair-v2",
  "verdict_A": "vulnerable",
  "verdict_B": "not_vulnerable",
  "confidence_A": 0.0,
  "confidence_B": 0.0,
  "evidence_lines_A": [8],
  "evidence_lines_B": [],
  "changed_lines": [8, 9],
  "cwe": "CWE-476",
  "rationale": "B 在第 8 行增加了空指针检查；A 没有。"
}
```

3. 两个变体，分开登记：
   - **P1a 全函数 A/B**：只给两个完整函数，不给 diff。测“模型能否自己发现差异”。
   - **P1b A/B + diff**：额外给一个只含变更行的 unified diff，测“显式差异提示”的上限。P1b 更接近“配对辨识”任务，不适合直接外推到单函数检测。
4. 评分增加 position bias：A 侧漏洞率是否随 A/B 顺序变化；报告 `A=vulnerable` 与 `B=vulnerable` 的混淆矩阵。

**可检验假设**

- 如果 both_clean 主要来自“看不到另一侧”，P1a 应显著降低 both_clean；如果模型即使看到 A/B 也无法定位变更，P1b 才会明显优于 P1a。
- 如果模型只是利用“两段代码不同 ⇒ 一定有一个漏洞”的表面线索，P1a/P1b 可能把 both_clean 转成 both_flagged 或 reversed，而不是提高 DA；因此必须同时报告四类联合结果，不能只看 DA。

**成本**

- 检测调用从 360 次/策略降到 180 次/策略；单次输入约为原来的 2 倍，输出约为原来的 2 倍（两个 verdict），总 token 大致持平或略增。请求数减半，延迟和调度开销下降。**这是规划估算，不是实测。**

**建议验收线**

- DA ≥ 0.20（当前 0.089–0.122），且配对 bootstrap 95% CI 下界 > 0.12（当前最高 0.122 的区间上界约 0.178）。
- both_clean ≤ 45%（当前 60.0%–62.8%）。
- 三策略全失败 pair ≤ 70%（当前 151/180 = 83.9%）。
- 成本 ≤ direct 的 1.2 倍。
- 如果 DA 提升但 both_flagged 大幅上升，说明模型只是“更敢报”，不是“更能区分”；这种情况不算成功。

**风险**

- pair benchmark 是人工构造的“漏洞/修复”对照，不是真实部署场景；P1 的结论不能直接外推到单函数检测。
- 给 diff 可能把任务变简单，甚至让模型只做“哪边多了检查”的模式匹配；必须把 P1a 和 P1b 分开报告。
- A/B 顺序、函数长度、语言（C vs C++）都可能带来位置/长度偏差；需要分层报告。

### P2：证据行 + 行号 + CWE 约束

**对应证据**

- 当前 prompt 没有行号、没有 `evidence_lines`、没有 CWE；模型只输出 3 个键。
- 漏报集中在短函数（FN 中位 35 行 vs TP 76–78 行）和生命周期/访问控制 CWE（CWE-416 1/19、CWE-20 1/9、CWE-264 0/5）。
- FN rationale 中 71/90 含 “safe”，9/90 含 “no memory”；模型把“没有显眼内存操作”当成“安全”。
- 数据集自带 `changed_lines`，可用于定位评分；当前完全没有利用。

**改动**

1. 代码按 `%4d | ` 编号（空行也编号），要求 `evidence_lines` 使用这些行号；`verdict=vulnerable` 时至少 1 行。
2. 检测 schema 改为 evidence-first：

```json
{
  "schema_version": "det-v2",
  "evidence_lines": [12, 13],
  "cwe_family": "memory_lifecycle",
  "cwe": "CWE-416",
  "is_vulnerable": true,
  "confidence": 0.0,
  "rationale": "第 12 行 free(p)，第 13 行继续使用 p->field；缺少置空或所有权转移。"
}
```

   prompt 明确要求“先列出证据行和缺陷类型，再给 verdict”；JSON 键顺序也按 evidence → cwe → verdict 排列，减少“先下结论再找理由”。
3. CWE 约束分三个设置，**不要混在一起**：
   - **部署设置**：模型自己预测 `cwe_family`/`cwe`，不提供 ground truth。
   - **Oracle 设置**：提供数据集的 `cwe_list`（只用于测量上限，明确标注 oracle，不是公平策略）。
   - **工具设置**：提供 Semgrep/CodeQL 的 CWE 标签（见 P4），作为真实可用的弱监督。
4. CWE 家族用粗粒度枚举（buffer、memory_lifecycle、integer、input_validation、access_control、info_exposure、resource、concurrency、other），避免强迫模型在 `CWE-125CWE-787` 这种拼接标签里选一个。

**可检验假设**

- 如果低召回主要因为“没有缺陷类型先验”，evidence-first + CWE checklist 应提高 CWE-416/20/264 的召回，同时证据行命中 `changed_lines` 的比例应高于随机。
- 如果模型只是把 evidence_lines 当装饰，定位命中率不会提高，召回也不会变；这种情况下不应继续加字段，而应转向工具反馈（P4）。

**成本**

- 检测输出增加约 50–100 token/条（证据行 + CWE + 更长 rationale）；520 条检测/策略约增加 26k–52k 输出 token，按当前价格约 $0.03–$0.06/策略。输入侧行号增加约 5%–10%，约 $0.01–$0.02/策略。**规划估算。**
- 这些成本远小于修复；即使检测成本翻倍，总成本仍由修复主导。

**建议验收线**

- 目标 CWE 家族（CWE-416/20/264/399）召回 +10 个百分点；整体召回 +5 个百分点，FP 不增加超过 5 个百分点。
- `evidence_lines` 命中 `changed_lines` 的 hit@1 ≥ 30%、hit@3 ≥ 50%（按“至少命中一个变更行”计）；如果 changed_lines 不在函数内，单独报告不可定位样本。
- CWE 家族 macro-F1 ≥ 0.35（当前没有 CWE 输出，无法比较；这是一个新指标，不能和旧结果直接比）。

**风险**

- CWE 标签噪声/多标签/`NVD-CWE-noinfo`；不要用单标签准确率作为主指标，用家族 macro-recall 和 coverage。
- `changed_lines` 是参考 diff 的行号，不一定落在函数体内；定位评分要区分“函数内可定位”和“不可定位”。
- 行号偏移、代码块格式、注释中的行号都可能引入 schema 错误；需要 dry-run 校验。
- 提供 ground-truth CWE 是 oracle，不能写成“模型能力提升”。

### P3：反事实差异提示与检测—修复一致性

**对应证据**

- 检测和修复是两次独立调用，输出可以互相矛盾：检测 FN 中 35.6%–64.3% 的修复仍实质改代码；检测 TP 中 2.6%–30.8% 的修复没有实质改动。
- 修复 prompt 预设“输入有漏洞”，但 22.1%–44.5% 的修复无实质改动；模型在“修”和“这已经安全”之间摇摆。
- pair 两侧高度相似（中位 0.926），差异通常只有几行；直接给 diff 比让模型自己找更可靠。

**改动**

1. **反事实检测（单函数）**：要求模型先写“最小反事实”——“如果要把这个函数变安全，最少要改哪一行/加什么检查？”；如果写不出，再判 safe。输出：

```json
{
  "counterfactual": {
    "change": "在 memcpy 前检查 len <= sizeof(dst)",
    "line": 12
  },
  "is_vulnerable": true,
  "confidence": 0.0,
  "evidence_lines": [12],
  "rationale": "..."
}
```

2. **差异检测（pair）**：给 A/B + unified diff，要求指出“哪一段变更消除了缺陷”，输出 `changed_lines`；如果 diff 中没有一行能解释缺陷消除，判 both_clean 或 both_flagged。
3. **一致性约束（检测+修复联合）**：
   - verdict=safe ⇒ patch 必须与输入一致（或明确返回 `no_change_reason`）。
   - verdict=vulnerable ⇒ patch 必须至少改一行，并且 `change_lines` 与 `evidence_lines` 有交集。
   - 在评分时增加 `detection_repair_consistency` 指标；不一致的样本单独报告，不静默算对。
4. 可选：一次调用同时输出 verdict 和 minimal patch（联合任务），减少两次调用之间的上下文丢失；但输出更长，需要单独评估 schema 失败率。

**可检验假设**

- 如果模型“其实知道怎么修但不敢报”，反事实提示应把部分 FN 转成 TP，并提高检测—修复一致性。
- 如果模型只是“更敢报”，FP 会上升；因此验收线必须同时看 recall 和 FP。
- 如果反事实提示让模型编造不存在的缺陷，evidence_lines 会落在无关行；定位命中率会暴露这一点。

**成本**

- 单函数反事实：输出增加约 50–150 token/条；520 条检测/策略约 +$0.03–$0.09。
- 差异检测：P1b 的 diff 块增加约 100–300 token/对；180 对约 +$0.02–$0.05。
- 联合检测+修复：一次调用替代两次，输入/输出结构变化较大；需要单独跑 dev 估算。

**建议验收线**

- 检测—修复不一致率 ≤ 10%（当前按“TP 中 no-change + FN 中 changed”粗算，远高于 10%）。
- 反事实提示的整体召回 +5 个百分点，FP 不增加超过 5 个百分点。
- pair 差异提示的 DA ≥ P1a；如果 P1b 只在 diff 明显时有效，按 diff 大小分层报告。

**风险**

- 反事实可能把“安全但可改进”的代码误判为漏洞；需要“最小性”约束和人工抽查。
- 模型可能学会“只要改一行就能过”的捷径，产生无意义但能改变文本的补丁；必须配合 P5 的自检/编译。
- 一致性约束会增加 schema 复杂度，可能提高无效输出率；先在 dev 上调 schema。

### P4：静态/动态工具反馈

**对应证据**

- 当前没有任何工具反馈；protocol 的 Clang 试点 0/20 通过（函数是片段，缺头文件/宏/类型）。
- context 只是标识符列表（中位 76.5 字符），不能表达生命周期/数据流。
- 低召回集中在 CWE-416/20/264/399，这些恰好是“需要跨语句/跨函数推理”的类型。
- 修复盲评 81/81 未编译；没有运行时证据。

**改动（分三层，按可行性排序）**

1. **T1 轻量静态事实（不需要完整构建）**
   - Semgrep/CodeQL/tree-sitter 规则：危险 API 调用（`memcpy`、`strcpy`、`sprintf`、`realloc`、`free`、`dlopen` 等）、缺失的边界检查、可疑的所有权转移、`goto err` 路径。
   - 输出结构化 `<TOOL_FINDINGS>`：`rule_id`、`line`、`message`、`severity`、`confidence`。
   - Prompt 要求模型逐条确认/反驳工具发现，并引用证据行；不要把工具输出当 ground truth。
2. **T2 项目级编译（中等成本）**
   - 按 `project_url` + `commit_id` 检出项目，使用 `compile_commands.json`（CMake/Make/Ninja）跑 `clang -fsyntax-only`；只对能构建的子集报告。
   - 三值状态：`PASS` / `FAIL` / `UNVERIFIED`；函数片段无法单独编译时标 `UNVERIFIED`，不要假装 PASS。
3. **T3 动态验证（高成本，子集）**
   - 对 20–30 个高风险函数，构造最小 harness 或复用项目测试，跑 ASan/UBSan；记录 `PASS`/`FAIL`/`NOT_RUN`。
   - 只报告“在该 harness 下未触发”，不能声称“漏洞已消除”。

**可检验假设**

- 如果工具能提供“第 12 行 free 后第 13 行使用”的事实，模型在 CWE-416 上的召回应上升；如果工具只给“危险 API 列表”，提升可能集中在 FP 而不是 TP。
- 工具 + 模型应优于单独工具和单独模型；如果模型只是复述工具，工具单独跑就够了，不值得加 LLM 成本。

**成本**

- T1：每条函数跑规则，计算成本低；prompt 增加 100–300 token/条，520 条检测约 +$0.05–$0.15/策略。
- T2：构建/编译是工程时间，不是 API 成本；只对可构建子集报告，覆盖率可能远低于 100%。
- T3：需要人工/CI 时间；只做 20–30 条，不作为全量结论。

**建议验收线**

- 工具覆盖率（能分析/能构建的函数比例）必须和指标一起报告；不能只报“覆盖子集上的提升”。
- 在覆盖子集上，模型+工具比模型单独召回 +10 个百分点，FP 不增加超过 5 个百分点。
- 工具本身的 precision/recall 单独报告；如果工具 precision < 0.5，模型+工具可能把噪声放大。

**风险**

- 工具误报会诱导模型过度报漏洞；需要“工具发现必须被代码证据确认”的约束。
- 项目构建失败/环境不一致；`UNVERIFIED` 不能算 PASS。
- 工具输出可能包含 CVE/CWE 标签或修复提示，造成泄漏；必须过滤 ground-truth 字段。
- 片段级函数无法直接跑项目级工具；T1 的规则要能处理不完整代码。

### P5：修复自检与编译闭环

**对应证据**

- 81/81 盲评候选 `compile_status=NOT_RUN`；没有编译、测试或 PoC。
- no-change/空白变化候选 VR=2 为 0/23；有实质改动 17/58。
- 93 条修复只因缺 `explanation` 被丢弃；91 条含完整函数，71 条有实质改动。
- no-change 补丁的参考相似度中位 0.899–0.923，文本相似度会误导。

**改动（按顺序）**

1. **宽松解析 + 补字段**：只要 `fixed_function` 可解析且结构完整，就接受为候选；`explanation` 缺失时单独 re-ask 一个短字段，而不是重生成整个补丁。
2. **静态自检**：
   - 签名/参数列表保持一致；
   - 括号/分隔符平衡；
   - 不是 diff/fragment/markdown；
   - verdict=vulnerable 时 `fixed_function` 必须与输入有实质差异（折叠空白后仍不同）；
   - `change_lines` 与 `evidence_lines` 至少有一个交集。
3. **模型自检（第二次调用）**：给 original + patch + 声称的缺陷行，要求回答：
   - patch 是否改变了缺陷行或增加了支配该行的检查？
   - 是否引入新的危险调用/未检查的返回值？
   - 签名和行为是否保持？
   - 返回 `accept` / `reject` / `revise` + 理由。
4. **编译闭环**：
   - 在项目容器里用 `compile_commands.json` 编译；三值 `PASS/FAIL/UNVERIFIED`；
   - 不能构建的函数片段，用 `clang -fsyntax-only` + 最小 stub，仍标 `UNVERIFIED`；
   - 只有 `PASS` 才能写“可编译”，不能把 `UNVERIFIED` 写成通过。
5. **测试/PoC（可选，子集）**：对 20–30 条生成针对性单元测试或 sanitizer harness；记录 `PASS/FAIL/NOT_RUN`。测试通过 ≠ 漏洞消除，只能写“在该测试下未触发”。

**可检验假设**

- 如果 no-change 主要是“模型觉得已经安全”，显式要求“必须改或说明为什么不能改”应降低 no-change；如果模型只是偷懒，自检/拒绝会把它转成 invalid 或 revise，而不是真正修复。
- 如果编译闭环能过滤掉语法错误/签名错误，VR 应上升；但编译通过不等于语义正确，提升幅度可能有限。

**成本**

- 补字段 re-ask：一次短请求（~50–100 输出 token），远低于完整修复（中位 510–561 token）；93 条无效修复的补救成本可大幅下降。
- 自检调用：+1 次/修复，输入 original+patch（~1–2k token），输出 ~200 token；308 条/策略约 +$0.3–$0.5。**规划估算。**
- 编译：工程时间/CI，不是 API 成本；只对可构建子集。

**建议验收线**

- 补字段 salvage 率 ≥ 80%（93 条中至少 75 条保留）；
- no-change/空白变化率 ≤ 5%（当前 18.8%–44.5%）；
- 在可构建子集上 `compile PASS` ≥ 50%；`UNVERIFIED` 单独报告；
- VR=2 从 21.0% 提升到 ≥ 30%，且 strict pass 同步提升；
- 每条“修复”必须带 `compile_status` 和 `self_check`，否则不算完成。

**风险**

- 编译环境可能无法复现（提交旧、依赖缺失）；不要把环境失败算成模型失败。
- 模型自检可能“自说自话”，与真实编译不一致；自检只能作为筛选，不是 oracle。
- 测试/PoC 可能覆盖不到真实攻击面；不能声称“漏洞已消除”。
- 自检调用增加成本；如果它只拒绝 no-change 而不提高 VR，性价比需要重新评估。

### P6：置信度校准与选择性预测

**对应证据**

- ECE 0.300–0.448，Brier 0.312–0.432，AUC 0.581–0.607；平均置信度比准确率高 0.285–0.442。
- 高置信（≥0.9）子集准确率 46.2%–54.5%；few-shot 49 条高置信里 23 条错。
- 风险—覆盖率：覆盖 25% 时准确率 0.60–0.65；覆盖 50% 时 0.45–0.71。
- 三策略一致性不提供有效信号（覆盖 91.3%，准确率 38.4%）。
- few-shot 示例把 confidence 固定为 0.95/0.9，模型模仿；这是提示伪影。

**改动**

1. **先报告，不先路由**：在新的实验里同时报告 reliability diagram、ECE、Brier、NLL、AUC、风险—覆盖率；不要只报平均 confidence。
2. **后验校准**：
   - 在 dev 集（40 条检测）上拟合 isotonic/Platt 或简单的分箱映射；用 leave-one-out / bootstrap 报告不确定性；
   - 不要用 test 拟合；不要把校准后的分数和旧结果混在一起；
   - 如果 dev 太小导致校准不稳定，明确写“校准不可靠”，不要硬做。
3. **证据型置信度**：如果自报 confidence 校准后仍然 AUC < 0.65，改用组合信号：
   - `evidence_lines` 是否非空且命中变更行；
   - CWE 是否与工具/上下文一致；
   - 自检/编译器是否确认；
   - k 次采样（temperature > 0）的一致性。
   用一个小的 logistic/线性模型在 dev 上组合，输出校准概率。
4. **选择性预测/弃权**：增加 `abstain` 或 `uncertain` 类别；在 dev 上选阈值，使覆盖率/风险满足目标，再在 test 上报告 coverage-risk。不要在没有校准的情况下用 raw confidence 做阈值。
5. **修掉 few-shot 的置信度模仿**：示例中的 confidence 不要固定为 0.95/0.9；可以省略 confidence，或使用多样化的、与证据强度匹配的值。否则 few-shot 的置信度分布不可比。

**可检验假设**

- 如果 confidence 只是风格标记，后验校准能把 ECE 降下来，但 AUC 不会显著提高；这种情况下校准只能改善“报告的概率”，不能改善排序。
- 如果证据型置信度（evidence + tool + self-consistency）能提高 AUC，选择性预测才可能达到高精度；否则应放弃“高置信自动通过”的设计。

**成本**

- 后验校准：dev-only，无额外 test 调用。
- 自一致性 k=3：检测调用 ×3，约 +$0.4/策略（按当前检测成本估算）；只建议在 dev 上验证有收益后再上 test。
- 证据型置信度：复用已有字段，无额外调用；如果需要工具，见 P4。

**建议验收线**

- ECE ≤ 0.10，Brier ≤ 0.20，AUC ≥ 0.70（目标；当前 0.58–0.61）。
- 覆盖 25% 时选择性准确率 ≥ 0.80；如果达不到，明确写“该模型/提示不适合高置信路由”。
- 校准前后的排序不变时，报告“校准只改变概率，不改变排序”，不要声称“置信度变可靠了”。

**风险**

- dev 只有 40 条，校准容易过拟合；必须用交叉验证/ bootstrap，并报告区间。
- 模型自报 confidence 是离散的（0.6/0.85/0.9），校准映射可能不稳定。
- 校准不解决召回；不要把“ECE 降低”当成“检测变好”。
- 自一致性 k=3 成本高，且 temp=0 下没有多样性；需要改解码参数，属于新的实验配置。

### P7：成本预算与路由

**对应证据**

- 总成本 $2.439；修复 65.1%；无效 + 无实质改动 = 28.5%。
- few-shot 贵 75.2%，M1−M2 macro-F1 = −0.0167（区间跨 0），DA −5，实质修复 −24。
- 每 DA 成本：$0.0187 / $0.0438 / $0.0183；每独立 TP：$0.0067 / $0.0105 / $0.0067。
- 修复单次 $0.00141–$0.00229，是检测的约 2.7–3.7 倍。

**改动**

1. **硬预算**：每个 run 设 `max_usd`；按 task/record 记账；报告“总成本、每正确检测、每正确 pair、每实质补丁、每编译通过补丁”。
2. **零成本 salvage**：先做 P5.1 的补字段/宽松解析；把 71 条可用补丁算回来，不重新生成。
3. **拒绝 no-change**：verdict=vulnerable 但 patch 无实质改动时，不把它算作修复；最多 re-ask 一次，仍无改动则记失败。这样 28.5% 的浪费中有一部分可以避免。
4. **配对联合**：P1 把 360 次检测降到 180 次；输入 token 约 2×/call，总 token 大致持平，请求数减半。
5. **级联路由**（在 P6 校准之后）：
   - 先跑 direct 检测（最便宜）；
   - 只在以下情况升级到工具/verifier/第二模型：direct 判 vulnerable；direct 与 context 不一致；函数短且属于高风险 CWE 家族；证据行缺失；
   - 不要用 raw confidence 做路由（当前 AUC 0.58–0.61）。
6. **few-shot 只在 dev 有明确收益时使用**：当前 few-shot 的成本/DA 最差；如果新任务（如 repair）上 dev 显示收益，再单独登记，不要默认全量跑。

**建议预算表（规划估算，不是实测）**

| 后续实验 | 估算调用数 | 估算成本 | 说明 |
| --- | ---: | ---: | --- |
| P1a/P1b pair-joint（180 对） | 180 检测 + 180 修复 | $0.35–$0.50/策略 | 单次输入约 2×，请求数减半 |
| P2 evidence/CWE（520 检测 + 308 修复） | 828 | $0.65–$0.75/策略 | 检测输出增加 50–100 token/条 |
| P3 反事实/一致性 | 520 检测 + 308 修复 | $0.65–$0.80/策略 | 输出更长；可与 P2 合并 |
| P5 verifier（308 修复） | +308 | +$0.30–$0.50/策略 | 只对候选补丁做二次检查 |
| P4 T1 工具（520 检测） | 520 + 规则计算 | +$0.05–$0.15/策略 + 计算 | 不含 T2/T3 构建时间 |
| 合计（单策略，不含工具构建） | ~1,300–1,800 | <$2.5 | 建议 `max_usd=5` |

**建议验收线**

- 每 DA 成本 ≤ direct（$0.0187）；如果新策略更准但更贵，报告 Pareto 点，不单独宣布赢家。
- 浪费（无效 + 无实质改动）≤ 10%（当前 28.5%）。
- 任何成本优化不得以显著降低召回为代价；同时报告 accuracy 和 cost。

**风险**

- 预算是线性外推，实际 token 受输出长度、重试、缓存命中影响；必须用真实 usage 重算。
- 级联路由需要可靠的置信度；P6 未完成前不要上线。
- 缓存命中会低估/高估成本；同时报告“缓存调整”和“全未命中”两种口径。

### P8：数据/标签审计（前置条件，不是模型改进）

**对应证据**

- 4 条漏洞 test-path 样本全部 FN；C-02 是 `tensorflow/core/ops/nn_ops_test.cc` 的 unit test，三种策略都以 0.95 置信度判安全，但标签为漏洞。
- NVD-CWE-noinfo 7 条，M1 召回 0/7；CWE 标签有 `CWE-125CWE-787` 这种拼接，存在数据质量噪声。
- CWE-416 19 条只召回 1 条，尽管 few-shot dev 里有一个 UAF 示例（`det-dev-11371`）；说明示例没有迁移，或者这些 UAF 的形态与示例差异大。
- FN 中位 35 行，短函数可能被 commit 级标签误标，也可能确实难。

**改动**

1. 从 FN 中分层抽 30–50 条（按 CWE 家族、函数长度、是否 test/generated path），人工核对：
   - `changed_lines` 是否落在该函数内；
   - 该函数是否真的是“可被维护者修复的安全漏洞”，还是 commit 级传播/测试改动；
   - 标签是否与 `cwe_list` 一致；
   - 是否存在同一函数的重复/近似重复。
2. 报告标签噪声率及 Wilson/ bootstrap 区间；做敏感性分析：排除 test path、排除 `NVD-CWE-noinfo`、排除无法定位的 changed_lines，重算召回。
3. 不静默改标签；如果发现错误，记录 `label_audit` 字段，旧结果保留，新增“清洗后”视图并明确标注。
4. 去重/污染检查：pair 相似度中位 0.926，检测集与配对集有 26 个项目重叠；报告项目/提交重叠，不要把跨任务结果当独立泛化证据。

**建议验收线**

- 完成 ≥30 条 FN 的人工审计，给出标签噪声率点估计和 95% 区间；
- 如果噪声率 >10%，所有召回结论都要加“上限受标签噪声限制”的说明，并同时报告清洗后召回；
- 审计记录可复现（样本 id、审计人、判断、理由），不覆盖旧标签。

**风险**

- 人工审计主观；需要双人/仲裁，报告一致性；
- 审计样本小，不能代表全体；
- 清洗后测试集如果被用于调参，会引入新的过拟合；清洗只用于敏感性分析，不用于提示选择。

### P9：解码/模型层面的补充（可选）

**对应证据**

- 所有主实验都是 `thinking=disabled`、`temperature=0`、单次运行；没有 thinking 敏感性结果。
- 低召回集中在需要多步推理的 CWE；短 rationale 可能不足以支撑跨语句分析。
- 置信度是模板化的，temperature=0 没有采样多样性。

**改动**

1. 在 40 条检测 + 40 对配对 + 10 条修复上做 thinking enabled / reasoning_effort=high 的敏感性分析；只报告排序和成本变化，不混入主表。
2. 在 dev 上试 temperature=0.3–0.7、k=3 自一致性；如果召回/校准有收益，再考虑 test。
3. 如果 MiMo 对比由并行任务负责，保持**同一 prompt、同一 schema、同一解码参数**；先跑“模型 × 原始提示”的 2×2，再跑“模型 × 改进提示”的 2×2，避免把模型差异和提示差异混在一起。

**成本/风险**

- thinking 可能显著增加输出 token 和延迟；只做子集敏感性，不做全量。
- 自一致性 k=3 成本 ×3；在低召回未解决前，优先级低于 P1/P2/P5。
- 换模型/解码参数会改变实验配置，必须单独登记，不能和现有三策略结果直接合并。

## 5. 建议的实验顺序与预算

### Phase 0：零 API 成本的整理（1–2 天）

1. 用本文的 salvage 逻辑重算 102 条无效修复：93 条可解析、91 条完整、71 条实质改动；产出一个**只读的** salvage 视图，不覆盖旧结果。
2. 用现有 results 生成置信度可靠性图、风险—覆盖率、成本分解；这些不需要新请求。
3. 抽 30–50 条 FN 做标签审计（P8）；先确认低召回里有多少是标签噪声。
4. 设计 P1/P2/P3 的 prompt 和 schema；在 20 对 / 40 条 dev 上做 dry-run，检查 JSON 有效率和 token 长度。

### Phase 1：dev 上的提示实验（2–3 天，≤$1）

- 固定 dev：40 条检测 + 20 对配对（协议已有 dev split）。
- 每个策略最多 3 次 prompt 迭代；记录 prompt hash；**不看 test**。
- 先跑 P1a/P1b、P2 evidence-first、P3 反事实；每个变体只跑 dev。
- 选择标准：dev 上 DA/召回/证据命中/无效率的综合，不只看一个指标；同时记录成本。
- 通过后冻结 prompt 版本（例如 `secvul-prompt-2026-11-13.1`），写 manifest。

### Phase 2：test 上的确认（3–5 天，≤$3）

- 每个变体用新的 run ID（`test_v2_*`），不覆盖 `test_v1_*`。
- 同一模型、同一解码参数、同一测试集；配对 bootstrap 按 project/pair 聚类；McNemar + Holm；报告 CI。
- 主表分开：单函数检测、pair 联合、修复质量、成本；不要把不同 schema 的结果混在一张表里。
- 负结果也报告；不要在看到 test 后改 prompt。

### Phase 3：工具/编译子集（1–2 周，工程成本为主）

- T1 静态规则先跑全量 160/180 对，报告覆盖率；
- T2 编译只对能构建的子集（预计 <50%），三值状态；
- T3 动态只做 20–30 条高风险样本；
- 所有工具结果单独报告，不覆盖主表。

### 预算原则

- 每个 run 设 `max_usd`；按 task 记账；同时报“缓存调整”和“全未命中”。
- 先做能复用现有产物的零成本分析（salvage、校准、成本），再做新请求。
- 不要为了“多一个策略”而全量重跑；先用 dev 筛掉明显无效的变体。
- 任何新结果都写新 run ID；旧 `test_v1_*` 保持冻结。

## 7. 限制与不声明

1. **单模型、单次运行**：只有 DeepSeek V4.1 Flash、一次 run；没有多 seed、多模型、多提示重复。所有差异都可能是噪声。
2. **没有编译/PoC**：81/81 盲评候选 `NOT_RUN`；本文的“修复”只到文本/结构层面，不能声称补丁可编译或漏洞已消除。
3. **盲评是 LLM 辅助**：30 个案例、81 个候选，评分者一致性在 MIN/COM 上很低（MIN κ=0.015，COM κ=0.000）；17/81 只是“在该 rubric 下被认为处理了根因”。
4. **标签可能噪声**：4/4 test-path 漏洞样本 FN，C-02 是 unit test；没有人工审计，不能断定标签错，但也不能把全部 FN 都归因于模型。
5. **context 伪影**：独立集 context 可用性与标签几乎共线；“context 非空 ⇒ 漏洞”平凡规则 98.8% 准确率。M3 总体指标不能解释为 context 推理能力。
6. **配对 benchmark 是构造任务**：pair 两侧来自同一 commit，相似度中位 0.926；DA 不是真实部署中的检测率。
7. **文本相似度不是正确率**：no-change 补丁的参考相似度中位 0.899–0.923；精确匹配也只有 1.7%–5.0%，都不是语义正确率。
8. **本文的改进数字是目标/估算**：所有“验收线”“预算估算”都不是实验结果；后续必须用新 run 验证。
9. **不声明**：不声明某个策略在所有 CWE/项目上更优；不声明 DeepSeek 是最佳模型；不声明 MiMo 更好或更差（并行任务负责）；不声明 context 对 LLM 无效；不声明修复补丁已通过测试。

## 8. 给主代理/并行任务的交接要点

1. **对用户的结论**：现有 DeepSeek 三策略的主要问题是**低召回 + 配对任务实现无效 + schema/无改动修复造成浪费**；不是“few-shot 略好”或“context 有用/无用”的简单排序。
2. **不要说的话**：
   - 不要说“context 策略无效”——当前 context 操纵太弱且与标签混杂，不能得出这个结论。
   - 不要说“修复正确率 21%”——盲评是 LLM 辅助、30 个案例、81 个候选，且 81/81 未编译；只能说“VR=2 17/81”。
   - 不要说“few-shot 更好”——macro-F1 区间重叠，DA 更低，成本高 75%。
   - 不要说“配对准确率 11.7% 说明模型不会配对”——模型根本没有看到 A/B 两侧。
3. **最高 ROI 的后续实验**：P1（pair A/B 联合）、P2（evidence + CWE）、P5（修复自检/编译）；P6 只作为路由前置，P4 先做子集可行性。
4. **MiMo 对比的隔离**：如果并行任务跑 MiMo，先用**原始 prompt**（`secvul-prompt-2026-11-11.1`）跑同一 828 请求/策略，得到“模型效应”；再用 P1/P2 的**同一改进 prompt**跑 DeepSeek 和 MiMo，得到“模型 × 提示”的 2×2。不要把 DeepSeek 的改进结果和 MiMo 的原始结果直接比。
5. **产物**：本文只新增 `research/improvement_opportunities.md`；旧 `test_v1_*`、`report/`、`analysis/`、`qualitative/` 均未修改。后续新 run 用 `test_v2_*`，不要覆盖旧结果。

# AI + 传统分析：LLM 漏洞检测与静态/动态工具结合的现状、评估陷阱与可检验假设

> **文档定位**：本文件是文献调研与实验设计，不包含新跑的实验结果。项目内数字全部引自已有产物 `report/results_summary.md`、`analysis/aggregation.md` 和 `research/evaluation_protocol.md`；文献数字逐条标注来源。写作日期 2026-11-12。
>
> **适用项目**：`cs224proj`，固定基座 DeepSeek V4.1 Flash，C/C++ 函数级漏洞检测 + 漏洞/修复配对判别 + 修复生成，测试集 160 条独立函数、180 对配对（360 条函数），已有三策略 2,484 次真实请求。
>
> **一句话结论**：混合检测的真实收益主要来自“把搜索空间变小、把判断变成可验证的证据”，而不是“让模型更聪明”。对本项目，信息量最大的新实验不是再换一版 prompt，而是**配对判别 + 安慰剂对照的工具反馈 + 覆盖率调整的动态证据**。

## 0. 结论摘要

| 判断 | 证据强度 | 关键依据 |
| --- | --- | --- |
| LLM + SAST 的可靠增益集中在**告警分流、规格推断、路径验证、模式合成**四类任务 | 强（多篇同行评审） | IRIS、LLM4SA、LLIFT、LLMDFA、LLMSAN、InferROI、MoCQ、KNighter |
| “LLM 直接读函数做二分类”是定义不良的任务，上下文缺失时人类也无法判定 | 强 | Risse et al. ISSTA 2025；PrimeVul；Vul-RAG |
| Agent 不是默认更好；接口设计、验证器和停止规则比“多轮”更重要 | 中—强 | SWE-agent、EnIGMA、Agentless、RepoAudit、SEC-bench |
| 动态证据对内存安全最直接，但覆盖率是硬约束；不报告覆盖率的动态增益不可解释 | 强（机制）+ 中（LLM 结合） | ASan/Valgrind、ARVO、Magma、CWE-401、Revelio（2026 预印本） |
| Juliet/SARD 的主要风险不是“太简单”一句带过，而是**标签泄漏、近似重复、工具共设计**三者叠加 | 强 | NIST IR 8561、Juliet 用户指南、ROMEO、Grahn & Zhang |
| 本项目当前最值得测的是“工具证据能否改善配对判别”，而不是“再给更多上下文” | 中（可检验假设） | 现有三策略：P 高、R 低、配对 DA 8.9–12.2%，低于机会水平 |

**尚未确立、不要写成结论的事项**：

- 没有一篇论文在**C/C++ 函数级配对数据**上同时比较 LLM-only、SAST-only、LLM+SAST、LLM+SAST+dynamic 的精度、覆盖率与美元成本；这是空白，也是课程项目的机会。
- 没有论文用**安慰剂工具输出**（同长度随机告警）控制“提示变长/格式变化”的混杂；多数混合实验把“工具证据”和“更多 token”混在一起。
- 没有论文系统量化 **Juliet 标签清洗对 LLM 的影响**；现有泄漏研究多针对传统 ML 模型。
- 没有证据表明混合增益可以跨模型迁移；多数工作报告的是 GPT-4 系列。
- 没有证据表明 agent 在多轮工具调用下一定优于**同预算的单轮工具条件化**；Agentless 反而给出了反例。

## 1. 范围、术语与证据分级

### 1.1 本文讨论的“AI”与“传统”

- **AI**：以 DeepSeek V4.1 Flash 为代表的自回归 LLM，通过提示完成判定、解释、路径生成、修复生成；不含微调和多模型集成。
- **传统静态分析（SAST）**：CodeQL、Semgrep、Infer、Clang Static Analyzer、Cppcheck、Joern/CPG。它们提供规则匹配、数据流/控制流、污点跟踪、路径条件。
- **传统动态分析**：AddressSanitizer（ASan）、LeakSanitizer（LSan）、Valgrind Memcheck、UBSan；以及 fuzzing/测试执行。它们提供运行时错误、泄漏报告、调用栈。
- **符号/神经符号**：把 LLM 的输出（规格、模式、路径、意图）交给符号引擎验证或执行；符号引擎的输出再反馈给 LLM。

### 1.2 评估单元

## 2. 为什么混合：误差互补的机制，而不是“1+1>2”

LLM、SAST、动态分析的错误模式并不相同。混合的价值在于**用一方的强约束去限制另一方的假设空间**，而不是简单投票。

| 失败模式 | LLM 单独 | SAST 单独 | 动态单独 | 混合对策 | 残余风险 |
| --- | --- | --- | --- | --- | --- |
| 无依据的“看起来可疑” | 高 | 低 | 低 | 要求引用工具证据/路径 | 工具本身无告警时仍靠猜 |
| 漏报（保守） | 本项目高 | 中—高（取决于规则） | 低但覆盖窄 | SAST 扩大候选，LLM 排序 | SAST 规则不覆盖的 CWE |
| 误报 | 中 | 高 | 低 | LLM 分流 + 动态否决 | 动态不可运行 |
| 跨函数/仓库上下文 | 受窗口限制 | 需要构建/规格 | 需要 harness | CPG/切片 + LLM | 构建失败、规格缺失 |
| 语义/意图（这个资源该不该释放） | 强 | 弱 | 弱 | LLM 推断意图，符号验证路径 | 意图推断错误 |
| 成本 | 中 | 低（部署后） | 高（工程/运行） | 级联：便宜的先跑 | 级联误差传播 |

**关键机制**：

1. **SAST 把“无限代码”变成“少量告警 + 路径”**，LLM 不必在整段代码上做无约束推理；这直接缓解上下文窗口和幻觉。
2. **LLM 把“缺失的规格”补出来**（哪些 API 是 source/sink、哪些资源需要释放、哪些前置条件使路径不可行），SAST 再用符号执行验证；这缓解 SAST 的规格瓶颈。
3. **动态分析把“语义判断”变成“可执行事实”**（ASan 报 use-after-free、LSan 报 leak），但只能覆盖可编译、可运行、输入能触达的单元；这缓解 LLM 的无依据判断，但引入覆盖率偏差。
4. **符号验证把“解释”变成“可检查的工件”**（路径、约束、模式），使评估可以从“答案对不对”扩展到“证据是否成立”。

> 因此，混合系统的评估不能只看 F1；必须同时报告**证据覆盖率**、**验证通过率**、**成本**和**弃权率**。否则“混合更好”可能只是“混合在更容易的样本上更好”。

## 3. 四条结合路线与代表工作

### 3.1 路线 A：LLM 作为 SAST 告警的分流器（triage）

**做法**：先跑 SAST，得到告警；用程序依赖图/切片抽取告警相关代码；让 LLM 判断“真 bug / 误报 / 不确定”。

**代表工作**：

- **LLM4SA**（Wen et al., TKDD 2024）[R5]：在 Juliet、3 个嵌入式 RTOS、11 个真实 C/C++ 项目上，用 Cppcheck/Csa/Infer 产生 **9,547 条告警**；LLM 分流后精确率 **81.13%**、召回率 **94.64%**，平均每条告警 **<30 秒**、**$0.31**。关键点：它不负责“发现”漏洞，只负责“删误报”；如果 SAST 没有告警，它无能为力。
- **LLIFT**（Li et al., OOPSLA 2024）[R6]：针对 Use-Before-Initialization（UBI），LLM 推断初始化器和后置约束，UBITect 做路径剪枝；报告 **50% 精确率、100% 召回率**，在 Linux 内核发现 **13 个此前未知的 UBI bug**。关键点：LLM 补的是“静态分析缺失的规格”，不是替代静态分析。

**对本项目的含义**：如果先跑 SAST，LLM 分流可以提高精确率，但**不会自动提高召回率**。本项目当前的问题恰恰是召回率低（0.30 左右）、配对任务大量“双报安全”；单纯做 triage 可能让召回率更低。要提升召回，必须让 SAST 产生更多候选，或让 LLM 主动提出候选再验证。

### 3.2 路线 B：LLM 作为 SAST 的规格/模式生成器

**做法**：LLM 生成 source/sink 规格、污点规则、检查器模式、资源意图；符号引擎执行这些规格并返回结果；LLM 根据反例迭代修正。

**代表工作**：

- **IRIS**（Li, Dutta, Naik, ICLR 2025）[R4]：LLM 推断第三方 API 的 taint 规格，CodeQL 做全仓库污点分析。在 **CWE-Bench-Java 120 个真实 Java 漏洞**上，CodeQL 单独检出 **27** 个，IRIS+GPT-4 检出 **55** 个（+28），平均误报率改善 **5 个百分点**。关键点：瓶颈是“规格”而不是“引擎”；LLM 的语义知识用在符号分析看不见的地方。
- **MoCQ**（Li et al., arXiv 2025）[R10]：LLM 生成漏洞模式的 DSL，再用 trace-driven symbolic validation 迭代修正；覆盖 **12 类漏洞、4 种语言**，生成 **46 个专家遗漏的新模式**，发现 **25 个此前未知漏洞**。关键点：LLM 的产物是“可执行模式”，不是“一次性判定”。
- **KNighter**（Yang et al., SOSP 2025）[R11]：从历史修复补丁中让 LLM 合成静态检查器；在 Linux 内核发现 **92 个新的、长期潜伏的关键 bug**。关键点：从“修复”学习，而不是从“标签”学习；检查器可复用、可审计。
- **InferROI**（Wang et al., ICSE 2025）[R9]：LLM 推断资源获取/释放/可达性意图，静态两阶段路径分析做泄漏检测；DroidLeaks **59.3%**、JLeaks **62.5%** 检出率，误报率 **18.6%/19.5%**；发现 **29 个未知资源泄漏**，7 个被开发者确认。关键点：与 CWE-401 最接近，但对象是 Java/Android，不是 C。

**对本项目的含义**：对 C/C++ 内存泄漏，最有希望的路线是“LLM 推断资源所有权/释放意图，静态或动态验证路径”，而不是“LLM 直接看函数说有没有泄漏”。这条路线也最适合形成课程项目的创新点：把“意图”作为可检验的中间产物。

### 3.3 路线 C：LLM 作为数据流/路径推理器

**做法**：把数据流分析拆成子任务（source/sink 识别、传播、路径可行性），LLM 生成代码或路径，外部工具（解析库、定理证明器、静态分析器）验证。

**代表工作**：

- **LLMDFA**（Wang et al., NeurIPS 2024）[R7]：编译无关的数据流分析；LLM 合成代码调用解析库和定理证明器；平均 **87.10% 精确率、80.77% 召回率**，F1 最多提升 **0.35**。关键点：不是“LLM 直接推理”，而是“LLM 写代码调用工具”。
- **LLMSAN**（Wang et al., Findings EMNLP 2024）[R8]：强制 LLM 在 few-shot CoT 中输出数据流路径，再用 program-property decomposition 验证；合成基准 **91.03% 精确率、74.00% 召回率**，sanitization 提升 **21.99 个百分点**精确率；真实 Android 恶意应用上比工业分析器精确率高 **15.36 个百分点**、召回率高 **3.61 个百分点**。关键点：路径既是解释，也是可验证工件。
- **Interleaving Static Analysis and LLM Prompting**（Chapman et al., SOAP 2024）[R13]：静态分析器与 LLM 交替调用，LLM 的输出用于后续分析；在 MbedTLS、zlib 等 C 系统代码上，EESI 的平均召回率从 **52.55% 提升到 77.83%**，F1 从 **0.612 提升到 0.804**，精确率从 **86.67% 微降到 85.12%**。关键点：LLM 补静态分析的“漏”，静态分析约束 LLM 的“飘”。

**对本项目的含义**：配对任务要求“看出漏洞版本与修复版本的差异”。让模型输出 source→sink 路径，再用符号工具验证，比让它输出一个二值标签更可能捕捉到“差异”。这就是 H4 的直接依据。

### 3.4 路线 D：LLM 作为 agent 调用工具

**做法**：ReAct/工具调用循环：读代码、查调用者、跑 SAST、跑测试、看 sanitizer、修正假设；直到停止条件。

**代表工作**：

- **RepoAudit**（Wang et al., arXiv 2025）[R14]：agent 有记忆，沿可行路径分析函数内数据流事实，validator 验证数据流事实和路径条件；15 个真实项目发现 **40 个真 bug**，精确率 **78.43%**，平均 **0.44 小时/$2.54 每项目**；另有 **185 个新 bug**，174 个已确认/修复。关键点：真正起作用的是 validator 和数据流事实，不是“agent”这个标签。
- **EnIGMA**（Abramovich et al., arXiv 2024/2025）[R15]：给 LM agent 提供交互式终端工具（调试器、服务器连接），在 **390 个 CTF 挑战、4 个基准**上显著提升，NYU CTF/InterCode-CTF/CyBench 达到 SOTA；同时发现 **soliloquizing**：模型会自生成“工具观察”，实际上没有调用工具。关键点：工具接口设计很重要，但 agent 会伪造观察。
- **SWE-agent**（Yang et al., NeurIPS 2024）[R16]：agent-computer interface（ACI）设计让 SWE-bench 解决率 **12.29%**，比仅用默认 Linux shell 的基线多 **10.7 个百分点**。关键点：观察的截断、lint 守卫、编辑格式，都会显著影响结果。
- **Agentless**（Xia et al., arXiv 2024）[R18]：简单的“定位—修复—验证”三阶段，在 SWE-bench Lite 上 **32.00%（96 个正确修复）**、**$0.70**，优于当时所有开源 agent。关键点：复杂度不是免费的；简单流程 + 验证可能更好。
- **SEC-bench**（Lee et al., arXiv 2025）[R19]：自动化构造真实仓库、复现漏洞、生成 gold patch，**$0.87/实例**；最强 agent 的 PoC 生成 **≤18.0%**、漏洞修补 **≤34.0%**。关键点：端到端安全任务仍然很难。
- **CyberGym**（Wang et al., arXiv 2025）[R20]：**1,507 个真实漏洞、188 个项目**；给描述和代码库，让 agent 生成 PoC；最强组合约 **20%** 成功率；发现 **34 个零日**、**18 个历史上不完整的补丁**。关键点：真实、可执行、大规模的 agent 评估成本很高。

**对本项目的含义**：agent 路线对课程项目是高风险/高成本选项。若要做，必须：(a) 限制轮数（3 轮以内）；(b) 记录每次工具调用与原始输出；(c) 加安慰剂对照；(d) 用确定性验证器做最终判定。否则很容易把“多花了 token”误判为“工具反馈有效”。

## 4. Agentic analysis：能力、失败模式与设计约束

### 4.1 能力从哪来

- **ReAct** [R33]：推理轨迹与动作交替，动作从环境获取新信息；比纯 CoT 更能在交互任务中纠错。
- **Reflexion** [R34]：用语言化的自我反思作为“强化信号”，在失败后重试。
- **Self-Refine** [R35]：同一模型生成—批评—修订；在无外部反馈时，收益有限。
- **CRITIC** [R36]：引入外部工具（搜索、代码执行、计算器）做验证，模型根据工具反馈修正；这是“工具输出反馈”的经典证据。
- **Huang et al.** [R37]：**没有外部反馈时，LLM 的内在自我纠错不能可靠提升推理，甚至会变差**。这条负面结果非常重要：它把“多轮反思”与“工具验证”区分开。
- **LLM agent 在软件工程中的系统综述** [R45]：覆盖代码生成、修复、测试、静态检查等；本文只取与工具反馈/验证相关的部分。

### 4.2 失败模式

| 失败模式 | 表现 | 如何检测 | 缓解 |
| --- | --- | --- | --- |
| Soliloquizing | 模型声称“我运行了工具/看到了输出”，但日志里没有调用 | 对比工具调用日志与模型陈述 | 强制每次结论引用原始工具输出；无调用则判无效 |
| 工具输出误读 | 把 SARIF 字段、栈帧、错误码读错 | 程序化解析 + 人工抽检 | 不让模型自由文本解析；结构化字段 |
| 锚定 | 第一个告警/第一个假设主导后续 | 统计“首假设正确率”和“改判率” | 要求提出至少一个替代假设 |
| 误差传播 | 早期错误结论一路保留 | 检查中间结论与最终结论的一致性 | checkpoint/replan；独立验证器 |
| 上下文溢出 | 观察被截断，关键证据丢失 | 记录 token/截断位置 | 结构化摘要；按需读取 |
| 成本膨胀 | 轮数增加，准确率不增 | 边际准确率/边际美元 | 3 轮上限；停止规则 |
| 提示注入 | 代码注释/工具消息含指令 | 注入测试集；检查是否执行了非预期动作 | 引用/转义；系统提示隔离 |
| 非确定性 | 温度 0 仍可能不同 | 重复运行，报告一致率 | 固定 seed/版本；重复抽样 |

### 4.3 对本项目的设计约束

如果要做 agent 实验，建议把范围压到最小：

1. **最多 3 轮**：第 1 轮读函数与 SAST 告警；第 2 轮请求调用者/被调用者或具体切片；第 3 轮给出判定与证据。第 4 轮以后边际收益通常很小，但成本线性上升（这是 H7 的探索性问题）。
2. **工具集固定**：只给 `read_function`、`get_callers`、`run_semgrep`/`run_codeql`（二选一）、`compile_and_run_asan`（仅动态子集）。不要给开放式 shell。
3. **结论必须引用证据**：输出 schema 增加 `evidence` 字段，包含工具名、文件、行号、原始消息摘要；无证据的“vulnerable”判为无效。
4. **确定性验证器做最终判定**：静态告警/动态报告由程序解析，不让模型自由心证。
5. **安慰剂对照**：同长度、同格式的随机告警；如果 agent 仍然提升，说明提升来自提示长度/格式，而不是证据。

> 这一节的核心不是“agent 能不能用”，而是“怎样证明 agent 的增益来自工具，而不是来自更多 token”。没有安慰剂对照，混合实验的内部效度很弱。

## 5. 工具输出反馈：什么算证据，如何测量

### 5.1 五类反馈信号

| 信号 | 精度 | 覆盖率 | 语义含量 | 适用任务 | 主要失败模式 |
| --- | --- | --- | --- | --- | --- |
| 编译错误 | 高 | 仅可编译单元 | 低（语法/类型） | 修复、PoC | 与漏洞无关；环境差异 |
| SAST 告警 | 中 | 高（无需运行） | 中（规则/路径） | 检测、分流、定位 | 误报；规则不覆盖 |
| Sanitizer 报告 | 高 | 低（需运行+输入） | 高（运行时事实） | 内存安全确认 | 覆盖不到；输入不触发 |
| 测试失败 | 高 | 低 | 中（行为） | 修复、PoC | 测试缺失/不稳定 |
| 参考 diff | 高 | 仅配对数据 | 高（修复位置） | 配对判别、修复评估 | 测试时不可用（泄漏） |

**关键区分**：SAST 告警是“假设”，sanitizer 报告是“事实”，编译错误是“约束”。三者不能混为“工具反馈”一个变量；实验必须分开操纵。

### 5.2 证据怎么说

- **CRITIC** [R36] 表明：模型用外部工具验证自己的输出，可以纠正错误；**没有工具时，自我批评容易变成自我确认**。
- **Huang et al.** [R37] 表明：不让模型接触外部反馈、只让它“再想想”，推理准确率不会可靠提升，甚至下降。这为“工具输出必须外部、可验证”提供了负面证据。
- **SWE-agent** [R16] 表明：即使工具相同，**观察的呈现方式**（截断、lint 守卫、编辑格式）也会造成 10.7 个百分点的差异。也就是说，“有工具”不等于“工具反馈被正确使用”。
- **EnIGMA** [R15] 表明：交互式工具（调试器）能显著提升 CTF 表现，但模型会出现 **soliloquizing**，即伪造工具观察。工具反馈的真实性必须被审计。

### 5.3 测量：不要只报最终 F1

| 指标 | 定义 | 为什么重要 |
| --- | --- | --- |
| Tool-call success rate | 工具调用成功且返回可解析结果的次数 / 总调用次数 | 区分“工具坏了”与“模型不会用” |
| Evidence grounding rate | 最终结论中引用的证据能在工具日志中找到的比例 | 检测 soliloquizing / 伪造引用 |
| Validated path rate | LLM 声称的 source→sink 路径被符号工具确认的比例 | 检测路径幻觉 |
| Marginal accuracy per call | Δ正确数 / Δ工具调用数 | 判断多轮是否值得 |
| Cost per correct decision | 总 USD /（正确阳性 + 正确阴性） | 跨条件可比 |
| Time to verdict | 从输入到最终判定的 wall-clock | 课程项目/实际使用约束 |
| Abstention rate | 输出“不确定”的比例 | selective prediction 的必要信息 |

### 5.4 安慰剂对照：混合实验最容易被忽略的内部效度

假设 C1 = LLM + 真实 SAST 告警，C0 = LLM。C1 比 C0 好，可能有三种原因：

1. **证据效应**：告警确实提供了漏洞位置/路径信息。
2. **长度/格式效应**：C1 的 prompt 更长、结构化字段更多，模型更“认真”。
3. **选择效应**：只有部分单元有告警，C1 在这些单元上更容易。

**安慰剂设计**：

- **C1-placebo**：同数量、同格式、同 token 长度的**随机告警**（从其他单元抽取，或随机生成 rule id/行号）。
- **C1-shuffled**：真实告警但**打乱单元对应关系**（把 A 的告警给 B）。
- **C1-empty**：同格式的“无告警”卡片，控制格式但不提供信息。

判断：

- 若 C1 > C0，但 C1 ≈ C1-placebo → 增益主要来自长度/格式，不是证据。
- 若 C1 > C1-placebo，且 C1 > C1-shuffled → 证据与单元的对应关系重要，支持“证据效应”。
- 若 C1 只在“有告警”的子集上提升，而在“无告警”子集不提升 → 需要报告覆盖率，不能外推到全集。

> 这是本文件建议的最重要方法学创新：**把“工具证据”与“更多 token”分离**。现有混合论文很少这样做。

### 5.5 反馈回路的四种形态

| 形态 | 描述 | 成本 | 适用 | 代表 |
| --- | --- | --- | --- | --- |
| One-shot conditioning | 工具结果一次性放进 prompt | 低 | 告警分流、证据条件化 | LLM4SA、C1 |
| Cascade | 便宜工具先筛，贵的工具/LLM 后判 | 中 | 大规模告警 | 工业 SAST + LLM |
| Iterative | 模型请求工具、看结果、再请求 | 高 | 仓库级、路径验证 | RepoAudit、EnIGMA |
| Debate/ensemble | 多个角色/模型互相批评 | 高 | 高风险判定 | 多 agent（本项目不建议） |

对课程项目，**One-shot conditioning + 安慰剂**的性价比最高；Iterative 只在 H2 中作为小规模验证。

### 5.6 反馈的风险

- **反馈投毒**：代码注释、告警 message、测试输出都可能含对抗性文本；工具输出进 prompt 前要转义/引用，不能当指令。
- **过度信任**：模型把 SAST 告警当 ground truth，忽略告警本身的误报；需要求模型给出“反证”或“为何不采信”。
- **反馈过时**：工具版本/规则变化导致同一单元结果不同；必须 pin 版本并记录 SARIF。
- **反馈偏差**：只给“有告警”的单元，等于把“工具覆盖”当成“模型能力”；必须报告 coverage。

## 6. 神经符号/混合检测的设计空间

### 6.1 四个设计轴

| 轴 | 选项 | 说明 | 代表工作 |
| --- | --- | --- | --- |
| 神经侧角色 | 规格推断 / 模式合成 / 路径提议 / 分流 / 排序 | LLM 到底生产什么 | IRIS、MoCQ、LLMDFA、LLM4SA、RepoAudit |
| 符号侧角色 | 验证 / 执行 / 枚举 / 剪枝 | 传统工具到底做什么 | LLMSAN、KNighter、InferROI、LLIFT |
| 耦合方式 | 一次性 / 交替 / 迭代 | 反馈是否回流 | LLM4SA、Interleaving、RepoAudit |
| 粒度 | 函数 / 文件 / 仓库 | 上下文范围 | LLM4SA、IRIS、RepoAudit |

### 6.2 四种可复用的设计模式

**模式 1：神经提议 + 符号否决（neural proposal, symbolic veto）**

- LLM 提出“这里可能泄漏/可能污点传播”，符号工具检查路径可达性、资源释放、锁状态。
- 若符号工具不能确认，系统弃权或降级，而不是直接判正。
- 证据：LLMSAN（路径验证提升 21.99pp 精确率）[R8]、IRIS（规格 + CodeQL）[R4]。
- 适合本项目：H4。

**模式 2：神经规格 + 符号执行（neural spec, symbolic execution）**

- LLM 生成 source/sink、资源 API、前置条件；符号引擎执行全量分析。
- 证据：IRIS [R4]、InferROI [R9]、LLIFT [R6]。
- 适合本项目：如果要做 CWE-401，让 LLM 推断“这个资源是否应在所有路径释放”，再用静态/动态验证。

**模式 3：神经模式 + 符号验证（neural pattern, symbolic validation）**

- LLM 生成检查器/DSL/查询；符号引擎跑模式；反例回流修正。
- 证据：MoCQ [R10]、KNighter [R11]。
- 适合本项目：把“检测规则”作为产物，而不是一次性答案；可复用、可审计，但工程量大。

**模式 4：神经分流 + 符号枚举（neural triage, symbolic enumeration）**

- 符号工具枚举大量告警；LLM 分流/排序；人只看高优先级。
- 证据：LLM4SA [R5]。
- 适合本项目：低成本、最容易复现；但不解决召回。

### 6.3 设计原则

1. **符号侧必须能说“不”**：如果符号工具只能确认、不能否决，LLM 的幻觉不会被过滤。
2. **神经侧的产物要可检查**：路径、模式、规格、查询，比自然语言解释更容易验证。
3. **反馈要可追溯**：每条结论对应一条工具日志；否则无法区分证据与编造。
4. **弃权是一等公民**：当证据不足时，输出“不确定”比强行二分类更诚实；评估要报告 coverage-risk。
5. **成本要前置**：符号工具的运行成本、LLM 的 token 成本、人工 harness 成本要分开记。

### 6.4 风险

- **循环验证**：LLM 生成规格，LLM 又判断规格是否正确；符号工具只是执行了错误规格。需要独立的人工标注子集或动态事实验证。
- **工具不可靠**：静态分析器有误报/漏报；动态工具有覆盖盲区。把工具当 oracle 会引入新的偏差。
- **规格漂移**：LLM 生成的规格可能过拟合当前样本；换项目/CWE 就失效。
- **基准过拟合**：在 Juliet 上调好的模式，在真实项目上可能不成立；需要 H6 的迁移检验。

### 6.5 空白

- C/C++ **函数级**、**内存安全**、**配对数据**上的神经符号研究很少；现有工作多是 Java/Android、仓库级、或非安全任务。
- **动态证据 + LLM** 的结合多集中在 fuzzing/agent（EnIGMA、Revelio），而不是“函数级检测 + 覆盖率报告”。
- **成本-精度 Pareto** 几乎没有系统报告；多数论文只报 accuracy/F1。

## 7. Juliet/SARD 评估陷阱

### 7.1 事实基础

- **SARD** 是 NIST SAMATE 维护的参考数据集，**超过 450,000 个程序、150+ CWE 类**，包含合成程序、生产程序、注入漏洞的生产程序 [R27][R28]。
- **Juliet** 是 NSA CAS 为**评估静态分析工具**而生成的合成套件；Juliet 1.2 包含 **61,387 个 C/C++ 程序、25,477 个 Java 程序**；Juliet 1.3 的 C/C++ 套件覆盖 **118 个 CWE** [R28][R29][R30]。
- Juliet 的每个用例通常包含 **bad 函数**与 **good 函数**，以及 helper/source/sink 函数；bad 与 good 往往只差很小的编辑 [R29]。
- Juliet 的设计目标是**测试静态分析工具**，不是模拟真实项目的漏洞分布 [R29][R30]。

### 7.2 陷阱一：标签泄漏（label leakage）

Juliet 的命名和注释直接编码了答案：

- 函数名：`CWE401_Memory_Leak__..._bad`、`..._good`、`BadSource`、`BadSink`、`goodG2B`、`goodB2G`、`helperBad`、`helperGood` [R29]。
- 文件名：`..._bad.cpp`、`..._good1.cpp` [R29]。
- 注释：`/* POTENTIAL FLAW: ... */` 标记缺陷位置，`/* FIX: ... */` 标记修复 [R29]；这些注释在真实代码中很少以这种形式出现。
- 路径/文件名含 CWE 编号：`CWE401_Memory_Leak__...`，模型即使不看代码，也能从 CWE 编号猜到弱点类别。

**证据**：

- NIST IR 8561 在讨论“用 Juliet 训练 ML”时，转述 Nascimento 的两点限制：**函数名与重要代码属性高度相关，模型可能依赖名字分类，而不是学习漏洞**；**Juliet 用例在结构上高度相似，数据类型/条件的变化可能只是“多样性的幻觉”** [R28]。
- ROMEO 在构造二进制数据集时，明确**删除 primary good function 以避免标签泄漏**，并验证编译过程没有额外泄漏标签 [R31]。
- Juliet 用户指南本身说明：测试用例包含 bad/good 函数，命名规则用于自动评估 [R29]。

**诊断**：把函数名、文件名、CWE 编号、注释全部替换/删除（例如函数改名为 `f1`、`f2`，路径改为 `case_001.c`，删除 `POTENTIAL FLAW`/`FIX` 注释），再跑同一模型；如果 F1 大幅下降，说明原设置存在泄漏。

### 7.3 陷阱二：近似重复与随机划分泄漏

Juliet 的“flow variant”用同一模板生成大量变体（01–22 控制流、31–34 数据流、41–45 跨函数、51–54 多文件、61–64 跨文件、81–84 虚函数/构造析构等）[R29]。这些变体在 AST/语义上高度相似，随机划分会把“近重复”放进训练和测试。

**证据**：

- NIST IR 8561 直接引用“**effectively duplicate instances**”：所有 Juliet 用例结构上惊人地相似，数据类型和条件的变化可能只是幻觉 [R28]。
- Grahn & Zhang 分析 C/C++ 数据集时指出：Juliet 的增强/变体导致随机划分（即使按 CWE 分层）也会把近重复放入训练和测试，造成数据泄漏 [R32]。
- ROMEO 也按“primary/secondary good/bad”规则筛选，避免把 helper/无关函数混入标签 [R31]。

**诊断**：按“测试用例基名/functional variant/CWE”做 group split，而不是按函数随机 split；用 AST 归一化/相似度去重；比较 random split 与 group split 的分数差。

### 7.4 陷阱三：合成简单性与分布偏移

Juliet 用户指南明确写道：

- “Test cases are simpler than natural code... This simplicity may inflate results in that tools may report flaws in the test cases that they would rarely report in natural, non-trivial [code].” [R29]
- “Frequencies of flaws and non-flawed constructs in the test cases may not reflect their frequencies in natural code.” [R29]

NIST IR 8561 更直接：Juliet “the code is far from what is usually written and used” [R28]。

**含义**：在 Juliet 上 90%+ 的 F1 不能外推到真实项目；它只能说明“在该合成分布上有效”。如果课程报告只报 Juliet，审稿人/老师有理由质疑外部效度。

### 7.5 陷阱四：静态工具共设计、bad-only、无关缺陷

- **共设计偏差**：Juliet 是为静态分析工具设计的；工具厂商可能针对 Juliet 调过规则。用它比较“工具 A vs 工具 B”相对公平，但用它证明“工具在真实代码上有效”不公平 [R29][R30]。
- **bad-only 用例**：少数用例只有 bad 函数，没有 good 对照；用户指南明确说这些用例**应从误报分析中排除** [R29]。如果把它们算进 FP 分母，会低估误报率。
- **无关缺陷**：一个用例只针对一个 CWE，但可能**偶然包含其他缺陷**；工具报告了“非目标缺陷”，不应简单算作 FP。用户指南有专门的 “Unrelated Flaw Reports” 讨论 [R29]。
- **多文件/多函数**：primary bad/good、secondary good、helper、source/sink 的标签不同；把 helper 当负样本会污染评估。ROMEO 因此只保留 primary/secondary 规则内的函数 [R31]。

**诊断**：使用官方 manifest/SARIF 元数据，按 primary 函数和目标 CWE 过滤；单独报告 bad-only；对“无关缺陷”做人工/规则判定，而不是一律算 FP。

### 7.6 陷阱五：动态可运行性与“泄漏是否真的发生”

- Juliet 用例有 `main`，但需要 `INCLUDEMAIN` 宏；批量编译时用 `OMITBAD`/`OMITGOOD` 控制；部分用例是 Windows 专用（文件名含 `w32`）[R29]。
- 内存泄漏用例的 bad 路径可能只在特定输入/错误路径下触发；直接跑 `main` 不一定复现。
- 把多个用例编译成一个可执行文件，会改变堆状态、退出行为、泄漏检测结果；Valgrind 可能把块归类为“still reachable”而非“definitely lost”，LSan 则区分 direct/indirect leak。
- 动态工具的“无报告”不等于“无漏洞”，只等于“该输入/该路径没触发”。

**诊断**：逐用例构建 harness；记录编译成功/失败、运行超时、sanitizer 退出码；报告**动态覆盖率**；对“无报告”的单元不要直接当负样本，除非能证明路径被覆盖。

### 7.7 陷阱六：指标与统计

| 陷阱 | 表现 | 后果 | 修正 |
| --- | --- | --- | --- |
| 只报 accuracy | 类别不平衡时 80% 准确率可能等于“全判漏洞” | 高估能力 | 报 P/R/F1/MCC/balanced accuracy + majority baseline |
| 函数级 vs 行级 | 函数标签正确但定位错误 | 修复/审计不可用 | 单独报 localization Top-k |
| 告警不去重 | 同一缺陷多条告警 | 虚高 TP/FP | 按缺陷/行聚类后评估 |
| 多条件多重比较 | 6 个条件选最好 | 假阳性 | Holm/BH 校正；预注册 |
| 配对任务用单侧指标 | 只报 per-version F1 | 掩盖“双报安全/双报漏洞” | 报 joint DA、双报率、判反率 |
| 文本匹配当修复正确 | 与参考 diff 相似 | 误导 | 编译/测试/PoC 或明确标注“文本相似” |

### 7.8 陷阱七：污染与提示敏感性

- Juliet 是公开数据，LLM 预训练可能见过；模型可能记住函数名/模式。改名/改注释/改控制流可以部分检测，但不能完全排除。
- 提示格式（JSON vs 自然语言、标签顺序、是否给 CWE）会显著改变结果；同一模型在不同 prompt 下的差异可能大于方法差异。
- 温度 0 仍可能非确定性（API 后端、批处理、版本漂移）；单次运行不足以支持强结论。

**诊断**：至少做 name/comment/CWE 三种消融；固定 prompt 模板；重复 2–3 次，报告一致率；记录模型版本/日期。

**LLM 单独检测的证据也不乐观**：Khare et al. 在 16 个 LLM、5,000 个样本、25 类漏洞上平均准确率 **62.8%**、F1 **0.71**，且只在过程内漏洞上表现好 [R38]；Ullah et al. 发现 LLM 在需要跨过程推理时不可靠 [R39]；Vul-RAG 发现 LLM 区分漏洞与相似修复代码的准确率仅 **0.06–0.14** [R40]；LLM4Vuln 把知识、上下文、提示解耦后，发现“更多信息不一定更好” [R41]；Lin & Mohaisen 的系统比较也显示模型间差异大 [R42]。这进一步说明：**没有工具/上下文约束的 LLM 二分类，天花板不高**。

### 7.9 陷阱总表

| 陷阱 | 机制 | 诊断 | 缓解 | 偏差方向 |
| --- | --- | --- | --- | --- |
| 函数名/文件名泄漏 | `_bad`/`_good`/`BadSource` 直接编码标签 | 改名后 ΔF1 | 名称归一化；label-blind prompt | 高估 |
| 注释泄漏 | `POTENTIAL FLAW`/`FIX` 标记答案 | 删注释后 ΔF1 | 注释剥离 | 高估 |
| CWE 编号泄漏 | 路径/函数名含 CWE | 去 CWE 后 ΔF1 | 匿名化路径 | 高估 |
| 近似重复 | flow variant 同模板 | random vs group split | group split + 去重 | 高估 |
| 合成简单 | 一两页代码、无真实依赖 | Juliet vs 真实项目 | 双基准报告 | 高估 |
| 工具共设计 | 为 SAST 认证而设计 | 换未调优工具 | 预注册工具/规则 | 高估 SAST |
| bad-only | 无 good 对照 | 检查 manifest | 从 FP 分析排除 | 低估 FP |
| 无关缺陷 | 非目标 CWE 被报 | 人工判定 | 单独报告 | 高估 FP |
| 多函数标签 | helper 既非 good 也非 bad | 检查函数角色 | 只用 primary | 双向 |
| 动态不可运行 | 需要 harness/输入 | 编译/运行覆盖率 | 逐用例 harness；报告 coverage | 低估/高估 |
| 指标不平衡 | accuracy 主导 | 加 MCC/多数类基线 | 预注册指标 | 高估 |
| 污染 | 公开数据被预训练 | 改名/扰动 | 报告风险；不做强泛化声明 | 高估 |

### 7.10 使用 Juliet 的最低负责协议（8 步）

1. **只保留 primary bad/good 函数**；helper/source/sink 不进入主评估；bad-only 单独报告，不混入 FP 分母。
2. **剥离标签**：函数名改为 `f_<id>`，文件名改为 `case_<id>.c`，删除 CWE 编号、`POTENTIAL FLAW`/`FIX` 注释。
3. **按用例基名/functional variant 做 group split**，不随机按函数 split；报告去重前后的样本数。
4. **同时报告 raw 与 cleaned 两组结果**；raw 用于与文献对比，cleaned 用于本文主张。
5. **报告 per-CWE 与 macro-average**；给出多数类基线、MCC、balanced accuracy。
6. **动态实验逐用例构建 harness**；报告编译成功率、运行超时率、sanitizer 触发率；`w32` 用例单独处理。
7. **把 Juliet 当作“工具行为压力测试”**，不要当作“真实项目泛化”的证据；真实项目结论用 SecVulEval/PrimeVul/ARVO。
8. **如果用于训练**：与真实项目测试集严格隔离；报告污染风险；不要用 Juliet 调参后再在 Juliet 测试集上报最好结果。

### 7.11 Juliet 在本项目中的合理定位

- **可以**：作为 CWE-401/416/476 的“压力测试/案例系列”，验证工具是否能处理已知模式；作为 label-cleaning 消融的实验材料；作为教学演示。
- **不可以**：作为主测试集声称“真实项目泛化”；用 Juliet 的排名代替 SecVulEval 的排名；用 Juliet 的高 F1 证明模型“会检测漏洞”。
- **建议**：把 Juliet 放在附录/补充实验，主表仍用 SecVulEval 的 160 + 180 对；如果要用 Juliet 补足 CWE-401 样本，明确标注“合成、清洗后、仅用于机制验证”。

## 8. 与本项目已有结果的对接

### 8.1 已有真实结果（引自 `report/results_summary.md`）

| 策略 | P | R | F1 | Acc | Spec | MCC | 配对 DA |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| M1 direct | 0.826 | 0.297 | 0.437 | 38.8 | 75.0 | 0.041 | 0.117 |
| M2 few-shot | 0.837 | 0.320 | 0.463 | 40.6 | 75.0 | 0.061 | 0.089 |
| M3 context | 0.812 | 0.305 | 0.443 | 38.8 | 71.9 | 0.020 | 0.122 |

- 配对任务中，M1/M2/M3 的“双报安全”分别为 113/113/108 对，“双报漏洞”44/49/49 对，“判反”2/2/1 对。
- 三种策略的 DA 都低于随机指定一侧的 56.1% 双方均正确率；主要失败是**双报安全**，不是判反。
- 修复：schema 有效率 83.4%–99.0%，但与输入不同只有 62.6%–83.3%，精确匹配参考修复只有 1.7%–5.0%。
- 成本：每策略 828 请求，总 USD 0.646–1.131；p50 5.8–6.25s，p95 17.9–20.0s。

### 8.2 这些结果说明了什么

1. **保守偏置**：P 高、R 低，模型只在表面证据很强时判“漏洞”。在配对任务中，它倾向于把两侧都判安全（108–113/180），而不是随机猜。
2. **上下文不是万能药**：M3 给了项目上下文，但 DA 只从 0.117 到 0.122，macro-F1 没有显著提升。这说明“更多文本”不等于“更有针对性的证据”。
3. **配对任务与独立任务不是同一能力**：独立集上 M2 的 macro-F1 最高，但配对 DA 最低（0.089）。不能用一个任务的排名推断另一个任务。
4. **修复的“格式正确”不等于“语义正确”**：schema 有效率高，但精确匹配低；这与 APR 文献的教训一致（文本相似/格式合规不能当修复正确）。
5. **统计功效有限**：160/180 的样本量、单一模型、单次运行；两两差值区间都跨 0，不能支持强排序结论。

### 8.3 对混合设计的直接含义

- **目标应该是提高配对 DA，而不是独立集 F1**。因为独立集已经 P 高 R 低，继续加上下文可能只改变很少的样本；配对任务才是“区分漏洞与修复”的核心。
- **工具证据要针对“差异”**：SAST 告警的 file:line、数据流路径、修复前后的告警变化，比“项目背景”更可能帮助模型看出哪一侧有问题。
- **不要只加 SAST 告警数量**：如果告警只告诉模型“这里可疑”，但不告诉它“修复版本为什么安全”，可能反而增加双报漏洞。需要**对比证据**（vulnerable vs fixed 的告警差异、路径差异、动态结果差异）。
- **动态证据应优先用于内存安全子集**：CWE-401/416/476 等；但本项目 CWE-401 只有 3/308，单独做 CWE-401 会严重欠功效。应把“内存安全家族”作为一个预先定义的分层，或引入 ARVO/Juliet 作为补充压力测试（明确标注合成）。
- **报告覆盖率**：如果只有 30% 的单元能跑 SAST/动态，任何“混合更好”的结论都只适用于这 30%；必须给出全集的 worst-case 下界。

### 8.4 已有结果不能支持的主张

- 不能支持“混合方法有效”——本项目还没跑混合条件。
- 不能支持“上下文有用/无用”——M3 的操纵同时改变了长度、格式、内容；且 context 非空层是单类别（126/126 漏洞），与总体差异混杂。
- 不能支持“修复正确率 17/81”——修复盲评是 LLM 辅助、无编译/测试/PoC；只能写“在该 rubric 下，LLM 辅助评审认为 17/81 处理了根因”。
- 不能支持“模型有 80% 准确率”——多数类基线就是 80%；必须看 MCC/balanced accuracy。
- 不能支持“跨项目泛化”——单模型、单次运行、测试集来自同一数据源。

### 8.5 边界条件与功效

- 160 条独立函数、180 对配对：在 discordance ≈30% 时，McNemar 的**最小可检测效应（MDE）约 11–12 个百分点**（80% power, α=0.05, two-sided）。这意味着 H1 的 10pp 目标在当前样本下**功效不足**；要么把目标设为 ≥10–12pp，要么增加配对样本到 250–300 对。
- 单一模型、单次运行：不能区分“方法效应”与“运行噪声”；新实验至少对 20% 子样本重复 2 次，报告一致率。
- CWE-401 只有 3/308：不能把 CWE-401 单独作为主分析；只能作为案例系列或分层探索。

> 结论：本项目最有信息量的下一步不是“再跑一个 prompt”，而是**在配对任务上做工具证据的条件化实验，并用安慰剂和覆盖率把“证据效应”与“长度/选择效应”分开**。

## 9. 可检验的研究假设 H1–H6

### 9.0 共同实验协议（所有假设共用）

1. **固定基座**：DeepSeek V4.1 Flash，temperature 0，max tokens 8192，thinking disabled；与现有三策略一致。
2. **固定测试集**：160 条独立函数 + 180 对配对；UID、拆分、项目分组不变；不重采样测试集。
3. **不覆盖旧结果**：新运行使用新的 `run_id` 和输出目录；旧 `test_v1_*` 只读。
4. **工具版本固定**：CodeQL/Semgrep/Infer/Clang/ASan/Valgrind 版本、规则集、查询文件全部记录；SARIF/JSON 原始输出存档。
5. **提示预算匹配**：同一假设内，各条件的输入 token 上限一致；如果工具卡更长，用截断/摘要控制在 ±10% 以内。
6. **开发/测试隔离**：阈值、few-shot 示例、融合权重只在 dev 上选；测试集只跑一次最终配置。
7. **重复性**：对 20% 子样本重复 2 次，报告一致率；若一致率 <90%，扩大重复比例。
8. **统计**：配对二值用 McNemar 精确检验；比例区间用 bootstrap（按项目聚类）；多假设用 Holm 校正；报告点估计、95% CI、成本、覆盖率、无效率。
9. **预注册**：在跑测试前写下条件、主要终点、决策规则、停止规则；分析时不改主要终点。
10. **失败分析**：随机抽 30–50 个案例做错误分类（无告警、告警误导、路径错误、格式错误、工具失败、超时），报告分类比例。

> 说明：以下“成本”是 API + 工具运行的粗略量级，不含人工 harness 开发；实际以账单为准。样本功效按 McNemar 近似估算，真实功效取决于 discordant 对的 b/c 分布。

### 9.1 H1：SAST 证据条件化提升配对判别，而非独立集 F1

| 项 | 内容 |
| --- | --- |
| **陈述** | 在固定模型与提示预算下，把离线 SAST 证据（rule id、file:line、message、数据流路径）加入单函数判定，会把配对 DA 从当前 8.9–12.2% 提高至少 **10 个百分点**；对 160 条独立检测的 macro-F1 提升不超过 **5 个百分点**（非劣/中性）。 |
| **机制与证据** | 配对任务要求“看出漏洞版本与修复版本的差异”；SAST 的 file:line/路径提供定位与差异线索。IRIS 在 Java 仓库级把 CodeQL 27/120 提到 55/120 [R4]；LLM4SA 在告警分流上 P 81.13/R 94.64 [R5]；LLMDFA/LLMSAN 说明路径/数据流证据能提升精确率 [R7][R8]。 |
| **条件** | C0 = M1 direct；C1 = M1 + 每单元 top-k（k=3）SAST 告警卡；C1p = C1 + 同长度随机告警（安慰剂）；C1s = C1 + 来自其他单元的真实告警（打乱对应）。 |
| **主要终点** | ΔDA = DA(C1) − DA(C0)，180 对。 |
| **次要终点** | 独立集 macro-F1（非劣，margin 5pp）；per-version P/R；告警覆盖率；输入 token；USD；p50/p95 延迟；无效输出率。 |
| **决策规则** | ΔDA 的 95% CI 下界 > 0，且点估计 ≥ 10pp；同时独立集 macro-F1 的 95% CI 下界 > −5pp；C1 相对 C1p 的 ΔDA ≥ 5pp（证据效应，而非长度效应）。 |
| **证伪条件** | ΔDA < 5pp 或 CI 跨 0；或独立集 macro-F1 下降 > 5pp；或 C1 ≈ C1p（安慰剂同样提升）→ 增益来自长度/格式，不支持“证据效应”。 |
| **混杂与处理** | 告警覆盖率（只在有告警单元提升 → 报告分层，不外推）；prompt 长度（安慰剂控制）；工具版本（pin + SARIF 存档）；单元选择（intent-to-evaluate，不删无告警单元）。 |
| **成本/可行性** | 3–4 个条件 × 340 单元；C1 输入 token 约为 C0 的 1.5–2 倍；API 约 $3–6；SAST 运行一次性、可缓存。1 周内可完成。 |
| **功效** | 180 对、discordance ≈30% → MDE ≈11pp（80% power）。H1 的 10pp 目标处于边缘；若要把 8pp 作为目标，需要约 300–360 对。建议把 H1 目标设为 12pp，或把配对集扩到 250+。 |

**解释**：如果 H1 成立，说明“工具证据”能改变配对判断；如果只在有告警的子集成立，说明是覆盖率效应，不是模型能力。两种结果都有价值，但结论不同。

### 9.2 H2：Agent 反馈的增益来自真实工具，而非多轮/更长提示

| 项 | 内容 |
| --- | --- |
| **陈述** | 在 H1 的 C1 基础上，允许最多 3 轮工具调用（读函数、查调用者、跑 SAST），会把 DA 再提高至少 **6 个百分点**；但把工具输出替换为同长度随机告警后，增益小于 **2 个百分点**。 |
| **机制与证据** | Agent 可以按需请求证据，而不是被动接收固定卡片；EnIGMA 的交互式工具显著提升 CTF [R15]；RepoAudit 的 validator + 数据流事实达到 P 78.43 [R14]；但 Agentless 的简单流程在 SWE-bench Lite 上 32.00%、$0.70，优于复杂 agent [R18]；EnIGMA 还发现 soliloquizing [R15]。 |
| **条件** | C1（单轮条件化）；C2（3 轮 agent，真实工具）；C2p（3 轮 agent，安慰剂随机告警）；C2s（3 轮 agent，打乱单元的真实告警）。 |
| **主要终点** | ΔDA(C2−C1)；ΔDA(C2−C2p)。 |
| **次要终点** | Tool-call success rate；evidence grounding rate；validated path rate；每轮边际正确数；USD/正确对；p95 延迟；无效输出率。 |
| **决策规则** | ΔDA(C2−C1) ≥ 6pp 且 CI 下界 > 0；ΔDA(C2−C2p) ≥ 4pp；C2p−C1 < 2pp。 |
| **证伪条件** | C2 ≈ C2p（增益来自多轮/长度）；或 C2 < C1（agent 反而更差）；或 evidence grounding rate < 70%（结论大量无证据）。 |
| **混杂与处理** | 轮数、token 预算、工具延迟、模型工具使用能力、观察截断；固定轮数上限与工具集；记录每次调用与原始输出；对工具输出做程序化解析。 |
| **成本/可行性** | 4 个条件 × 340 单元 × 最多 3 轮；API 约 $10–20；工程 2–3 周（工具封装、日志、重试）。 |
| **功效** | 同 H1，6pp 目标功效不足；建议把目标设为 10pp，或把样本扩到 300+ 对。 |

**关键**：H2 的 value 不在“agent 是否更好”，而在“**能否证明增益来自工具证据**”。安慰剂/打乱对照是必须的。

### 9.3 H3：动态证据在可运行内存安全子集上提升最大，但覆盖率是硬约束

| 项 | 内容 |
| --- | --- |
| **陈述** | 在预注册的内存安全子集（CWE-401/416/476 等）上，加入 ASan/LSan/Valgrind 的运行时证据，会把精确率提高至少 **12 个百分点**或 F1 提高至少 **8 个百分点**；但该收益只出现在可编译、可运行的子集，且覆盖率预计 <50%，因此必须报告覆盖率调整后的下界。 |
| **机制与证据** | ASan 检测越界/UAF，LSan/Valgrind 检测泄漏 [R24][R25][R47]；CWE-401 官方页面明确把 ASan/Valgrind 列为动态检测手段，并指出需要 crafted inputs、只报告错误条件而非根因 [R26]；ARVO 81% 可复现、Magma 提供 ground-truth 注入 bug，说明动态基准可行但工程重 [R22][R23]。 |
| **条件** | C1（LLM+SAST）；C3（LLM+SAST+dynamic）。可选 C3p（动态结果打乱/假阳性注入）作为安慰剂。 |
| **主要终点** | 在 runnable 子集上的 Δprecision 或 ΔF1；动态覆盖率（编译成功且运行完成的比例）。 |
| **次要终点** | 全集 worst-case/best-case 边界；编译失败率；超时率；sanitizer 触发率；每单元 harness 开发时间；USD。 |
| **决策规则** | runnable 子集上 Δprecision ≥ 12pp 或 ΔF1 ≥ 8pp，CI 下界 > 0；同时报告全集 [worst, best] 区间；若覆盖率 <30%，无论点估计如何，结论写“证据不足”。 |
| **证伪条件** | runnable 子集无显著提升；或覆盖率过低导致全集区间跨 0；或动态证据只确认了 SAST 已确认的样本（增量信息为零）。 |
| **混杂与处理** | harness 质量（统一模板 + 人工抽检）；故意泄漏/退出时 still-reachable（区分 definitely lost/lost）；sanitizer 版本；环境差异（WSL/容器）；超时设置。 |
| **成本/可行性** | 工程 2–4 周；API 成本低（$2–5）；主要成本是 harness 与编译环境。 |
| **样本/功效** | 若内存安全子集只有 30–50 个 runnable 单元，只能做案例/pilot；建议用 ARVO 或清洗后的 Juliet CWE-401 作为补充压力测试，但主结论仍以真实项目为准。 |

**解释**：H3 最容易被“覆盖率偏差”误导。正确的报告不是“动态把 F1 提高了 20pp”，而是“在 35% 可运行子集上提高 20pp；全集 worst-case 下界为 −2pp，best-case 为 +7pp，因此不能断言全集提升”。这种诚实的边界比点估计更有价值。

### 9.4 H4：路径验证降低误报，优于同等 token 的 few-shot/context

| 项 | 内容 |
| --- | --- |
| **陈述** | 要求模型输出可验证的 source→sink 路径，并用符号工具检查可达性；与同等 token 预算的 few-shot（M2）或 context（M3）相比，验证条件会把误报率降低至少 **10 个百分点**，召回率损失不超过 **5 个百分点**。 |
| **机制与证据** | LLMSAN 强制输出数据流路径并验证，精确率提升 21.99pp [R8]；LLMDFA 用定理证明器验证路径可行性，P 87.10/R 80.77 [R7]；IRIS 用 LLM 规格 + CodeQL 验证 [R4]；Interleaving 用静态分析约束 LLM，召回 52.55→77.83、F1 0.612→0.804 [R13]。 |
| **条件** | M2（few-shot）；M3（context）；V（路径 + 验证器）；V'（路径但不验证，控制“要求写路径”的格式效应）。 |
| **主要终点** | FPR（独立集负样本上的假阳性率）；recall；validated path rate。 |
| **次要终点** | validator precision（50 条人工标注路径）；DA（配对集）；token；USD；无效输出率。 |
| **决策规则** | FPR 降低 ≥10pp，recall 损失 ≤5pp；validator precision ≥80%；V 相对 V' 的 FPR 降低 ≥5pp（验证本身有效，而非“写路径”有效）。 |
| **证伪条件** | validator pass rate <30%（工具无法确认大多数路径）；或 recall 损失 >10pp；或 FPR 降低 <5pp；或 V ≈ V'（验证无增量）。 |
| **混杂与处理** | 验证器不完备/不可靠；路径粒度（行级/语句级）；模型格式合规率；token 预算；人工标注一致性。 |
| **成本/可行性** | 4 个条件 × 340 单元；验证器运行便宜；API 约 $5–10；工程 1–2 周。 |
| **功效** | 160 条独立集、discordance ≈30% → MDE ≈12pp；10pp 目标边缘。建议把 FPR 目标设为 12–15pp，或把负样本扩到 250+。 |

**解释**：H4 的关键不是“让模型写解释”，而是“让解释变成可验证的约束”。如果只是要求写路径但不验证，可能只是增加 token，不降低误报（V' 对照就是为此设计）。

### 9.5 H5：混合选择性预测在 risk–coverage 上支配单一方法

| 项 | 内容 |
| --- | --- |
| **陈述** | 把 LLM 分数、SAST 告警数、动态证据融合为可弃权分类器，在 50% 覆盖率下错误率至少比最佳单一方法低 **40%**，在 80% 覆盖率下低 **20%**；收益在低覆盖率区间最大。 |
| **机制与证据** | LLM/SAST/dynamic 的错误模式不同（见第 2 节）；选择性分类在低置信度时弃权，可提升高置信度区域的准确率 [R43]；风险-覆盖率曲线是比单点 F1 更完整的评估。 |
| **条件** | 最佳单一方法（预计 M1 或 C1）；混合融合（logistic regression / rank averaging，dev 上拟合）；混合 + 弃权。 |
| **主要终点** | 固定覆盖率（50%、80%）下的错误率；AURC（area under risk–coverage curve）。 |
| **次要终点** | E-AURC；校准误差（ECE）；弃权率；每个覆盖率下的 P/R；USD/正确决策。 |
| **决策规则** | 50% 和 80% 覆盖率下，Δerror 的 bootstrap 95% CI 上界 < 0；AURC 低于最佳单一方法。 |
| **证伪条件** | 无支配；或收益在校准后消失；或融合权重在 dev/test 上不稳定（bootstrap 符号翻转）。 |
| **混杂与处理** | 分数校准；dev/test 分布漂移；融合过拟合；LLM 输出是离散标签而非概率（需要 logit/verbalized confidence 或多采样频率）。 |
| **成本/可行性** | 复用已有预测即可，API 成本近零；需要 dev 集和校准；1 周内可完成。 |
| **功效** | 340 单元；50% 覆盖率下 n≈170，12pp 差异可检测；80% 下 n≈272，8pp 差异可检测。 |

**解释**：H5 是“工程上最实用”的假设：即使单个方法不强，融合 + 弃权也能在允许拒答的场景下提升可靠性。课程项目可以用它展示“风险-覆盖率”思维，而不是只追 F1。

### 9.6 H6：Juliet 排名不能迁移到真实项目；标签清洗会显著改变结论

| 项 | 内容 |
| --- | --- |
| **陈述** | 在 Juliet C/C++ 上得到的方法排名，与在 SecVulEval 配对集上的排名，Spearman ρ ≤ **0.3**；去掉函数名、注释、CWE 标识后，LLM-only 的 Juliet F1 下降至少 **15 个百分点**，而 SAST-only 下降不超过 **5 个百分点**。 |
| **机制与证据** | Juliet 函数名/文件名/注释直接编码标签 [R29]；NIST IR 8561 引用“函数名与代码属性高度相关”“近似重复”两点限制 [R28]；ROMEO 删除 primary good function 以避免泄漏 [R31]；Grahn & Zhang 指出随机划分导致近重复泄漏 [R32]；PrimeVul 显示真实/严格拆分下性能从 68.26% F1 跌到 3.09% [R2]；Top Score 说明函数级二分类在缺少上下文时定义不良 [R3]。 |
| **条件** | 4–6 个方法（LLM-only、SAST-only、LLM+SAST、LLM+dynamic、混合、随机基线）× 2 个基准（Juliet raw、Juliet cleaned、SecVulEval 配对）。 |
| **主要终点** | Spearman ρ（方法排名）；ΔF1（raw − cleaned）。 |
| **次要终点** | Kendall τ；top-1 方法是否改变；per-CWE ΔF1；SAST-only 的 ΔF1；bootstrap 排名稳定性。 |
| **决策规则** | ρ ≤ 0.3 或 top-1 改变 → 支持“不能迁移”；LLM-only ΔF1 ≥ 15pp 且 SAST-only ΔF1 ≤ 5pp → 支持“标签泄漏主要影响 LLM”。 |
| **证伪条件** | ρ ≥ 0.7 → Juliet 排名可迁移；ΔF1 < 5pp → 标签泄漏不 material；或清洗后 LLM 仍远高于 SAST（说明 LLM 不是靠名字）。 |
| **混杂与处理** | 方法数量少（6 个）导致 rank 不稳定；用 bootstrap 报告排名分布，必要时增到 8–10 个方法；CWE 组成不同；prompt 不同；样本量小。 |
| **成本/可行性** | Juliet 子集 200–400 例；LLM API 约 $5–10；SAST 运行便宜；1–2 周。 |
| **功效** | 6 个方法的 Spearman 置信区间很宽；结论应写成“排名不稳定/不可迁移”，而不是精确的 ρ 值。 |

**解释**：H6 是“元评估”假设：它不提出新检测器，而是检验我们用来评价检测器的基准是否可信。对课程项目，这是一个低成本、高讨论度的创新点。

### 9.7 H7（探索性）：Agent 的准确率在 3 轮内饱和

| 项 | 内容 |
| --- | --- |
| **陈述** | 在 H2 的 agent 设置下，第 1→3 轮的边际 DA 增益最大；第 4→6 轮的边际增益 <2pp，而成本近似线性上升；因此 3 轮是 Pareto 最优点。 |
| **条件** | 轮数上限 1/2/3/6；同一工具集、同一模型。 |
| **主要终点** | 每轮边际 DA；累计 USD；p95 延迟。 |
| **决策规则** | 3→6 轮 ΔDA < 2pp 且成本增加 >50% → 支持饱和。 |
| **证伪条件** | 6 轮仍有 ≥5pp 增益；或成本 sublinear。 |
| **成本** | 中—高；只建议在 H2 已运行时顺带做，不单独开实验。 |

### 9.8 假设汇总

| 假设 | 主要终点 | 目标效应 | 当前样本的近似 MDE | 成本档 | 关键证伪 |
| --- | --- | ---: | ---: | --- | --- |
| H1 SAST 条件化 | ΔDA | ≥10pp | ~11pp（180 对） | 低 | C1 ≈ 安慰剂 |
| H2 Agent 反馈 | ΔDA(C2−C1) | ≥6pp | ~11pp | 中 | C2 ≈ 安慰剂 |
| H3 动态确认 | Δprecision/ΔF1 | ≥12/8pp | 取决于 runnable 子集 | 高 | 覆盖率 <30% |
| H4 路径验证 | ΔFPR | ≥10pp | ~12pp（160） | 中 | 验证通过率 <30% |
| H5 选择性混合 | Δerror@coverage | −40%/−20% | ~10–12pp | 低 | 校准后消失 |
| H6 Juliet 迁移 | ρ / ΔF1 | ≤0.3 / ≥15pp | rank 不稳定 | 低 | ρ ≥0.7 |
| H7 轮数饱和 | 边际 ΔDA | <2pp@6轮 | 探索性 | 中 | 6 轮仍 +5pp |

> **建议的最小实验包**：H1 + H6 + Juliet 清洗消融。三者共用大部分工具与数据，API 成本约 $10–20，2–3 周可完成，且能形成“方法 + 评估”双贡献。H2/H4 作为扩展，H3 作为案例研究。

## 10. 统一 AI + 传统 benchmark 设计

### 10.1 评估矩阵

| 证据来源 \ 任务 | U1 函数检测 | U2 配对判别 | U3 仓库定位 | U4 动态复现 | U5 端到端 agent |
| --- | --- | --- | --- | --- | --- |
| 无（LLM only） | 必做 | 必做 | 可选 | 不可行 | 可选 |
| SAST only | 必做 | 必做 | 可选 | 不可行 | 不可行 |
| LLM + SAST | 必做 | 必做 | 可选 | 不可行 | 可选 |
| LLM + dynamic | 子集 | 子集 | 不可行 | 可选 | 可选 |
| LLM + SAST + dynamic | 子集 | 子集 | 可选 | 可选 | 可选 |
| Agent | 可选 | 可选 | 可选 | 可选 | 可选 |

**原则**：不要把所有单元池化。U1/U2 是主表；U3–U5 是扩展/案例。每个单元单独报告，不做跨任务平均。

### 10.2 条件定义

| 条件 | 证据 | 说明 | 预期优势 | 预期风险 |
| --- | --- | --- | --- | --- |
| B0 | 无 | 多数类/随机基线 | 校准 | 无信息 |
| B1 | SAST | 规则/数据流，阈值固定 | 高覆盖率、低成本 | 误报高、缺语义 |
| B2 | LLM | M1 direct | 语义、解释 | 保守、幻觉 |
| B3 | LLM+SAST | C1 单轮条件化 | 定位+语义 | 长度/选择偏差 |
| B4 | LLM+dynamic | 仅可运行子集 | 运行时事实 | 覆盖率低 |
| B5 | LLM+SAST+dynamic | C3 | 互补 | 工程重、成本高 |
| B6 | Agent | C2，3 轮 | 按需取证 | 成本、soliloquizing |
| B7 | Selective hybrid | H5 融合+弃权 | 风险控制 | 覆盖率下降 |

### 10.3 指标

**检测（U1）**：P、R、F1、macro-F1、balanced accuracy、MCC、AUC；per-CWE macro；多数类基线；Wilson/bootstrap CI。

**配对（U2）**：DA（双方均正确）、双报漏洞、双报安全、判反；per-version P/R/F1；position bias（A/B 顺序）；localization hit（如果输出 evidence_lines）。

**定位（U3）**：Top-1/3/5 函数命中；行级 hit rate；与参考 diff 的重叠；误报行数。

**动态（U4）**：编译成功率、运行完成率、sanitizer 触发率、PoC 成功率、超时率、平均运行时间。

**成本**：输入/输出 token、USD、p50/p95 延迟、工具 CPU 时间、人工 harness 小时；`USD / (TP+TN)`（U1）与 `USD / #both-correct`（U2）。

**覆盖率**：static coverage（有可解析 SAST 结果的单元比例）、dynamic coverage（可运行单元比例）、evidence coverage（至少一条非空证据的比例）、abstention rate。

**稳健性**：重复运行一致率；prompt 变体敏感度；label-cleaning ΔF1；CWE 分层稳定性。

### 10.4 公平性控制

1. **同模型、同版本、同解码参数**；记录 API 返回的 model id/日期。
2. **同测试单元、同 UID、同顺序**；A/B 位置随机化，避免 position bias。
3. **同提示预算**：按 token 上限匹配；工具卡超长时截断并记录。
4. **同工具版本/规则**：CodeQL 查询包、Semgrep 规则集、Infer 版本、ASan/Valgrind 版本全部 pin；工具文档见 [R48][R49][R50]，动态检测文档见 [R47]。
5. **同评估脚本**：解析、去重、匹配、统计用同一套代码；避免“不同条件不同口径”。
6. **dev-only 调参**：阈值、few-shot、融合权重、停止规则只在 dev 上选。
7. **不删失败单元**：编译失败、超时、无效输出都进入分母；另报“可评估子集”的结果。
8. **顺序随机化**：同一天内随机化条件顺序，减少 API 漂移；记录时间戳。

### 10.5 统计与报告

- **配对二值**：McNemar 精确检验；报告 b/c（条件 A 对/条件 B 对）和 odds ratio。
- **比例区间**：bootstrap 按项目聚类（cluster bootstrap），至少 2,000 次；报告 95% CI。
- **多条件**：Holm 校正；预先指定主要终点，避免“挑一个显著的结果”。
- **效应量**：ΔDA、ΔF1、ΔFPR、risk–coverage 的 Δerror；不要只报 p 值。
- **功效**：报告 MDE；如果样本不足以检测目标效应，明确写“underpowered”，不要把“不显著”写成“无差异”。
- **可复现**：提供 predictions JSONL、工具原始输出、成本账本、分析脚本；不提供密钥。

### 10.7 反模式（会让 benchmark 误导）

1. **跨数据集比较**：LLM-only 在 Juliet、SAST-only 在真实项目，然后说“LLM 更好”。
2. **池化任务**：把 U1 和 U2 的平均分合并，掩盖配对失败。
3. **只报 accuracy**：在不平衡数据上，80% 可能等于多数类基线。
4. **文本匹配当修复正确**：与参考 diff 相似不等于漏洞消除。
5. **忽略覆盖率**：动态只在 20% 单元上跑，却把结果外推到全集。
6. **测试集调参**：用测试表现选 prompt/阈值/轮数，再报同一测试集。
7. **只报最好的 CWE**：挑一个容易的 CWE 证明方法有效。
8. **单次运行 + 单模型**：把运行噪声当方法效应。
9. **不报无效输出**：schema 失败、超时、API 错误被静默删除。
10. **不报成本**：混合方法的 USD/延迟可能比基线高一个数量级。

## 11. 课程项目创新点与可行路线

### 11.1 四个可形成创新点的设计

**I1：安慰剂对照的工具反馈（方法学创新）**

- **做法**：真实告警 vs 同长度随机告警 vs 打乱单元的真实告警；三者对比，分离“证据效应”“长度/格式效应”“选择效应”。
- **为什么新**：现有混合论文大多只比“有工具 vs 无工具”，很少控制提示长度/格式；因此“工具有效”常与“prompt 更长”混淆。
- **产物**：一张 2×2 表（证据真/假 × 有/无工具卡）+ “证据效应”估计 + 失败分类。
- **风险**：随机告警太假，模型可能一眼识破；应使用“同 CWE、同格式、来自其他单元”的告警，保持表面可信。

**I2：配对差异端点（评估创新）**

- **做法**：主指标从单函数 F1 改为 DA、双报安全/双报漏洞/判反、per-version P/R；增加“差异敏感度”（只改漏洞行时，判定是否翻转）。
- **为什么新**：单函数 F1 会把“保守”误读为“准确”；配对任务才接近真实的安全决策（这个版本是否引入了漏洞）。
- **产物**：DA + risk–coverage + 错误 taxonomy；可直接复用到修复评估。
- **风险**：DA 的机会水平不是 50%（本项目随机指定一侧的双方均正确率为 56.1%）；必须报告机会基线。

**I3：覆盖率调整的混合 benchmark（测量创新）**

- **做法**：把 static/dynamic/evidence coverage 作为一等指标；对未覆盖单元给出 worst-case/best-case 边界；不静默删除失败单元。
- **为什么新**：动态/SAST 的增益通常只在可运行/可解析子集上；不报告覆盖率，等于把“工具能处理的样本”当成“全部样本”。
- **产物**：coverage 表 + 全集边界 + 分层森林图。
- **风险**：worst-case 边界可能很宽，结论变成“不确定”；但这比虚假的精确更有价值。

**I4：Juliet 标签清洗消融 + 合成到真实的排名迁移（元评估创新）**

- **做法**：raw / 去函数名 / 去函数名+注释 / 去函数名+注释+CWE 四档；比较 LLM-only 与 SAST-only 的 ΔF1；把 Juliet 排名与 SecVulEval 排名做 Spearman/Kendall。
- **为什么新**：Juliet 被广泛使用，但 LLM 时代的标签泄漏量化很少；一个“排名不迁移”的负结果本身就有教学/方法学价值。
- **产物**：ΔF1 表 + 排名散点 + 清洗脚本/清单。
- **风险**：方法数少导致 rank 不稳定；用 bootstrap 报告排名分布，避免精确 ρ 的过度解读。

### 11.2 最小可行研究包（MVP，3–4 周）

## 12. 限制、未决问题与边界

### 12.1 文献缺口

1. **C/C++ 函数级混合检测证据薄**：IRIS 偏 Java 仓库级；InferROI 偏 Android/Java；LLM4SA 是告警分流；LLIFT 是窄 bug 类。很少有工作在本项目的“C/C++ 函数级 + 配对 + 单模型”设置上做系统比较。
2. **动态 + LLM 的结合多集中在 fuzzing/agent**：EnIGMA、Revelio 等；函数级“动态证据条件化”的研究很少。
3. **成本-精度 Pareto 缺失**：多数论文只报 F1/准确率，不报 USD/延迟/覆盖率；课程项目可以用“每美元正确决策”形成差异化。
4. **Juliet 的 LLM 标签泄漏量化缺失**：现有泄漏研究多针对传统 ML；LLM 是否更依赖函数名/注释，缺少系统实验。
5. **跨模型迁移缺失**：多数混合工作用 GPT-4；DeepSeek/Qwen/Llama 上的可迁移性未知。

**补充阅读**（用于扩展文献地图）：

- LLMxCPG [R12]：用 Code Property Graph 切片压缩仓库代码，再交给 LLM；属于“符号侧提供结构、神经侧读切片”的变体。
- AutoCodeRover [R17]：代码搜索 + 频谱故障定位；说明结构化搜索本身就能带来增益，不一定需要复杂 agent。
- Cybench [R21]：40 个专业级 CTF 任务；任务级验证，适合评估 agent 的端到端能力。
- ReVeal [R44]：深度学习漏洞检测会利用数据集伪影，跨项目泛化显著下降；与本项目的“单数据集”限制直接相关。
- Revelio [R46]：用 sanitizer 确认 PoV，在 100 个 ARVO 项目上评估；说明“agent + 动态验证”的可行性与成本（约 1 小时/项目、$300 总量）。

### 12.2 方法限制

- **样本量**：160/180 的 MDE 约 11–12pp；小于 10pp 的效应很难可靠检测。H1/H2/H4 的目标效应都在边缘。
- **单模型/单次运行**：不能区分方法效应与运行噪声；需要重复子样本。
- **测试集同源**：SecVulEval 的 160/180 来自同一数据源；跨项目/跨 CWE 的外推有限。
- **CWE-401 样本极少**：3/308；不能单独支撑“内存泄漏检测”结论。
- **工具版本漂移**：CodeQL/Semgrep 规则更新会改变告警；必须 pin 版本并归档 SARIF。
- **动态 harness 工程**：函数级 snippet 往往缺 `main`/依赖；harness 质量是 H3 的最大混杂。
- **LLM 非确定性**：temperature 0 仍可能变化；单次运行的结论应标注“探索性”。

### 12.3 本文件没有做的事

- 没有跑任何新实验；没有生成新的检测/配对/修复数字。
- 没有做人类评审；没有做编译/测试/PoC 验证。
- 没有覆盖所有 CWE；没有做仓库级/端到端 agent 实验。
- 没有把 2026 年的预印本（如 Revelio）当作同行评审结论；文中已标注“预印本”。

### 12.4 待决问题（交给后续工作）

1. 本项目是否有多项目元数据，能做 cluster bootstrap？如果项目数 <10，cluster 区间会很不稳定。
2. SAST 工具在 WSL 中是否可安装/可跑？CodeQL 需要构建 C/C++ 数据库；Semgrep 无需构建但规则覆盖有限。建议先做 20 单元 pilot。
3. 是否有可用的 C 编译环境/harness 模板？如果没有，H3 应降级为案例研究。
4. 测试集是否已经冻结？新实验是否允许读取测试集标签？如果不允许，H1/H4 的评估需要预先写死脚本。
5. 课程报告的主贡献是“方法”还是“评估”？如果是评估，H6 + 安慰剂对照比 H3 更划算。

## 附录 B：Juliet 标签清洗检查清单

### B.1 清洗级别

| 级别 | 处理 | 目的 |
| --- | --- | --- |
| L0 raw | 原样 | 与文献对比 |
| L1 name | 函数名/文件名去标签 | 测函数名泄漏 |
| L2 name+comment | 再去 `POTENTIAL FLAW`/`FIX` 注释 | 测注释泄漏 |
| L3 name+comment+CWE | 再把 `CWE\d+` 替换为 `CWE-XXX` | 测 CWE 编号泄漏 |
| L4 L3+group split | 按用例基名/functional variant 分组划分 | 测近重复泄漏 |

### B.2 建议的替换规则（示例，不是唯一实现）

```text
# 函数名
(_bad|_good[0-9]*|BadSource|BadSink|goodG2B[0-9]*|goodB2G[0-9]*|helperBad|helperGood) -> _f

# 文件名/路径
CWE[0-9]+_ -> case_
_(bad|good[0-9]*)\. -> .
w32 -> port

# 注释
/\*\s*POTENTIAL FLAW.*?\*/ -> /* ... */
/\*\s*FIX.*?\*/ -> /* ... */
//\s*POTENTIAL FLAW.* -> //
//\s*FIX.* -> //

# CWE 编号
CWE[0-9]+ -> CWE-XXX
```

**注意**：

- 替换后要保证代码仍可编译；函数名冲突时加唯一后缀。
- 不要删除 `#include`/类型定义；只改标识符和注释。
- 记录替换前后的 diff；报告清洗后的样本数、编译成功率。
- 如果模型仍然从代码结构（malloc/free 模式）识别出 CWE，这是合理信号，不是泄漏；泄漏指的是“名字/注释/编号直接给答案”。

### B.3 提示词约束（建议加入 system prompt）

> “你只能依据代码的数据流、控制流、资源生命周期和可见的函数调用关系判断。不要使用标识符名称、文件名、注释、CWE 编号作为证据；如果这些信息被匿名化，你仍应给出相同判断。请在 `evidence` 中引用具体行号与语句。”

### B.4 报告要求

- 每个清洗级别报告：样本数、编译成功率、F1/P/R、ΔF1（相对 L0）。
- 分别报告 LLM-only 与 SAST-only；如果 LLM-only 下降远大于 SAST-only，支持“标签泄漏主要影响 LLM”。
- 如果 L1 就大幅下降，说明函数名是主要泄漏源；如果 L2 才下降，说明注释是主要泄漏源。

## 附录 C：功效估算（近似）

对配对二值数据，McNemar 的近似最小可检测效应：

\[
\mathrm{MDE} \approx (z_{1-\alpha/2}+z_{1-\beta})\sqrt{p_d/n}
\]

其中 \(p_d\) 是 discordant 对比例，\(n\) 是配对数；\(\alpha=0.05\)、\(\beta=0.2\) 时 \(z_{1-\alpha/2}+z_{1-\beta}\approx 2.80\)。

| n \ p_d | 0.20 | 0.30 | 0.40 |
| ---: | ---: | ---: | ---: |
| 160 | 9.9pp | 12.1pp | 14.0pp |
| 180 | 9.3pp | 11.4pp | 13.2pp |
| 250 | 7.9pp | 9.7pp | 11.2pp |
| 300 | 7.2pp | 8.9pp | 10.2pp |
| 360 | 6.6pp | 8.1pp | 9.3pp |

**读法**：当前 180 对、discordance 30% 时，只有 ≥11pp 的 DA 差异才有约 80% 功效。H1 的 10pp 目标处于边缘；H2 的 6pp 目标明显功效不足。若课程报告要主张小效应，必须扩样本或把结论写成“探索性”。

**注意**：这是近似公式，假设 discordant 对在 b/c 之间大致平衡；真实功效取决于 b、c 的具体分布。正式实验前建议用 pilot 估计 \(p_d\)，再做模拟功效分析。

## 附录 D：一页速查（给报告/答辩用）

**如果只能记住五件事**：

1. 混合检测的可靠收益在**告警分流、规格推断、路径验证、模式合成**；不是“LLM 直接读函数”。
2. Agent 不是默认更好；**接口、验证器、停止规则**比“多轮”重要；Agentless 是反例。
3. 动态证据对内存安全最直接，但**覆盖率**是硬约束；不报覆盖率的增益不可解释。
4. Juliet/SARD 的三大陷阱：**标签泄漏、近似重复、合成简单**；必须清洗 + group split + 双基准。
5. 本项目最有信息量的实验：**配对 DA + 安慰剂工具反馈 + 覆盖率调整**；不是再换 prompt。

**如果只能做一个新实验**：H1 + 安慰剂对照（C0/C1/C1p），180 对，2 周，约 $5。它能回答“工具证据是否真的改善配对判别”，且能直接写进报告。

**如果只能做一个评估研究**：H6 + Juliet 清洗消融，200–400 例，1–2 周，约 $5–10。它能回答“我们用的合成基准是否可信”，负结果也有价值。

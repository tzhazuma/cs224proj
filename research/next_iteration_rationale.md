### 0.2 一句话版本

1. **Tier A 的 0.383 不是“模型不够强”这么简单，而是“模型比一个不看代码的长度规则还差”**；同时它的置信度几乎没有排序能力（AUROC 0.540），所以“调阈值”能抬 `macro-F1`，但抬不了 `MCC`。
2. **Pair 的 86.67% 在方向平衡后只剩 63.6%（MiMo）和 47.7%（DeepSeek）**；前者略高于 50%，后者与随机不可区分。单序数字的主要成分是长度方向和槽位。
3. **验证器不是“找不到 FP”，而是“把 TP 和 FP 一起撤”**；两个臂把 11/11 个 FP 都撤了，同时撤了 40–43 个 TP。它的置信度对 FP/TP 甚至是反向排序。
4. **CodeQL 的 23 个 FP 不是随机噪声，而是 4 个可命名的 C++ 模式**；`memory-never-freed` 单独是 46 TP / 0 FP，问题被隔离在一个查询里，因此“用证人过滤修 may 查询”是一个边界清晰的实验。
5. **动态 140/140 是“三种定向模式的并集”**，不是通用动态检测器；没有覆盖率时，`clean` 只能写成“本次执行路径未观察到”，不能写成 TN。

### 2.2 本次复核：三个零成本基线

#### 2.2.1 常量基线

测试集 128 V / 32 NV，正类占 80%。两个常量规则：

| 规则 | TP | FP | FN | TN | accuracy | macro-F1 | MCC |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 永远判有漏洞（多数类） | 128 | 32 | 0 | 0 | **80.00%** | **0.4444** | 0 |
| 永远判无漏洞 | 0 | 0 | 128 | 32 | 20.00% | 0.1667 | 0 |

DeepSeek direct 的 `accuracy=38.75%` **低于多数类的 80%**；`macro-F1=0.3828` **低于多数类的 0.4444**。这不是“F1 低一点”，而是“在项目自己的主终点上，模型不如一个常量规则”。

原因不是模型“不会判正类”，而是它的操作点极度保守：它只把 46/160 判为正（28.75%），而真实正类率是 80%。它的 precision 0.826 看起来高，但只比基准率 0.80 高 2.6 pp；这是基准率的影子，不是判别力。MCC 0.041 也说明这一点。

#### 2.2.2 单参数长度规则

在 dev 40 上扫描“函数体字符数阈值”，选 `macro-F1` 最大的规则；方向由数据决定。选中：

> **body 字符数 ≤ 3,227 → 判有漏洞**（dev `macro-F1=0.5699`）。

把这个**在 dev 上选好的**规则原样应用到 test 160：

| 规则 | TP | FP | FN | TN | accuracy | macro-F1 | MCC |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 长度 ≤3,227 → 漏洞 | 101 | 23 | 27 | 9 | **68.75%** | **0.5331** | **0.0674** |
| 95% CI（项目 cluster bootstrap） | — | — | — | — | — | **[0.4564, 0.6145]** | — |
| DeepSeek direct | 38 | 8 | 90 | 24 | 38.75% | 0.3828 | 0.0414 |

配对 McNemar（同一 160 条，模型错/长度对 vs 模型对/长度错）：**83 vs 35，exact two-sided `p=1.16e-5`**。长度规则在 83 条上对而模型错，模型只在 35 条上对而长度错。

这不是说“长度是好检测器”。它的 MCC 也只有 0.067，接近 0；它只是抓住了数据的一个先验：**漏洞函数的中位长度 1,307 字符，非漏洞 1,791 字符**（test）。一个参数、不看代码，就能在 `macro-F1` 上比 LLM 高 0.15。这说明 LLM 的 0.383 主要不是“难度”，而是“操作点 + 数据先验不匹配”。

为了排除“阈值是 test 上调出来的”这一质疑，再给两个参照：

| 规则 | 阈值来源 | test macro-F1 |
| --- | --- | ---: |
| dev 选中阈值 3,227 | dev 40，`macro-F1` 最大 | 0.5331 |
| test oracle 阈值 3,973 | test 160，上界（不可部署） | 0.5645 |
| test 中位数 1,329 | test 中位数，事后 | 0.4643 |
| dev 中位数 1,504 | dev 中位数，可部署 | 0.5107 |

阈值在 1,500–4,000 之间时，test `macro-F1` 在 0.51–0.56 之间（见附录 B），不是单点侥幸。**结论：0.383 低于一个稳健的单参数先验，低得不是抽样噪声。**

#### 2.2.3 置信度操作点（事后上界）

DeepSeek direct 的 `parsed.confidence` 是“对自身判定的置信度”，不是 `P(vulnerable)`。构造一个**事后**分数：

```
score = confidence            if is_vulnerable
      = 1 - confidence        if not is_vulnerable
```

在 test 上扫描阈值（这是 oracle，不可部署）：

| 阈值 | TP | FP | FN | TN | accuracy | macro-F1 | MCC |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 0.5（等于原判定） | 38 | 8 | 90 | 24 | 38.75% | 0.3828 | 0.0414 |
| 0.4 | 88 | 21 | 40 | 11 | 61.88% | 0.5038 | — |
| **0.3** | **111** | **26** | **17** | **6** | **73.13%** | **0.5280** | **0.0624** |
| 0.7 | 23 | 4 | 105 | 28 | 31.88% | 0.3181 | — |

阈值 0.3 的规则实际上是“**如果模型说安全但置信度 ≤0.7，就翻成有漏洞**”（safe 的分数是 `1-confidence`；`1-confidence ≥ 0.3` 等价于 `confidence ≤ 0.7`）。它把 `macro-F1` 从 0.383 抬到 0.528，accuracy 从 38.75% 抬到 **73.13%**（仍低于常量 80%，但 macro-F1 超过常量；这是 macro-F1 与 accuracy 的取舍），MCC 只从 0.041 到 0.062。也就是说：**操作点可以修，排序能力没有修。** 模型对“是否漏洞”的置信度 AUROC 只有 **0.540**，接近随机。

这个结果是 N1 的关键设计依据：如果把 `macro-F1` 作为唯一主终点，一个简单的阈值翻转就能“成功”；但那是基准率套利，不是检测能力。N1 必须把 `MCC` 设为并列主终点，否则会重演“看起来提升了”的叙事。

### 2.3 误差结构：不是均匀地差

#### 2.3.1 按 CWE

DeepSeek direct 的召回按 CWE（多标签，一条函数可计入多个 CWE；分母是该 CWE 的正例数）：

| CWE | 正例 n | 召回 | 读法 |
| --- | ---: | ---: | --- |
| CWE-416（use-after-free） | 20 | **0.05** | 几乎全漏；生命周期/别名需要跨语句推理 |
| CWE-119（buffer overflow） | 18 | 0.39 | 一部分能看出 |
| CWE-125（out-of-bounds read） | 13 | 0.62 | 边界模式较明显 |
| CWE-787（out-of-bounds write） | 11 | 0.64 | 同上 |
| CWE-476（NULL deref） | 11 | 0.55 | 中等 |
| CWE-20（input validation） | 8 | **0.12** | 几乎全漏；需要调用者/契约 |
| CWE-399（resource management） | 8 | 0.25 | 低 |
| CWE-190（integer overflow） | 6 | **0.83** | 模式最明显 |
| CWE-264（permissions） | 5 | **0.00** | 全漏；需要权限模型 |
| CWE-200（info exposure） | 3 | **0.00** | 全漏；需要数据流/信任边界 |

这不是“模型整体弱”，而是**CWE 结构性差异**：模式匹配型 CWE（190/125/787）能到 55%–83%，生命周期类型（416）和契约型（20/264/200）接近 0。CWE-416 一项就占 20/128 正例，和 CWE-20 的 8 条合计 28/128，是低召回的主要来源之一；但不能说这两类单独决定了 0.38。N1 的 CWE 分层/检查表就是针对这个结构，而不是再换一个模型。

#### 2.3.2 按长度与结果

DeepSeek direct 的 TP/FN/FP/TN 长度（字符，中位数）：

| 结果 | n | 中位长度 | 均值 |
| --- | ---: | ---: | ---: |
| TP | 38 | 1,967.5 | 4,200 |
| FN | 90 | **971.5** | 1,780 |
| FP | 8 | 3,598 | 7,370 |
| TN | 24 | 960.5 | 3,080 |

FN 比 TP 短一半。把 test 按长度四等分：

| 长度四分位 | n | 长度范围 | 正类率 | DeepSeek accuracy |
| --- | ---: | --- | ---: | ---: |
| Q1（最短） | 40 | 57–554 | 82.5% | **25.0%** |
| Q2 | 40 | 563–1,313 | 80.0% | 40.0% |
| Q3 | 40 | 1,345–2,838 | 85.0% | 35.0% |
| Q4（最长） | 40 | 2,865–32,767 | 72.5% | 55.0% |

最短四分位正类率 82.5%，模型 accuracy 只有 25%——它在最短、最该报漏洞的片段上默认“安全”。这与长度规则的“短→漏洞”方向相反。**模型的先验不是“保守”，而是“短函数看起来没事”**；这正好与数据集先验相反。

#### 2.3.3 按项目

召回高度集中：`linux` 9/43=0.21、`Chrome` 3/28=0.11，两个项目占 71/128 正例；`OpenSC` 3/3、`gpac` 3/3 但样本少。这说明总体 macro-F1 被两个大项目主导；N1 的 cluster bootstrap 必须按项目重采样，不能按函数独立重采样。

### 2.4 根因假设（按可检验性排序）

| 假设 | 支持证据 | 反证/边界 | 对应实验 |
| --- | --- | --- | --- |
| **H1.1 操作点/先验错配**：模型过度判安全，尤其对短函数 | 只报 46/160 正；阈值 0.3 可到 0.528；最短四分位 accuracy 25% | MCC 仍 0.062，说明只修操作点不够 | N1 的 prior-calibrated 臂 |
| **H1.2 函数级标签缺上下文**：很多漏洞取决于调用者/被调用者 | FN rationale 反复出现“depends on callers”“unseen implementation”“not demonstrated from this function alone” | 没有人工标签审计，不能量化比例 | N1 的 abstention/context 臂 + 20 条 FN 审计 |
| **H1.3 长度伪相关**：正例更短，模型/基线都能利用 | 长度规则 0.533；FN 中位 971 vs TP 1,967 | 模型方向与长度先验相反，不是单纯“用长度” | N1 的长度平衡 few-shot + 长度基线 |
| **H1.4 CWE 结构差异**：416/20/264/200 需要生命周期/契约推理 | 416 召回 5%，20 召回 12.5%，264/200 为 0 | 子群小，CI 宽 | N1 的 CWE checklist/分层 |
| **H1.5 标签噪声/构造伪影**：commit 级漏洞函数不一定是函数级漏洞 | 文献 [S2][S3] 报告同类问题；本项目未做标签审计 | 没有独立标签，不能直接断言 | N1 的 20 条 FN 人工/规则审计（探索性） |

**最重要的判断**：H1.1 和 H1.3 足以解释“0.383 低于 0.533”，但解释不了“MCC 只有 0.041”。MCC 低说明**排序信号弱**，这指向 H1.2/H1.4/H1.5。下一轮如果只做阈值校准，会在 `macro-F1` 上“成功”、在 `MCC` 上失败；这不是真正的进展。

### 2.5 2024–2026 文献：为什么这不是本项目独有的异常

## 3. 最弱环节 2：pair 位置/长度混淆

### 3.1 旧报告已经给了什么

180 对 test（每对一个 vulnerable、一个 fixed），forced A/B 与 open 四分类，正/反两序：

| 模型 | 任务 | 正向 DA | 反向 DA | 交换一致 DA | 语义一致率 | 同字母率 | 顺序 McNemar p |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| DeepSeek | forced | 76.67% (138/180) | 77.78% (140/180) | **61.67%** (111/180) | 68.89% | 31.11% | 0.8939 |
| DeepSeek | open | 66.11% (119/180) | 63.89% (115/180) | **55.56%** (100/180) | 72.78% | 14.50% | 0.6076 |
| MiMo | forced | 86.67% (156/180) | 81.67% (147/180) | **74.44%** (134/180) | 80.56% | 19.44% | 0.1755 |
| MiMo | open | 66.11% (119/180) | 65.56% (118/180) | **58.33%** (105/180) | 79.44% | 8.59% | 1.0000 |

长度启发式“选较短版本，等长选 A”：单向 **74.44%**（134/180），两序同语义 **72.22%**（130/180）。DeepSeek 交换一致 61.67% **显著低于** 72.22%（McNemar p=0.0145，Holm 0.0289）；MiMo 74.44% 仅高 2.22 pp（p=0.644，不显著）。

槽位偏差：DeepSeek 正向 A 92.22% vs B 61.11%（31.11 pp），反向 93.33% vs 62.22%（31.11 pp）——偏差跟着 A 槽走，不是“先呈现”效应。MiMo 正向 4.44 pp，反向 21.11 pp。

开放四分类把位置偏差压到不显著（A/B 分侧差 p=0.115–0.753），但弃权率 17.22%–22.22%；按“恰好一个版本有漏洞”计，DA 只有 63.89%–66.11%；只看 committed 输出则 77.18%–84.40%。

旧报告的正确结论已经写了“单序 86.67% 不能作为最终能力”。但它**没有**回答：**在控制长度方向之后，模型还有多少信号？** 这是本节的核心。

### 3.2 本次复核：按“长度差方向”分层，而不是按“长度差幅度”匹配

#### 3.2.1 三种长度方向

180 对按 `len(vulnerable)` vs `len(fixed)` 分：

| 方向 | 对数 | 长度启发式（选较短） | 含义 |
| --- | ---: | ---: | --- |
| 漏洞更短（vshorter） | 130 | **100% 对** | 长度启发式天然正确 |
| 修复更短（fshorter） | 44 | **0% 对** | 长度启发式天然错误；这是“干净子集” |
| 等长（tie） | 6 | 取决于 tie 规则 | 样本太少，不作主证据 |

关键：**fshorter 的 44 对是唯一能区分“语义判断”与“选较短”的子集**。在这个子集上，长度规则是 0%，任何高于随机的准确率都只能来自代码语义（或位置/其他伪影）。

#### 3.2.2 模型在 fshorter 上的表现

| 模型 | 正向 DA | 反向 DA | 两序都对（交换一致） | vs 25% 随机一致 | vs 50% |
| --- | ---: | ---: | ---: | ---: | ---: |
| DeepSeek | 25/44 = **56.8%** | 24/44 = **54.5%** | 15/44 = **34.1%**（95% CI 21.9–48.9） | p=0.166 | p=0.049（低于 50%） |
| MiMo | 28/44 = **63.6%** | 27/44 = **61.4%** | 20/44 = **45.5%**（95% CI 31.7–59.9） | **p=0.0045** | p=0.652 |

读法：

- **交换一致 DA 的随机基线是 25%**（两序独立随机、都要对），不是 50%。MiMo 45.5% 显著高于 25%，说明它有**弱但真实**的内容信号；DeepSeek 34.1% 不显著高于 25%。
- 但两者都远低于 50% 的“可用”线；MiMo 的 45.5% 仍然不能支持“跨版本推理”的主张。
- 正向/反向单序 56.8%–63.6% 看起来“高于 50%”，但两序一致后只剩 34.1%–45.5%，说明单序的一部分是顺序噪声/槽位。

#### 3.2.3 对照：vshorter 子集

| 模型 | 两序都对（vshorter, n=130） | 长度规则 |
| --- | ---: | ---: |
| DeepSeek | 93/130 = **71.5%** | 100% |
| MiMo | 111/130 = **85.4%** | 100% |

在长度规则天然正确的 130 对上，模型仍然低于 100%；MiMo 的 85.4% 与它的总体 74.44% 相比更高，说明它的“正确”主要集中在长度方向正确的对。**模型不是超过长度规则，而是跟随长度规则，且在 15% 的对上跟错。**

#### 3.2.4 方向平衡后的 88 对

把 44 个 fshorter 与 44 个 vshorter 按“相对长度差”做最近邻匹配（不放回），得到一个**方向平衡**的 88 对子集；在这个子集上，长度启发式按构造是 50%：

| 模型 | 交换一致 DA（88 对） | 95% CI | vs 50% | 读法 |
| --- | ---: | --- | ---: | --- |
| DeepSeek | 42/88 = **47.7%** | [37.6%, 58.0%] | p=0.749 | 与随机不可区分 |
| MiMo | 56/88 = **63.6%** | [53.2%, 72.9%] | **p=0.0138** | 略高于 50%，约 +13.6 pp |

这是本项目目前**最干净的 pair 信号**：控制长度方向后，MiMo 仍有 63.6%，DeepSeek 没有。但它仍是事后构造的子集，不能当作正式结果；N2 要用预注册的长度中性化/方向平衡设计来复现它。

#### 3.2.5 为什么“10% 长度匹配”不够

旧文档建议构造 `|Δchars|/max ≤5%` 的匹配子集。本次复核发现这个建议在本数据上**不可行**：

| 匹配阈值 | n | vshorter | fshorter | tie | 长度启发式 |
| --- | ---: | ---: | ---: | ---: | ---: |
| ≤5% | 107 | 68 | 33 | 6 | 63.6%–69.2%（tie 规则端点） |
| ≤10% | 144 | 101 | 37 | 6 | **72.92%**（项目口径） |
| 精确等长 | 6 | 0 | 0 | 6 | 无意义 |

10% 匹配子集的方向构成仍是 **101:37**；长度启发式 72.92% ≈ 101/144 的 vshorter 比例。**匹配幅度没有控制方向**：修复补丁通常只加几行检查/释放，长度差很小，但方向仍然是“修复更长”。所以“匹配到 10%”并没有让长度规则退化到 50%，只是把它的优势从 74.44% 降到 72.92%。

**正确的控制是方向平衡或长度中性化，不是幅度匹配。** 这是本节对旧 E2 建议的修正，也是 N2 的设计依据。

### 3.3 根因

| 假设 | 支持证据 | 边界 |
| --- | --- | --- |
| **H2.1 修复版本系统性更长** | 130/180 对漏洞更短；10% 匹配后仍 101:37 | 这是数据构造事实，不是模型偏差；不能靠“让模型忽略长度”的指令消除 |
| **H2.2 模型跟长度方向走** | vshorter 71.5%/85.4%；fshorter 34.1%/45.5%；DeepSeek 交换一致低于长度规则 | MiMo 在 fshorter 有弱信号，说明不全是长度 |
| **H2.3 槽位偏好** | DeepSeek A 92.22% vs B 61.11%，两序都约 31 pp | 强制二选一放大槽位；开放四分类把偏差压到不显著，但用弃权换覆盖 |
| **H2.4 强制二选一改变任务** | forced 76.67/86.67 vs open 63.89–66.11；open 弃权 17–22% | 不能把 forced 与 side-wise 直接比较；forced 的“高”有一部分是任务框架 |
| **H2.5 证据不足** | 开放条件下 both/neither 17–22%；rationale 常写“both similar” | 模型没有可引用的差异证据；需要 evidence-first/差异行提示 |

### 3.4 2024–2026 文献

| 文献 | 与本环节的关系 | 关键结论 |
| --- | --- | --- |
| **Judging the Judges** [S7]，IJCNLP-AACL 2025，DOI:10.18653/v1/2025.ijcnlp-long.18 | 位置偏差的测量 | 15 个 judge、22 个任务、15 万+ 实例；位置偏差不是随机，随 judge/task 变化；**受 prompt 组件长度影响较弱，受候选质量差影响更强**。支持“必须 swap + 报 position consistency”，但不能只归因于长度 |
| **Bias in the Loop** [S8]，arXiv:2604.16790，2026 | 代码 pair 的 prompt 偏差 | code LLM-judge 对 prompt 呈现线索高度敏感；语义保持的扰动可改变判定；偏置可大到改变任务级结论。支持“长度中性化 + 盲评 + 双序” |
| **Top Score on the Wrong Exam** [S3] | 伪相关 | 词数/词频单独可高分；pair 的“选较短”是同一类伪相关。支持“方向分层”，而不是只看总体 DA |

### 3.5 本节结论

1. **单序 76.67%/86.67% 不能作为 pair 能力**；交换一致 61.67%/74.44% 已经低很多。
2. **长度方向是主要混淆**：130/180 对漏洞更短；方向平衡后，DeepSeek 47.7%（随机），MiMo 63.6%（弱信号）。
3. **10% 幅度匹配无效**；必须方向平衡或长度中性化。旧 E2 的“5% 匹配 ≥100 对”在本数据上不可行，应改写。
4. **MiMo 是唯一有弱信号的模型**；N2 应做 model-specific 预注册：MiMo ≥60% 且 >50% 至少 10 pp 才算成功，DeepSeek ≥55% 才算成功；预期 DeepSeek ≤50%。如果 MiMo 在中性化后仍 ≥60%，才能写“有限的语义信号”；否则撤回 pair 主张。

## 4. 最弱环节 3：CodeQL 的 23 个假阳性

### 4.1 旧报告已经给了什么

Juliet CWE-401 test 140，端到端（`compile_error` 按未报泄漏计）：

| 工具 | TP | FP | TN | FN | P | R | macro-F1 | MCC |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Clang SA 22.1.8 | 53 | 0 | 70 | 17 | 1.0000 | 0.7571 | **0.8768** | **0.7805** |
| CodeQL 2.27.4（并集） | 68 | 23 | 47 | 2 | 0.7473 | **0.9714** | 0.8173 | 0.6739 |

CodeQL 的分查询（端到端）：

| 查询 | TP | FP | TN | FN | P | R | MCC |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `cpp/memory-never-freed` | 46 | 0 | 70 | 24 | **1.0000** | 0.6571 | 0.6995 |

CodeQL 官方 CWE 覆盖文档把 `memory-may-not-be-freed` 列为 CWE-401 相关查询 [S22]；它和 `memory-never-freed` 是同一 CWE 下的高召回/高精度两档。

旧报告的正确结论：CodeQL 用召回换精确率，23 个 FP 全是 C++ good；不能写成“优于 Clang”。但它**没有**回答：这 23 个 FP 是随机的，还是可命名的模式？如果是后者，能不能在不损失 TP 的情况下过滤？这是本节的核心。

### 4.2 本次复核：23 个 FP 的四个模式

#### 4.2.1 全部来自 may 查询，全部是 C++ good

- 23/23 FP 来自 `cpp/memory-may-not-be-freed`；`cpp/memory-never-freed` 是 **0 FP**。
- 23/23 FP 是 C++ good；test 140 的 C 语言 58 个单元是 29 TP / 0 FP / 29 TN / 0 FN（200 单元全量是 44/0/44/0），C 上满分。
- 23 个 FP 分布在 22 个 family，几乎一个 family 一个；不是某个 family 的重复。

按 Juliet 流变体：

| 变体 | FP 数 | 代码形态 | CodeQL 为什么误报 |
| --- | ---: | --- | --- |
| `_33__good` | **15** | `char *&dataRef = data;` 后，在块内 `char *data = dataRef; free(data);` | 引用别名 + 变量遮蔽；may 查询没有把 `free(dataRef)` 识别为对原分配的释放 |
| `_22__good` | 3 | 分配后把指针传给 `goodB2G2Sink(data)`，sink 内释放 | 过程间 sink 摘要缺失；may 查询把“指针逃逸”当成“可能不释放” |
| `_72__good` | 3 | 指针插入 `std::vector`，再把 vector 传给 sink，sink 内释放 | STL 容器逃逸 + sink 摘要缺失 |
| `_54__good` | 2 | 指针传给 `goodB2GSink_b(data)`，sink 内释放 | 同 `_22` |

这些不是“模型/工具随机犯错”，而是 **CodeQL may 查询的建模边界**：它要找“函数可能提前返回而未释放”，对引用别名、变量遮蔽、过程间 sink、STL 容器这些“释放发生在别处”的形态天然保守。

#### 4.2.2 may 查询的 TP 与 FP 混在同一批变体里

| 变体 | may TP | may FP |
| --- | ---: | ---: |
| `_01__bad` | 8 | 0 |
| `_33__bad` | 5 | 0 |
| `_18__bad` | 3 | 0 |
| `_72__bad` | 3 | 0 |
| `_54__bad` | 1 | 0 |
| `_09__bad` | 1 | 0 |
| `_22__bad` | 1 | 0 |
| `_33__good` | 0 | 15 |
| `_22__good` | 0 | 3 |
| `_72__good` | 0 | 3 |
| `_54__good` | 0 | 2 |

所以“按变体一刀切”不行：`_33` 既有 5 个 TP 也有 15 个 FP；`_72` 3 TP / 3 FP；`_22` 1 TP / 3 FP；`_54` 1 TP / 2 FP。必须看**代码内的释放证人**，不能看文件名。

#### 4.2.3 三个简单过滤器的结果：两个失败，一个是部分成功

**(a) `code_flows` 过滤。** 45 个 may hit（22 TP + 23 FP）**全部 `code_flows=0`**。`code_flows>=1` 会把 22 个 may TP 和 23 个 FP 一起删掉，退化成 never-only（46/0/24/70）。这不是过滤，是放弃 may 查询。

**(b) 词法 `free`/`delete` 计数过滤。** 统计目标文件里 `free(` + `delete` 的次数，只在次数 ≤ 阈值时保留 may：

| 阈值 | TP | FP | FN | TN | 读法 |
| ---: | ---: | ---: | ---: | ---: | --- |
| ≤0 | 46 | 0 | 24 | 70 | 等于 never-only；丢掉全部 may TP |
| ≤1 | 51 | 8 | 19 | 62 | 保留 5 个 may TP，仍 8 FP |
| ≤2 | 61 | 23 | 9 | 47 | 保留 15 个 may TP，FP 不变 |
| ≤3 | 67 | 23 | 3 | 47 | 几乎回到并集 |

TP 和 FP 都普遍含 `free`/`delete`（例如 `_33` 的 good 与 bad 都有 2 个 `free(`；good 的释放写在别名上），词法计数无法区分。

**(c) 语言过滤（部分成功）。** may 查询只在 C 上用：14 TP / 0 FP；加 never 后 **60 TP / 0 FP / 10 FN / 70 TN**，P=1.000、R=0.857、macro-F1≈0.928、MCC≈0.866。它丢掉 8 个 C++ may TP（22 个 may TP 中 14 个在 C、8 个在 C++），但删掉全部 23 个 C++ FP。这不是“无效”，而是一个**高精度操作点**；N3 应把 C-only 作为第三个控制臂。

#### 4.2.4 上界与可行目标

| 方案 | TP | FP | FN | TN | P | R | macro-F1 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| never-only | 46 | 0 | 24 | 70 | 1.000 | 0.657 | 0.823 |
| may C-only（never + may 在 C） | 60 | 0 | 10 | 70 | 1.000 | 0.857 | ≈0.928 |
| may 并集（现状） | 68 | 23 | 2 | 47 | 0.747 | 0.971 | 0.817 |
| 理想证人过滤（FP 全删，TP 全留） | 68 | 0 | 2 | 70 | **1.000** | **0.971** | **≈0.986** |
| 证人过滤丢失一半 may TP | 57 | 0 | 13 | 70 | 1.000 | 0.814 | ≈0.906 |
| 删 50% FP、丢 10% may TP | ≈66 | ≈12 | ≈4 | ≈58 | ≈0.846 | ≈0.943 | ≈0.885 |

“理想证人过滤”不是预测，是上界：它说明**只要 FP 能被删掉而不伤 TP，CodeQL 可以同时做到 P=1.0、R=0.971**。这在 Juliet 上是 23 个可命名模式的问题，不是无底洞。C-only 的 0.928 是一个**已经可达的强基线**；N3 要证明证人过滤能在此基础上多回收 8 个 C++ TP，而不引入 23 个 FP。注意：如果证人过滤只能保住一半 may TP（0.814），反而**低于** C-only 的 0.857；所以“不能超过 C-only”应作为 N3 的提前停止线。N3 的现实目标不是 0.986，而是 `P≥0.90, R≥0.90` 或 `P≥0.85, R≥0.95`。

### 4.3 根因

| 假设 | 支持证据 | 边界 |
| --- | --- | --- |
| **H3.1 may 查询的过程内建模不足** | [S21] 的查询语义是“函数可能提前返回而未释放”；`_22/_54/_72` 的释放在 sink | 不是查询 bug，是 may 分析的保守性；要补 sink 摘要 |
| **H3.2 别名/遮蔽未跟踪** | `_33` 的 `T*&` + 块内同名变量；15 个 FP | 需要轻量别名/引用分析；不是词法问题 |
| **H3.3 STL 容器逃逸** | `_72` 的 `vector<char*>`；3 FP / 3 TP | 需要容器元素逃逸建模 |
| **H3.4 Juliet C++ good 的构造** | 23 FP 全在 4 个 good 变体；C 0 FP | 这是 benchmark 结构，不是真实项目分布；外推需谨慎 |
| **H3.5 单 TU/每单元建库** | CodeQL 每单元单独建库；sink 在同文件 | 真实项目的跨文件 sink 会更难；Juliet 的 0 FP 不能外推 |

**关键判断**：23 个 FP 的根因是**“释放发生在别名/sink/容器里”**，而 may 查询只看当前函数的退出路径。解决它需要**证人**（witness）：证明“这个分配在所有路径上都被释放”。这可以是静态的（别名 + sink 摘要），也可以是 LLM 辅助的（给出分配点、sink 调用、释放点，要求指出缺失路径）；但**不能只给 LLM 原始代码 + “may not be freed”**，因为它没有 trace 可依据。

### 4.5 本节结论

1. **23 个 FP 全部来自一个查询、全是 C++ good、集中在 4 个变体**；这是一个边界清晰的工程问题，不是“CodeQL 不行”。
2. **never-only 是完美精确率、0.657 召回；may C-only 是 1.000/0.857；may 并集是 0.747/0.971。** 正确报告方式是**三个操作点**，不是一个“更好的工具”。
3. **`code_flows` 和词法 free/delete 过滤器不行；语言过滤是部分成功**（C-only 0.928），但它只是绕开 C++，没有解决 8 个 C++ may TP vs 23 个 FP。真正的修复仍需要别名/sink 证人。
4. **N3 的成功先验是中等偏高**：23 个 FP 可命名、可定位；但 LLM 单独裁决的先验低（没有 trace），应优先做静态证人，LLM 只做未决项。

## 5. 最弱环节 4：验证器误撤 TP

### 5.1 旧报告已经给了什么

`evidence_verify` 对第一遍证据提示的 160 条测试函数做二次验证；只验证正例，负例不动。四臂：DeepSeek 自审、MiMo 审 DeepSeek、MiMo 自审、DeepSeek 审 MiMo。主口径 fail-closed（未明确 sustain 即撤销）。

| 臂 | 撤销总数 | 撤销 TP | 撤销 FP | 撤销精确率 | 正例 FP 基准率 | 超几何 Holm p |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |

旧报告的正确结论：二次验证降低 macro-F1；撤销不偏向 FP；同预算随机撤销的期望 macro-F1（0.4176/0.4201/0.4067/0.4067）全部高于验证器。它**没有**回答：验证器到底是“找不到 FP”还是“撤得太多”？如果是后者，是否存在一个可救的排序信号？这是本节的核心。

### 5.2 本次复核：验证器不是“找不到 FP”，而是“几乎全撤”

#### 5.2.1 两个臂把 11/11 个 FP 都撤了

`deepseek_self` 和 `mimo_cross` 的 `fp_correction_rate=1.0`：11 个 FP 全撤。但同时：

- DeepSeek 自审：撤了 43/49 个 TP（87.8%），只留 6 个；
- MiMo 跨模型：撤了 40/47 个 TP（85.1%），只留 7 个。

这不是“选择性撤销”，而是“**高召回地撤销所有正例**”。精确率 20%–22% 只是正例中 FP 基准率 18%–19% 的影子；超几何检验不显著（Holm p≥0.8367）。

另外两个臂（DeepSeek 跨模型、MiMo 自审）撤得少一些（26/21），但精确率也只有 23.1%/14.3%，仍然不高于基准率。

#### 5.2.2 撤销类型：`insufficient_evidence` 占 67%–71%

| 臂 | 撤销总数 | `insufficient_evidence` | 占比 | 其中 TP/FP | 其余具体类型 |
| --- | ---: | ---: | ---: | --- | --- |
| DeepSeek 自审 | 54 | 36 | 66.7% | 29/7 | guard 11（8/3）、no_reachable 3（3/0）、not_security 4（3/1） |
| DeepSeek 跨模型 | 26 | 18 | 69.2% | 14/4 | guard 5（3/2）、no_reachable 1（1/0）、not_security 1（1/0）、mislocated 1（1/0） |
| MiMo 自审 | 21 | 15 | 71.4% | 12/3 | guard 3（3/0）、no_reachable 1（1/0）、not_security 1（1/0）、mislocated 1（1/0） |
| MiMo 跨模型 | 51 | 34 | 66.7% | 27/7 | guard 11（9/2）、no_reachable 2（1/1）、not_security 3（3/0）、mislocated 1（0/1） |

`insufficient_evidence` 的语义是“函数内看不出攻击者控制，所以不足以成立”。但第一遍证据提示本来就是在**函数级**输入上做的；调用者/攻击者控制通常不在函数内。于是验证器把“缺少上下文”误读成“漏洞不成立”，把大量 TP 撤掉。这是一个**prompt 语义 bug**，不是模型不会判。

具体类型的 precision 反而较高：`guard_present` 四臂为 72.7%/60%/100%/81.8%（n=11/5/3/11）；`no_reachable_flow` 为 100%/100%/100%/50%（n=3/1/1/2）。但这些具体撤销每臂只有 6–18 个，覆盖很低；真正把 macro-F1 拉低的是 36/18/15/34 个 `insufficient_evidence` 撤销。**验证器不是没有具体机制，而是具体机制太少，fail-closed 又用 `insufficient_evidence` 把 TP 一起撤了。**

#### 5.2.3 验证器的置信度对 FP/TP 没有排序信号，甚至是反向的

用验证器输出的 `confidence` 作为“应撤销”的分数，计算 FP vs TP 的 AUROC（FP 为正类）：

| 臂 | FP n | TP n | confidence AUROC（FP vs TP） | `evidence_check` AUROC |
| --- | ---: | ---: | ---: | ---: |
| DeepSeek 自审 | 11 | 49 | **0.400** | 0.500 |
| DeepSeek 跨模型 | 10 | 48 | **0.455** | 0.500 |
| MiMo 自审 | 11 | 46 | **0.282** | 0.500 |
| MiMo 跨模型 | 11 | 47 | **0.304** | 0.500 |

四个臂都低于 0.5（0.455 也低于 0.5）；也就是说，验证器对 TP 的置信度反而更高，或者至少没有把 FP 排前面。`evidence_check`（supported/partially/unsupported）在所有臂几乎常量，AUROC=0.5。

这个结果比“post macro-F1 下降”更致命：**即使把 fail-closed 改成阈值扫描，也救不回来**，因为分数没有排序。N4 如果只用“让验证器更谨慎”或“调阈值”，会重复失败；必须换证据来源（代码事实/外部 oracle），而不是换措辞。

#### 5.2.4 具体反驳仍然整体为负

旧报告的事后 `refutation-only` 规则（只撤 `verdict=retract` 且 `rebuttal_type != insufficient_evidence`）仍然让 macro-F1 下降 0.0475/0.0148/0.0371/0.0422，Holm p=0.0927/0.3438/0.0625/0.0981。方向一致为负，只是幅度变小。

两个验证器的一致性也很低：Cohen κ 0.044（DeepSeek 正例）、0.151（MiMo 正例）。这说明“让另一个模型再审一遍”没有提供独立证据。

### 5.3 根因

| 假设 | 支持证据 | 边界 |
| --- | --- | --- |
| **H4.1 fail-closed 语义把“上下文不足”当“撤销”** | `insufficient_evidence` 占 67%–71%；TP 撤销主要是这一类 | 这是可修的 prompt bug；但修完后具体类型只剩 6–18 个，覆盖很低 |
| **H4.2 验证器没有 FP/TP 排序信号** | confidence AUROC 0.28–0.46；evidence_check 常量 | 这不是阈值问题；需要外部证据 |
| **H4.3 测试集已被第一遍使用** | `analysis_status=exploratory_post_hoc_test_seen` | 不能独立确认；必须换 holdout |
| **H4.4 验证器缺少攻击者控制/调用者上下文** | rationale 反复说“not demonstrated from this function alone” | 与 H1.2 同源；函数级任务的结构性问题 |
| **H4.5 具体机制覆盖低，不是精度低** | `guard_present` precision 60%–100%，但每臂只有 3–11 个；`no_reachable_flow` n=1–3 | 即使只看具体类型，也只能做小覆盖；不能提升总体 macro-F1 |

**关键判断**：验证器的失败有两层。表层是 `insufficient_evidence` 语义（可修）；深层是**没有排序信号**（难修）。下一轮必须把两层分开：先修语义，再看 AUROC；如果 AUROC 仍 ≤0.55，就不要再用“二次验证提升检测”的框架，改用外部 oracle（编译/PoC/静态证人）。

### 5.4 2024–2026 文献

| 文献 | 与本环节的关系 | 关键结论 |
| --- | --- | --- |
| **LLMs Cannot Self-Correct Reasoning Yet** [S17]，ICLR 2024，arXiv:2310.01798 | 无外部反馈的自纠正 | 没有外部反馈时，LLM 的 intrinsic self-correction 不能可靠提升推理，甚至会让性能下降；支持“验证器不能只靠自审” |
| **When Do LLMs Admit Their Mistakes?** [S18]，arXiv:2505.16170，2025 | retraction 机制 | LLM 有能力 retract，但**很少自发做**；retraction 与内部 belief 相关，belief 又常与参数知识背离；支持“fail-closed 的强制撤销不是 belief-driven，因而不可靠” |
| **Are LLMs reliable code reviewers?** [S19]，arXiv:2603.00539，2026 | 代码审查的过度纠正 | LLM 经常把**正确**实现判成不合规/有缺陷；**更详细的 prompt（要求解释/修复）反而提高误判率**；提出 Fix-guided Verification Filter：把模型提出的 fix 当可执行反事实证据，用测试验证原实现与修改实现 |
| **Bias in the Loop** [S8]，arXiv:2604.16790，2026 | 代码 judge 的 prompt 偏差 | prompt 呈现线索可系统性改变判定；支持“预注册 + 盲评 + 双序”，而不是事后加一段“请更严格” |

**综合读法**：

- [S17][S18] 解释为什么“让模型再审一遍”不可靠：没有外部信号时，模型没有稳定的 belief；强制 fail-closed 只是把操作点推向撤销。
- [S19] 给了最具体的修复方向：**不要问“它真的有漏洞吗”，而问“如果修，最小 fix 是什么；这个 fix 是否已经在代码里”**。如果 fix 已存在，原判是 FP；如果不存在，原判更可能是 TP。这把主观判断变成可检查的代码事实。
- [S19] 同时警告：更详细的解释要求会提高误判率；所以 N4 不能靠“更长的 rubric”，要靠**外部可执行检查**。

### 5.5 本节结论

1. **验证器不是“找不到 FP”**：两个臂把 11/11 个 FP 都撤了；问题是它同时撤了 40–43 个 TP。
2. **`insufficient_evidence` 是主因**（67%–71%），但修完它之后具体反驳太少，覆盖不足。
3. **置信度没有排序信号**（AUROC 0.28–0.46），所以阈值扫描救不了；必须换证据。
4. **N4 应把主终点改成 AUROC/PR 曲线**，而不是单一撤销率；并用 fix-guided 外部检查，而不是再让模型“更严格”。

## 6. 最弱环节 5：动态分析没有覆盖率

### 6.1 旧报告已经给了什么

`dynamic_enhanced` 对 Juliet CWE-401 test 140（70 bad / 70 good）跑三种模式：

- `default`：复现旧 ASan/LSan（`use_stacks=0:use_registers=0`）。
- `realloc_fail`：链接期 `-Wl,--wrap=realloc`，只让第一个收到非 NULL 指针的 `realloc` 返回 NULL。
- `nogobal`：`LSAN_OPTIONS=use_globals=0`，关闭全局根。

判定：任一适用模式出现“归因到本单元源文件”的泄漏即 leak；未归因的 glibc/libstdc++ 泄漏不计入。

| 模式 | 适用单元 | bad 归因泄漏 | good 归因泄漏 | bad 原始泄漏 | good 原始泄漏 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `default` | 140 | 58 | 0 | 58 | 0 |
| `realloc_fail` | 14 | 7 | 0 | 7 | 0 |
| `nogobal` | 140 | 63 | 0 | 70 | **70** |

并集：**70 TP / 0 FP / 70 TN / 0 FN**，`coverage=1.000`。12 个旧 ASan 不可观测的 bad 全部有证据：7 个 `malloc_realloc` 由 `realloc` 失败注入、5 个 `_68` 由关闭 LSan 全局根解决。good 0 FP。旧 ASan `default` 与旧运行 140/140 一致；并集相对旧 ASan/Valgrind 128/140 的差异恰好是 12 个 bad。

旧报告的正确结论：动态增强把 12 个不可观测 bad 变成可复核证据；`clean` 仍只是单路径观测，不是无泄漏证明。但它**没有**回答：`coverage=1.000` 到底是什么覆盖率？`clean` 的分母里有多少代码真的执行过？`nogobal` 的 0 FP 是原始 0 FP 还是归因后 0 FP？这是本节的核心。

### 6.2 本次复核：`coverage=1.000` 是“判定覆盖”，不是“代码覆盖”

#### 6.2.1 `coverage` 字段的语义

`dynamic_enhanced/dyne/metrics.py` 的 `coverage` 定义是：

```
coverage = (len(rows) - undecided) / len(rows)
```

即“140 个单元中有多少个给出了 leak/clean 判定”。这是**决策覆盖率**，不是行覆盖率、分支覆盖率或路径覆盖率。旧 README 的“coverage 140/140 = 1.000”容易被读成“代码覆盖 100%”，这是误读。

#### 6.2.2 没有覆盖率插桩

检查 140 个单元的 `build` 命令：编译参数是 `-fsanitize=address -fno-omit-frame-pointer -O0 -g`，**没有** `--coverage`、`-fprofile-instr-generate`、`-fprofile-arcs`、`gcov`、`llvm-cov`。`results_units.jsonl` 里也没有 coverage 字段。结论：

- **0/140 单元有行覆盖率；0/140 有分支覆盖率。**
- 每个模式只跑 **1 个输入**（Juliet 的 `INCLUDEMAIN` harness 固定路径）。
- 三种模式是 3 次单路径运行，不是 3 条独立路径的系统探索。

#### 6.2.3 原始泄漏 vs 归因泄漏

`nogobal` 下 **70/70 good 都有原始泄漏**，但 0 个被归因到单元源码；`default` 下 0/70 good 原始泄漏。也就是说：

- `nogobal` 的 0 FP 完全依赖**归因规则**：只看分配栈第一个落在非工具链位置的源码帧。
- 如果归因规则错一条，`nogobal` 的 FP 可能从 0 变成 70；这是一个**二值风险**，不是“0 FP 很稳”。
- 正确的写法是“**0 attributed FP**”，不是“0 FP”；原始泄漏与归因泄漏必须分列。

#### 6.2.4 12 个“条件可观测”单元

`conditionally_observable=true` 的 12 个单元：

- 7 个 `malloc_realloc`：只有第一次非 NULL `realloc` 失败时才泄漏；`default` 下 `realloc` 成功，观测不到。
- 5 个 `_68`：指针写入全局变量；LSan 默认把全局根视为 reachable；`use_globals=0` 才报。

这 12 个是**真实的进步**：它们把“标签 bad 但 LSan 看不到”拆成了可解释的机制。但也要看到：

- `realloc_fail` 只适用于 14 个单元（7 bad + 7 good），不是全量；它是**定向故障注入**，不是通用动态分析。
- `nogobal` 改变了 LSan 的根集语义；它报的“leak”是“在关闭全局根后不可达”，不一定是工程意义上的泄漏。good 单元的 70/70 原始泄漏就是证据。
- 并集 140/140 是**三种定向模式的 oracle 并集**：评测者知道哪种模式适合哪个单元。部署时跑三种模式是合法的，但“100%”应写成“在这个 Juliet 子集上，三种定向模式的并集覆盖了全部 70 个 bad”，不能写成“动态检测 100%”。

#### 6.2.5 全量 3,316 的 190 个 FN 已经暴露了覆盖率问题

旧全量动态（3,316 case）的 190 个 FN：

| 机制 | FN 数 | 说明 |
| --- | ---: | --- |
| `malloc_realloc_*` | 108 | 只有 `realloc` 失败才泄漏；默认运行不失败 |
| Juliet 流变体 45/68 | 68 | 指针写入全局变量；LSan 默认 still reachable |
| Juliet 流变体 12 | 14 | `globalReturnsTrueOrFalse()` 随机分支；本次运行走到非泄漏路径 |

14 个随机分支 FN 是**单输入/单路径**的直接证据：同一单元换一个随机种子就可能泄漏。test 140 里没有这 14 个（或已被其他模式覆盖），但机制存在；G0 的多输入要求就是针对它。

### 6.3 根因

| 假设 | 支持证据 | 边界 |
| --- | --- | --- |
| **H5.1 无代码覆盖率** | 编译命令无 coverage 标志；metrics 的 coverage 是判定覆盖 | 不是“覆盖率 100%”，是“判定覆盖率 100%” |
| **H5.2 单输入 harness** | 每模式 1 个输入；14 个随机分支 FN | 需要多 seed/多输入 |
| **H5.3 LSan 全局根语义** | `nogobal` 70/70 good 原始泄漏；`default` 0 | 0 FP 依赖归因，不是工具本身 |
| **H5.4 归因规则未审计** | 只看分配栈第一帧；未做人工抽样复核 | 需要 20 个单元的手工栈检查 |
| **H5.5 模式并集是 oracle** | 12 个单元各由特定模式解决；`realloc_fail` 只适用 14 个 | 部署可跑三模式，但不能外推为通用 100% |

### 6.4 2024–2026 文献

| 文献 | 与本环节的关系 | 关键结论 |
| --- | --- | --- |
| **RBZZER** [S15]，Computers, Materials & Continua 84(3):4601–4625，2025，DOI:10.32604/cmc.2025.065162 | 定向 fuzzing 找内存泄漏 | 用轻量静态分析标风险函数/风险区，定向 fuzzing；比 AFL/AFLGo/AFLfast/PerfFuzz 等发现更多泄漏（作者报告至少 +112%）。说明“泄漏检测需要定向路径探索”，不是单输入 sanitizer |
| **Data Coverage for Guided Fuzzing** [S16]，USENIX Security 2024 | 覆盖率不等于代码覆盖 | 代码覆盖只反映程序结构的一小部分；常量数据里的约束/自动机/DSL 需要 data coverage；在 OSS-Fuzz 上发现 28 个新 bug。支持“行覆盖/分支覆盖是必要但不充分” |
| **AddressWatcher** [S14]，IEEE TSE 50(9):2398–2411，2024，DOI:10.1109/TSE.2024.3438119 | sanitizer 的泄漏定位 | 把分配/释放/读写与 sanitizer 结合，定位泄漏修复；把 leak 定义为“不可从栈/全局到达”。直接对应 `nogobal` 的根集语义与归因规则 |
| **Lightweight and Modular Resource Leak Checking** [S13]，STTT 2025 | 静态资源泄漏 | 模块化别名/资源分析；可作为“哪些 free 站点必须执行”的静态清单，辅助覆盖率门禁 |

**综合读法**：

- [S15][S16] 说明：单输入 sanitizer 的 `clean` 只是“这条路径没看到”，不是“没有泄漏”；需要定向路径/多输入。
- [S14] 说明：LSan 的 leak 定义依赖根集；`nogobal` 改变语义，必须把原始泄漏与归因泄漏分开。
- [S13] 可以给 G0 提供“必须执行的 free/delete 站点”清单，而不是只看行覆盖率。

### 6.5 本节结论

1. **`coverage=1.000` 是判定覆盖率，不是代码覆盖率**；项目目前没有行/分支覆盖率。
2. **`nogobal` 的 0 FP 是“0 attributed FP”**；70/70 good 原始泄漏说明归因规则在承重。
3. **140/140 是三种定向模式的并集**，不是通用动态检测器；12 个单元是真实进步，但外推要限定。
4. **G0 必须先做**：没有覆盖率，动态章节的 `clean` 不能写成 TN；这会直接威胁“动态 0 FP”的结论。

- 每个实验只回答一个“是/否”问题；不要把“检测 + 定位 + 修复 + 成本”塞进一个 run。

### 7.1 N1：Tier A 先验校准 + CWE 分层 + 长度锚定

#### 7.1.1 要回答的问题

> 0.383 的低 macro-F1，主要是**操作点/先验**问题，还是**排序/上下文**问题？如果是前者，一个预注册的校准规则能否在 `MCC` 上也提升？如果是后者，CWE 分层/弃权能否把 CWE-416/20 的召回拉起来？

#### 7.1.2 设计

数据：`splits/test_detection_160.json`（160 条，128 V / 32 NV）与 `splits/dev_detection_40.json`（40 条，32 V / 8 NV）。dev 只用于阈值/示例选择；test 只看一次。

四个臂（每个模型都跑，或先跑 DeepSeek，MiMo 只跑最优臂）：

| 臂 | Prompt/规则 | 目的 |
| --- | --- | --- |
| `A0 direct` | 复用现有 direct（控制） | 基线 |
| `A1 prior-calibrated` | 在 system prompt 中声明该基准的正类率约 80%，要求输出 `P(vulnerable)` 而不是只输出布尔；在 dev 上选阈值，使 balanced accuracy 最大（dev 负例只有 8 个，MCC 方差大；MCC 只作报告） | 修操作点；区分“阈值”与“排序” |
| `A2 cwe-checklist` | 给一个 4 项检查表：生命周期（alloc/free/alias/escape）、边界、整数、输入契约；要求引用具体行；若函数内缺少判定所需上下文，输出 `undecidable` | 针对 CWE-416/20/264/200；把“缺上下文”显式化 |
| `A3 length-balanced few-shot` | few-shot 示例按长度分层（短/长 × 正/负各半），并在 prompt 中说明“长度不是漏洞信号”；示例只来自 dev | 去掉长度先验；看 `MCC` 是否上升 |

**为什么不加“context”臂**：现有 `context` 字段有数据伪影（40/40 负例是同一个全 null 字符串，160/160 正例含 `array(...)` 注释载荷），用它做输入会泄漏标签。N1 不做“伪上下文”；`A2` 的弃权是更诚实的替代。

**主终点**：`MCC`。**并列主终点**：`macro-F1`。
**次终点**：固定 `FPR≤25%` 时的 recall；CWE-416 与 CWE-20 的召回；弃权率；与长度规则（0.5331）的 Δ；与常量基线（0.4444）的 Δ；成本。

**判定规则**：

- `MCC≥0.15` 且 `macro-F1≥0.53` → **能力提升**（相对 direct 0.041/0.383，相对长度规则 0.067/0.533）。
- 固定 `FPR≤25%` 时 `recall≥0.50` 且 `MCC≥0.10` → **操作点成功**；不是能力提升，报告要单列。
- `macro-F1≥0.53` 但 `MCC≤0.07` → **只算操作点成功**；报告必须写“基准率套利”，不能写“检测能力提升”。
- `MCC` 在 0.07–0.15 之间 → **不确定**；需要扩大样本或换任务，不能宣称成功。
- 任一臂弃权率 >20% → 同时报 coverage/accuracy；不能只报 committed 准确率。

#### 7.1.3 为什么有成功可能

1. **操作点有明确的 +0.145 macro-F1 头寸**：事后阈值 0.3 把 0.383 抬到 0.528，accuracy 到 73.13%（仍低于常量 80%，但 macro-F1 超过常量）。这不是模型变强，但说明“默认布尔输出”不是唯一操作点；A1 在 dev 上选阈值，至少能复现这个头寸。
2. **长度规则给了 0.533 的参照**：一个不看代码的规则能到 0.533；如果 A1/A2/A3 连 0.533 都到不了，说明 prompt 连数据先验都没利用好。
3. **CWE 结构有明确的“可攻点”**：CWE-190 5/6、CWE-125 8/13、CWE-787 7/11 已经能到 55%–83%；把 CWE-416（1/20）和 CWE-20（1/8）从 5%/12.5% 拉到 25%–30%，就足以把总体 recall 抬 8–10 pp。A2 的检查表就是针对这两类。
4. **文献支持上下文/ CWE 专门化**：[S5] 在 context-rich 设置下关键 CWE 到 0.7 F1；[S6] CWE-specific 优于 generalist。N1 不能提供仓库级上下文，但可以提供 CWE 特定的证据模板，这是同一方向的最小版本。

#### 7.1.4 失败解释

- **`MCC≤0.07` 且 `macro-F1` 上升**：模型只是学会了“多报”，没有学会排序；函数级任务在现有输入上不可学。下一步不是再调 prompt，而是：
  - 改成语句级/差异行任务（SecVulEval 的原始粒度）；
  - 或提供真实调用者/被调用者上下文（需要仓库 checkout，成本更高）；
  - 或做 20 条 FN 的标签审计，确认多少是“函数级不可判定”。
- **CWE-416 仍 ≤10%**：生命周期/别名推理是独立瓶颈；需要静态 lifetime 证据（CodeQL UAF/leak 查询）或专门的“alloc-free-alias-escape”模板，不是通用 checklist。
- **弃权率 >20%**：模型无法在函数内判定；这时 coverage/accuracy trade-off 是主结果，不能把弃权算错或算对。
- **A3 让长度规则失效但 `MCC` 不升**：原模型确实靠长度；去掉后没有替代信号。这支持“长度伪相关是主因”，但不支持“模型有语义能力”。

#### 7.1.5 功效、成本、停止规则

- n=160，40 个项目；`MCC` 的 cluster bootstrap CI 很宽，MDE 约 0.10–0.15。N1 是**筛选实验**，不是定论；若效应 <0.10，只能写“未检测到”。
- dev 40 只有 8 个负例；A1 的阈值选择方差很大，dev 阈值只作 pilot；如果 dev 阈值的 bootstrap CI 跨 0.5，A1 视为不稳定，不进入 test 主表。
- 4 臂 × 160 = 640 请求；dev 40 × 4 = 160；合计 800。按现有 DeepSeek 证据请求约 $0.0005/次，约 **$0.4–0.6**。
- 停止规则：先跑 dev 40 的 4 臂 pilot；如果 A1/A2/A3 在 dev 上没有一个 `MCC≥0.10`，停止，不跑 test；先改任务/标签审计。

### 7.2 N2：Pair 长度中性化 + 方向平衡 + 双序

#### 7.2.1 要回答的问题

> 单序 86.67% 在去掉长度线索、控制槽位、并要求两序一致之后，还剩多少？MiMo 在方向平衡子集上的 63.6% 是可复现的语义信号，还是 residual length/position？

#### 7.2.2 设计

**构造长度中性化对（length-neutralized pairs）**：

- 对每一对，取较长一侧为目标长度；用**中性注释/空行**把较短一侧填充到与较长一侧的字符数差 ≤2%。
- 只允许空白、`/* ... */`、`// ...`；不得改变任何 token 的语义；用 diff 验证“非空白/非注释行”完全一致。
- 填充内容不包含“vulnerable/safe/fix/bug”等词；固定模板，避免引入新的语义线索。
- 对 6 个精确等长对不做填充。
- 这样长度启发式在每一对上退化为 50%（或 tie 规则），模型必须用代码差异。

**方向平衡子集（预注册敏感性）**：

- 从 180 对中取全部 44 个 fshorter + 44 个按相对长度差最近邻匹配的 vshorter，构成 88 对方向平衡子集；长度启发式按构造 50%。
- 这个子集在本次复核中是事后构造的（MiMo 63.6%、DeepSeek 47.7%）；N2 把它作为**预注册的敏感性分析**，不是主终点。

**四个臂**（每个模型，正/反两序）：

| 臂 | 输入 | 任务 | 目的 |
| --- | --- | --- | --- |
| `B0 original-forced` | 原始 180 对 | 强制 A/B | 控制；复用现有 |
| `B1 neutral-forced` | 中性化 180 对 | 强制 A/B | 去掉长度；主终点 |
| `B2 neutral-evidence` | 中性化 180 对 | 先各写一条漏洞机制/差异行，再选 A/B；允许 `uncertain` | 证据先行；看弃权与 committed |
| `B3 neutral-equivalence` | 中性化 180 对 | “两版本漏洞状态是否相同？若不同，哪个有漏洞、为什么？” | 把“选边”改成“状态比较”；减少槽位 |

**主终点**：`B1` 的交换一致 DA（两序都对）。
**次终点**：`B1` 的 fshorter 子集 DA；槽位偏差（A vs B）；弃权率；committed 准确率；`B2/B3` 相对 `B1` 的 Δ；与 50% 的 McNemar；与原始 `B0` 的 Δ。

**判定规则**：

- MiMo `B1` 交换一致 DA ≥60%，且 vs 50% 的单侧 McNemar p<0.05，且比 50% 高 ≥10 pp → **有限语义信号**。
- DeepSeek `B1` ≥55% → 弱信号；≥60% → 与 MiMo 同档；≤50% → 与现有 47.7% 一致，支持“无信号”。
- 任一臂弃权 >25% → 报 coverage/committed；不能把弃权算错后宣称下降。
- `B1` 的 fshorter 子集 ≤50% → 即使总体 ≥60%，也说明信号集中在长度方向正确的对；不能写“跨版本推理”。

#### 7.2.3 为什么有成功可能

1. **MiMo 在方向平衡 88 对上已经 63.6%**（56/88，95% CI 53.2–72.9，vs 50% p=0.0138）。这不是“总体 86.67%”的重复，而是控制长度方向后的独立信号；N2 的中性化是更强的控制，如果信号真实，应该保留一部分。
2. **DeepSeek 在方向平衡 88 对上 47.7%**（42/88，p=0.749），与随机不可区分；这给 N2 一个明确的负对照：如果 DeepSeek 在中性化后突然 ≥60%，更可能是新 prompt 的伪影，而不是“DeepSeek 原来只是被长度掩盖”。
3. **中性化是语义保持的**：只加空白/注释，不改 token；如果模型仍然能区分，说明它读的是代码差异，不是长度。
4. **文献支持**：[S7] 位置偏差真实且随任务变化；[S8] 代码 judge 对呈现线索敏感，语义保持扰动可改变判定；[S3] 词数/长度是已知伪相关。N2 是把这些控制同时做到位。

#### 7.2.4 失败解释

- **MiMo `B1` ≈50%，DeepSeek ≈50%**：pair 的主要信号是长度方向；原始 86.67% 不能解释为语义推理。应撤回“跨版本推理”主张，保留“强制选择下的判别”作为任务描述。
- **MiMo `B1` 55%–60%**：有弱信号但不稳定；需要扩大样本/换模型，不能写“显著优于长度”。
- **`B2` 弃权 >25% 且 committed 准确率高**：模型只在“有证据”时判；这是 coverage/accuracy trade-off，不是能力提升。报告要同时给弃权率和 committed 准确率。
- **`B3` 比 `B1` 高很多**：说明“选边”框架本身是伪影；状态比较更接近真实任务。下一轮可以改用 equivalence 任务，而不是继续优化 A/B prompt。
- **中性化后模型输出变得模板化/复述注释**：说明填充注释被当成线索；需要换填充方式（随机空白/不可见字符？不，不能用不可见字符）或改成“把两侧都填充到同一长度”，让注释对称。

#### 7.2.5 功效、成本、停止规则

- 180 对，交换一致 DA 的 MDE 约 10–12 pp；88 对方向平衡子集约 15–20 pp。MiMo 现有 63.6%，要检测“≥60% vs 50%”在 88 对上约有 80% 功效（效应 13.6 pp，n=88）。
- 新增 3 臂（B1–B3）× 180 对 × 2 序 × 2 模型 = **2,160 请求**；含 B0 复用共 2,880 条记录。若只跑两个模型的 `B1/B2`，约 1,440。按 pair 请求约 $0.00085/次，约 **$2–3**。
- 停止规则：先跑 44 个 fshorter 的 pilot（两序 × 2 模型，176 请求）；如果 MiMo `B1` fshorter 两序都对 <40%，停止全量，直接写“无信号”。

### 7.3 N3：CodeQL may 查询的证人过滤

#### 7.3.1 要回答的问题

> 23 个 FP 是否可以用“释放证人”在不损失 may TP 的情况下过滤？如果能，CodeQL 能否同时做到 P≥0.90、R≥0.90？如果不能，是不是只能报三个操作点（never/C-only/union）？

#### 7.3.2 设计

数据：现有 CodeQL test 140 预测中的 45 个 may hit（22 TP / 23 FP）。不重新跑 CodeQL 也能做 LLM 臂；静态证人臂需要一次本地后处理（或重跑查询）。

五个臂：

| 臂 | 规则 | 目的 |
| --- | --- | --- |
| `C0 never-only` | 只用 `cpp/memory-never-freed` | 高精度控制（46/0/24/70） |
| `C1 may-union` | 现有并集 | 高召回控制（68/23/2/47） |
| `C1b may-C-only` | `never` + may 仅在 C 上 | 高精度折中（60/0/10/70） |
| `C2 static-witness` | 对每个 may 告警，检查是否存在“所有路径上的 free/delete 证人”：① 别名/引用/遮蔽；② sink 函数摘要；③ 容器元素逃逸。有证人 → 删；无 → 留 | 主干预；针对 4 个模式 |
| `C3 llm-adjudicator` | 输入：分配点、may 诊断、函数体、sink 签名；输出：只有能引用“缺失 free 的具体行/路径”时才判 FP；否则 keep（fail-open） | 看 LLM 能否在无 trace 时补足 |
| `C4 hybrid` | 先 `C2`；未决项给 `C3`；仍不确定 → keep | 工程折中 |

**主终点**：`recall≥0.90` 时的 precision（或 macro-F1）。
**次终点**：TP 损失、FP 删除数、分查询/语言、成本；`C2` 的规则覆盖率（45 个 may hit 中有多少能被静态证人判定）。

**判定规则**：

- `C2` 或 `C4`：`P≥0.90` 且 `R≥0.90`，TP 损失 ≤2 → **成功**；可以写“在 Juliet C++ 上，证人过滤把 may 查询的精度从 0.489 提到 ≥0.90，召回保持 ≥0.90”。
- `P≥0.85` 且 `R≥0.95`，TP 损失 ≤2 → **部分成功**；写“高召回操作点”。
- 只能做到 never-only（P=1.0/R=0.657）、C-only（P=1.0/R=0.857）或 union（P=0.747/R=0.971）→ **失败（相对 N3 目标）**；写“三个操作点”，不写“更好的工具”。
- `C3` 的 TP 损失 >5 → LLM 裁决不可用；与 §5 的验证器失败一致。

#### 7.3.3 为什么有成功可能

1. **23 个 FP 是可命名的 4 个模式**：`_33` 15 个（别名/遮蔽）、`_22` 3 个（sink）、`_72` 3 个（容器）、`_54` 2 个（sink）。这不是 23 个随机错误，而是 4 个建模缺口。
2. **never-only 是 0 FP；may C-only 是 60 TP / 0 FP（R=0.857）**：说明高精度基座存在，C 侧已满分；问题集中在 C++ 的 8 个 may TP vs 23 个 FP。
3. **上界很清楚**：如果 FP 全删、TP 全留，P=1.0/R=0.971；如果丢一半 may TP，P=1.0/R=0.814。C-only 已经到 0.857；N3 的目标（R≥0.90）落在 C-only 与理想上界之间。
4. **文献有直接先例**：[S10] 的查询精化删除 81.8% 已审 FP、保留 7/8 TP；[S13] 的轻量别名/资源泄漏分析正好覆盖 `_33`/sink；[S9] 的 ZeroFalse 在结构化 trace 下 P/R>90%。N3 的静态证人比 ZeroFalse 更窄，但更容易做对。

#### 7.3.4 失败解释

- **`C2` 只能处理 `_33`，处理不了 sink/容器**：说明别名分析不够；需要过程间 sink 摘要/容器建模。可以先把 `_33` 的 15 个 FP 修掉，保留 sink 的 8 个 FP，报“部分修复”。
- **`C2` 把 `_33` 的 5 个 TP 也删了**：说明“有 free 证人”不等于“所有路径都有 free”；需要 must-free 支配关系，而不是 exists-free。这是最可能的失败模式。
- **`C3` 删 FP 也删 TP**：与 §5 的验证器同构；LLM 没有 trace 时不能区分“释放写在 sink”与“没释放”。这时不要继续调 prompt，直接回到静态证人。
- **Juliet 上成功、真实项目失败**：23 个 FP 是 Juliet 的 4 个变体；真实项目的 sink/容器/别名更复杂。报告必须写“Juliet C++ 子集”，不能外推为“CodeQL 精度修复”。

#### 7.3.5 功效、成本、停止规则

- 45 个 may 单元，23 FP / 22 TP；样本小，但效应大（要删 23 个 FP）。精确率/召回率的 Wilson CI 很宽；用 exact McNemar 比较 `C2` vs `C1` 的逐单元正确性。
- 分变体（`_33` n=20、`_22` n=4、`_72` n=6、`_54` n=3）只能描述，不能做显著性。
- `C2` 本地实现；`C3/C4` 45–90 次 LLM，<$0.1。若重跑 CodeQL 查询，200 单元 × 42.5 s ≈ 2.4 h，无 API。
- 停止规则：先实现 `C2` 的 `_33` 别名规则；如果它在 20 个 `_33` 单元上不能做到“删 15 FP、留 5 TP”，停止，不做全量；先修 must-free 支配。

### 7.4 N4：机制门控验证器 + 新 holdout

#### 7.4.1 要回答的问题

> 验证器能否在**没见过的数据**上，把 FP 排在 TP 前面？如果能，固定预算下的撤销精确率能否显著高于正例 FP 基准率？如果不能，是否应该放弃“二次验证提升检测”，改用外部 oracle？

#### 7.4.2 设计

**新 holdout**：

- 用 `splits/test_pairs_180.json` 的 360 个 side（180 vulnerable / 180 fixed）作为新检测池；先确认与 `test_detection_160.json` 的 source idx 无交集（脚本检查）。
- 第一遍：用现有 evidence prompt 或 direct prompt 跑 360 个 side，得到正例预测（预计 100–140 个，取决于 prompt；FP 按现有 FPR 25%–34% 估计约 45–60 个）。
- 第二遍：只验证第一遍的正例；负例不动。
- 这样 test 160 不再被验证器看到；新 holdout 的标签只用于评分，不进入 prompt。

**五个臂**：

| 臂 | 规则 | 目的 |
| --- | --- | --- |
| `V0 no-retraction` | 保留第一遍 | 控制 |
| `V1 random-retraction` | 同预算随机撤 k 个正例 | 正确的 null；比较“选择性” |
| `V2 mechanism-gated` | 只在能引用具体 FP 机制（guard/sanitization/unreachable free/alias）且给出行号时撤；`insufficient_evidence` = abstain（keep） | 修 §5 的语义 bug |
| `V3 fix-guided` | 让模型给“最小 fix”；如果 fix 已在代码中（行匹配/静态检查）→ 撤；如果 fix 不在 → keep | 把主观判断变成可检查事实；[S19] |
| `V4 jury` | 两个模型都给出具体机制才撤；否则 keep | 降方差；看是否比单模型好 |

**主终点**：验证器分数对 FP/TP 的 AUROC（FP 为正类）。分数可以是 `P(FP)`、`retract` 的置信度、或 `V2/V3` 的机制强度；**必须在看 test 前固定**。
**次终点**：固定预算（k = 第一遍正例的 30%/50%）下的撤销精确率；post macro-F1；TP 损失；弃权率；成本。

**判定规则**：

- `AUROC≥0.65` → 有排序信号；可以在某个预算下做选择性撤销。
- `AUROC 0.55–0.65` → 弱信号；只能做“高预算、低 TP 损失”的保守规则，不能宣称提升。
- `AUROC≤0.55` → 无信号；放弃“二次验证提升检测”；改用编译/PoC/静态证人。
- 撤销精确率 ≥40% 且 TP 损失 ≤10% → 可用的操作点；即使 AUROC 不高，也可以作为“保守过滤器”。
- post macro-F1 比 pre 高 ≥0.02 且 McNemar p<0.05 → 才算“检测提升”；否则只算“操作点变化”。

#### 7.4.3 为什么有成功可能（以及为什么先验不高）

**支持**：

1. 表层失败是 `insufficient_evidence` 语义（67%–71% 的撤销）；把它改成 abstain 是明确的修复。
2. 具体类型里有高精度子集：`guard_present` 四臂 precision 60%–100%（n=3–11）；`no_reachable_flow` 50%–100%（n=1–3）。说明“具体机制”不是无效，而是覆盖小；机制门控可以保住这部分，同时把 `insufficient_evidence` 改成 abstain。
3. `fix-guided` 把“是否有漏洞”变成“fix 是否已存在”，这是可检查的代码事实；[S19] 报告这种 filter 能改进可靠性。
4. 新 holdout 去掉 test 复用；至少能排除“post-hoc 过拟合”。

**反对（必须写进预注册）**：

1. 现有验证器置信度 AUROC 0.28–0.46，**低于随机**；这不是阈值能修的。
2. 具体机制的覆盖太低：`guard_present` 每臂 3–11 个，`no_reachable_flow` 1–3 个；即使 precision 高，也不足以改变总体 macro-F1。不能把“高精度小覆盖”写成“验证器有效”。
3. [S17] 说没有外部反馈的自纠正不可靠；[S19] 说更详细的 prompt 反而提高误判率。N4 如果只是“更严格的 rubric”，很可能失败。
4. 因此 N4 的成功先验是**低到中**；它的价值在于“如果失败，可以干净地放弃这条路线”，而不是“再给验证器一次机会”。

#### 7.4.4 失败解释

- **`AUROC≤0.55`**：验证器没有 FP/TP 排序信号；不要再调 prompt。改用：
  - 外部 oracle：编译 + LSan/Valgrind + PoC；
  - 静态证人：CodeQL/Clang 的路径证据；
  - 或把验证器降级为“弃权/人工复核”触发器，而不是自动撤销。
- **`V3` 的 fix 已经存在但模型仍判 TP**：说明模型不能可靠匹配 fix 与代码；fix-guided 失败。
- **`V2` 撤销精确率高但覆盖极低（<10 个）**：只能做“高精度小覆盖”，不能提升总体 macro-F1；报 PR 曲线，不报单点。
- **新 holdout 的 FP 基准率与 test 160 不同**：撤销精确率不能直接与旧 20% 比较；必须用新 holdout 的基准率做超几何检验。

#### 7.4.5 功效、成本、停止规则

- 360 sides，第一遍正例约 100–140；FP 按现有 FPR 25%–34% 估计约 45–60。AUROC 的 SE 约 0.05–0.06；MDE 约 0.08–0.10。
- 固定预算撤销精确率需要至少 80 个撤销才能区分 40% vs 20%；如果第一遍只有 100 个正例、只撤 30 个，CI 会很宽。必要时把预算提高到 50%，或扩大 holdout（先用脚本确认 dev 40 与 360 sides 无 source idx/commit 重叠，再合并）。
- 成本：360 第一遍 + 约 140 第二遍 × 2 模型 ≈ 1,000 请求；< $1。
- 停止规则：先跑 80 个正例的 pilot；如果 `V2` 的具体机制撤销 <10 个，停止，直接写“覆盖不足”；不要为了显著性降低门槛。

### 7.5 G0：动态覆盖率门禁（不是实验）

#### 7.5.1 要回答的问题

> 任何一个动态 `clean`，到底执行了多少代码？`clean` 是“这条路径没看到”，还是“所有路径都看过”？`nogobal` 的 0 FP 是原始 0 FP 还是归因后 0 FP？

#### 7.5.2 门禁要求

1. **编译插桩**：在现有 `-fsanitize=address -O0 -g` 基础上加 `--coverage`（gcov）或 `-fprofile-instr-generate -fcoverage-mapping`（LLVM）；不改变 harness 语义。
2. **每个单元/模式记录**：行覆盖率、分支覆盖率、执行的 `free/delete` 站点列表；输出 `coverage.json`。
3. **`clean` 的判定**：
   - 行覆盖率 ≥90%，且目标函数内每个 `free/delete` 站点至少执行一次 → 可以写 `clean`；
   - 否则写 `undecided`，不计入 TN；
   - 报告 `clean` 时附覆盖率数字（例如“clean at 92% line / 78% branch”）。
4. **多输入**：对随机分支变体（`globalReturnsTrueOrFalse()`；全量 3,316 中有 14 个，test 140 本次复核未见 `_12` 变体）跑 20 个固定种子；如果 20 次都 clean，写“clean at 20 seeds”并给 Clopper-Pearson 上界，不写“无泄漏”。
5. **原始/归因分离**：所有表同时给 raw leak 和 attributed leak；`nogobal` 的 70/70 good raw leak 必须显式列出。
6. **归因审计**：抽 20 个单元（10 good / 10 bad），人工检查分配栈第一帧是否真的在单元源码；如果归因错 1 个，0 FP 结论就要重写。

#### 7.5.3 成功线

- 所有动态 `clean` 都带覆盖率；没有覆盖率的一律 `undecided`。
- 12 个条件可观测单元仍有证据；`default` 与旧 ASan 仍 140/140 一致。
- `nogobal` 的 0 attributed FP 在归因审计后仍成立；70/70 raw leak 被解释为工具链/运行时，而不是单元源码。

#### 7.5.4 失败解释

- **行覆盖率 <90% 占多数**：`clean` 不可解释；140/140 只能写成“判定覆盖”，不能写“检测覆盖”。动态章节的“0 FP”要降级为“0 attributed FP on observed paths”。
- **20 seed 后某些 good 单元出现单元源码归因泄漏**：归因规则或 harness 有问题；先修 harness，不能把它写成 FP。
- **`realloc_fail` 只适用 14 个单元**：不要把它写成通用模式；它是定向故障注入，覆盖率要按“适用单元”分母报。
- **归因审计发现 1 个错例**：0 FP 结论不成立；需要重新审 70 个 good（必要时加 70 个 bad）的栈。

### 7.6 四个实验之间的关系

```
N1 (Tier A 低 F1) ──→ 如果 MCC 仍低，说明函数级任务缺上下文
        │
        └──→ 与 N4 共享“函数级上下文不足”的解释

N2 (pair 长度/位置) ──→ 如果中性化后无信号，pair 主张撤回
        │
        └──→ 与 N3/N4 共享“证据是否可检查”的方法论

N3 (CodeQL FP) ──→ 如果静态证人可行，给 N4 提供“外部证据”模板
        │
        └──→ 如果 LLM 裁决失败，印证 N4 的负先验

N4 (验证器) ──→ 如果 AUROC≤0.55，放弃二次验证，改用 N3 式外部证据

G0 (覆盖率) ──→ 约束所有动态 claim；不通过则动态章节降级
```

**优先级**：

1. **G0**（0 API，先做；否则动态结论不可写）。
2. **N2 的零 API 复核**（方向平衡 88 对已做；先把它写进预注册，再决定是否跑全量）。
3. **N3 的 `_33` 静态证人**（本地，45 单元；最快看到“是否可行”）。
4. **N1 的 dev pilot**（4 臂 × 40，低成本；先看 MCC 是否有 0.10 的苗头）。
5. **N4**（最后；负先验最高，且依赖新 holdout 的第一遍）。

## 9. 风险、替代方案与“如果都失败”

### 9.1 如果四个实验都失败

这不是“项目失败”，而是一个明确的科学结论：

> **在当前的函数级、去上下文、带长度先验的 SecVulEval 子集上，LLM 的 detection/pair 信号不足以超过简单先验；二次验证没有 FP/TP 排序信号；CodeQL may 查询的 FP 需要过程间证人，LLM 裁决不够；动态 140/140 是定向模式并集，不是通用检测。**

如果 N1–N4 都失败，正确的下一步不是“再换一个模型”，而是：

1. **改任务粒度**：从函数级二分类改为 SecVulEval 的语句级定位/理由正确 [S1]；从“选哪个版本有漏洞”改为“哪条差异行引入了漏洞”。
2. **补真实上下文**：调用者/被调用者、数据流、构建配置；[S5] 显示 context-rich 可以把关键 CWE 到 0.7 F1。
3. **用可执行 oracle**：编译 + LSan/Valgrind + PoC；[S19] 的 fix-guided filter 是一个中间形态。
4. **接受负结果**：把“函数级任务不可学”的边界写清楚；这比再报一个 0.4 的 macro-F1 更有价值。

### 9.2 如果只能做一个

**G0 + N2 的零 API 复核**：

- G0 不需要新模型调用，直接决定动态章节能不能写“0 FP”。
- N2 的 88 对方向平衡复核已经完成（MiMo 63.6%、DeepSeek 47.7%）；把它写进预注册，再决定是否跑中性化全量。
- 这两个动作的共同点：**先修解释，再花钱**。

如果只能做一个“新 run”，选 **N3 的 `_33` 静态证人**：45 个单元、本地、最快看到“FP 是否可修”；它也能给 N4 提供“外部证据”模板。

## 附录 A：本次复核的公式与构造

### A.1 指标

```
macro-F1 = (F1_positive + F1_negative) / 2
F1_positive = 2TP / (2TP + FP + FN)
F1_negative = 2TN / (2TN + FN + FP)

MCC = (TP*TN - FP*FN) /
      sqrt((TP+FP)(TP+FN)(TN+FP)(TN+FN))
```

### A.2 长度规则

- dev 40 上扫描所有唯一 `len(func_body)` 阈值，方向 `≤` / `>`，取 dev macro-F1 最大者。
- 选中：`len ≤ 3227 → vulnerable`，dev macro-F1 `0.5699`。
- test 160 应用同一规则，不重新选阈值。
- 95% CI：按 project 聚类、2,000 次 percentile bootstrap，seed=20261122。

### A.3 置信度操作点

```
score = confidence            if is_vulnerable
      = 1 - confidence        if not is_vulnerable
```

- 这是事后 oracle：阈值在 test 上扫描，只用于给 N1 一个“操作点头寸”的上界，不可部署。
- 阈值 0.3 的混淆矩阵：111 TP / 26 FP / 17 FN / 6 TN。

### A.4 Pair 方向分层与 88 对平衡子集

### A.5 CodeQL may 查询的证人

- 45 个 may hit = 22 TP + 23 FP；全部 `code_flows=0`。
- 23 个 FP 的变体：`_33` 15、`_22` 3、`_72` 3、`_54` 2。
- 证人规则（N3 `C2`）：
  1. 别名/引用/遮蔽：若 `free/delete` 作用于 `T*&` 或块内同名变量，且支配所有出口 → 删 may。
  2. sink 摘要：若分配只逃逸到“必定 free/delete 其参数”的函数，且该调用支配所有出口 → 删 may。
  3. 容器：若指针进入容器且容器只传给 freeing sink → 删 may。
- 不能用 `code_flows`、词法 `free` 计数替代；本次复核已证明它们会误删 TP。语言过滤可作 C-only 操作点（0.928），但不能解决 C++ may TP/FP。

### A.6 验证器 AUROC
